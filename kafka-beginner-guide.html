Module 1
What & Why of Kafka

What is Kafka?

Apache Kafka is a distributed, durable, high-throughput event streaming platform. In one sentence: it's a system where producers write events into ordered logs called topics, and many independent consumers can read those events at their own pace, while Kafka guarantees ordering per partition, durability via replication, and horizontal scalability.

It's open source (Apache 2.0 license) and was originally built at LinkedIn in 2010 by Jay Kreps, Neha Narkhede, and Jun Rao. They later founded Confluent, the company behind much of Kafka's commercial ecosystem. Kafka was donated to the Apache Software Foundation in 2011 and became a top-level project in 2012.

The name "Kafka" was picked by Jay Kreps because the system is "a writing system" and he liked Franz Kafka's writing — there's no acronym, no deep technical meaning.

What problem does Kafka solve?

Before Kafka, integrating N systems with M systems meant N×M point-to-point connections — a tangled mess where each producer knew about each consumer. Kafka introduced a single backbone: every system writes to Kafka, every system reads from Kafka. N+M instead of N×M.

Without Kafka (N×M coupling)             With Kafka (N+M)

  App A ──┬──► DB                           App A ──►┐
          ├──► Search                        App B ──►├─► Kafka ─►┌──► DB
          └──► Analytics                     App C ──►┘            ├──► Search
  App B ──┬──► DB                                                  ├──► Analytics
          ├──► Search                                              └──► Cache
          └──► Cache
  App C ──┬──► Search
          └──► Analytics

Common use cases

  • Asynchronous service communication — replace synchronous HTTP between microservices.
  • Activity tracking — clickstreams, page views, user actions.
  • Log aggregation — centralize logs from many services into a search store.
  • Metrics & monitoring — pipe metrics from thousands of agents.
  • Stream processing — real-time analytics, fraud detection, anomaly detection.
  • Event sourcing — store every state change as an immutable event.
  • Database replication / Change Data Capture (CDC) — stream DB row changes to other systems.
  • IoT data ingestion — millions of sensors producing telemetry.

Who uses Kafka?

Netflix, LinkedIn, Uber, Airbnb, Walmart, PayPal, Goldman Sachs, Twitter (X), Pinterest, Spotify, Shopify, and tens of thousands of others. LinkedIn alone processes over 7 trillion messages per day on Kafka.

Kafka's headline numbers

  • Throughput: millions of messages/sec on commodity hardware.
  • Latency: low single-digit milliseconds end-to-end.
  • Storage: petabytes per cluster (logs are flat files on disk).
  • Retention: configurable from minutes to forever.

Module 2
When (Not) to Use Kafka

Kafka is a great fit when…

  • You have multiple consumers for the same data (each consuming independently).
  • You need high throughput (10k+ msg/sec).
  • You need to replay events (e.g., reprocess last week's data with new code).
  • You need durable message storage with strict ordering per key.
  • You're decoupling services that change independently.
  • You're doing real-time stream processing.

Kafka is overkill / wrong choice when…

  • You need a request-response RPC pattern (use HTTP/gRPC).
  • You only have one producer and one consumer with a few hundred messages/day (use a SQL queue table or RabbitMQ).
  • You need long-delay scheduled messages ("send this in 7 days") — Kafka doesn't have native delays. Use a scheduler.
  • You need per-message TTL or priority queues — Kafka has neither natively.
  • You need complex routing (topic-exchange, headers-exchange) — RabbitMQ is built for this.
  • Your team is small and has no infrastructure capacity — Kafka has real ops overhead.
Reality check: Kafka is not a drop-in replacement for a "queue". It's an event log. If your mental model is "I put a job, a worker takes it and the job is gone," consider RabbitMQ, AWS SQS, Redis Streams, or a simple DB-backed queue first.

Module 3
The Mental Model

Picture a shared notebook that's append-only:

  • Anyone can write a new line at the bottom (producers).
  • Anyone can read any line, starting from wherever they left off (consumers).
  • Lines are never erased until a configured time/size cutoff (retention).
  • Every line gets a permanent, sequential line number (offset).
  • Reading a line does not delete it. Multiple readers see the same line.

The crucial difference from a traditional message queue:

TraitTraditional Queue (RabbitMQ, SQS)Kafka (Log)
Storage modelMessages deleted after consumptionAppend-only log; messages stay until retention expires
Multiple consumersEach message goes to oneEach consumer group reads independently
ReplayGenerally noYes — rewind offsets
OrderingGenerally per queuePer partition
Throughput10k–100k msg/sec1M+ msg/sec
RoutingRich (exchanges, headers)Simple (topic + partition key)

Once "log, not queue" clicks in your head, every other Kafka concept becomes easier.

Module 4
Core Vocabulary

Event / Message / Record

A single immutable fact: "user 42 logged in at 2026-05-07 10:31 UTC". A Kafka record has:

  • Key (optional bytes) — used to choose a partition. Same key → same partition → ordered.
  • Value (bytes) — the actual payload (JSON, Avro, Protobuf, plain text).
  • Headers (optional key-value pairs) — metadata like trace IDs, content type.
  • Timestamp — set by producer or broker.
  • Offset — assigned by broker on write; unique per partition.

Topic

A named, ordered stream of records. Examples: orders, user.signups, iot.telemetry. Topics live forever; you can produce and consume at any time.

Partition

A topic is split into 1 or more partitions. Each partition is an ordered, immutable, append-only sequence of records on a specific broker's disk. Partitions are the unit of parallelism and distribution.

Topic "orders" (4 partitions)

P0:  [r0][r1][r2][r3][r4]                    ◄── on broker A
P1:  [r0][r1][r2]                            ◄── on broker B
P2:  [r0][r1][r2][r3][r4][r5][r6]            ◄── on broker C
P3:  [r0][r1][r2][r3]                        ◄── on broker A

Offset

The position of a record within a partition. Strictly increasing per partition (P0 offset 7, P1 offset 7 are unrelated). Once assigned, never changes.

Producer

Client that publishes records into topics. Picks the partition (via key hash, round-robin, or custom logic).

Consumer

Client that subscribes to one or more topics and reads records. Tracks its own progress via committed offsets.

Consumer Group

A set of consumer instances sharing a group.id. Kafka assigns each partition to exactly one consumer in the group. This is how you scale processing horizontally.

Broker

A single Kafka server. Holds partitions, serves producer writes and consumer reads, replicates data to other brokers.

Cluster

A group of brokers that work together. Identified by a unique cluster ID. Production clusters are typically 3–30 brokers.

Controller

One broker in the cluster is elected as the controller. Responsible for leader elections, partition reassignment, and cluster-wide metadata. With KRaft mode, controllers are dedicated nodes.

Replica / Leader / Follower

Each partition has 1 leader replica and N–1 follower replicas. All reads/writes go to the leader; followers replicate from the leader.

ISR (In-Sync Replicas)

The set of replicas (including leader) that are caught up with the leader. Only ISR members are eligible to be promoted to leader if the current leader fails.

Retention

How long Kafka keeps records. Configured per topic via retention.ms (time) or retention.bytes (size). Default is 7 days.

Log Compaction

Alternative retention mode: keep at least the latest record for each key. Older records for the same key are deleted in background. Used for stateful streams (e.g., user profiles by userId).

Zookeeper / KRaft

Old Kafka (≤ 2.x) used Apache Zookeeper to manage cluster metadata. Modern Kafka (≥ 3.3) uses KRaft (Kafka Raft) — Kafka manages its own metadata via the Raft consensus algorithm, no Zookeeper needed. Zookeeper is being removed entirely in Kafka 4.0.

Key things to internalize:

  • Producer never talks to followers directly — only the leader of each target partition.
  • Disk writes are sequential appends — that's why Kafka is so fast.
  • Consumers poll brokers (Kafka does not push). The poll-based model is what enables backpressure.
  • Offsets are committed by the consumer, stored in an internal topic __consumer_offsets.

(L) = Leader replica, (F) = Follower replica

Broker responsibilities

  • Accept producer writes for partitions it leads.
  • Replicate data to followers.
  • Serve consumer fetches for partitions it leads (or follower-fetch on rack-aware setups).
  • Track ISR membership.
  • Participate in elections.

Controller responsibilities

  • Store cluster metadata (topics, partitions, configs, ACLs).
  • Detect broker failures and trigger leader re-election.
  • Coordinate partition reassignment when topics are scaled.
  • Manage topic creation, deletion, config updates.

KRaft mode (modern)

In KRaft mode, a small set of brokers (usually 3 or 5) act as a Raft quorum that holds the metadata log. They're called controller nodes. They can be dedicated or shared with regular brokers. The metadata itself is stored as another Kafka log, replicated via Raft.

Why KRaft replaced Zookeeper

  • One system to operate instead of two.
  • Metadata changes (topic creation, etc.) propagate faster.
  • Clusters can scale to millions of partitions, not just hundreds of thousands.
  • Faster controller failover (seconds instead of tens of seconds).
Recommendation for new clusters in 2026: always use KRaft. Zookeeper-based clusters work but are end-of-life as of Kafka 4.0.

Module 7
Storage Internals

This is where Kafka's performance reputation comes from. Understanding storage helps you tune retention, sizing, and recovery.

Logs and segments

Each partition is stored on disk as a directory like orders-0/ (topic name + partition id). Inside that directory, the partition log is split into segments — fixed-size files (default 1 GB each).

/var/lib/kafka/logs/orders-0/
├── 00000000000000000000.log        ◄── records
├── 00000000000000000000.index      ◄── offset → file position
├── 00000000000000000000.timeindex  ◄── timestamp → offset
├── 00000000000000098234.log        ◄── next segment, starts at offset 98234
├── 00000000000000098234.index
├── 00000000000000098234.timeindex
└── leader-epoch-checkpoint

Why segments? So old data can be deleted by simply unlinking whole files — far cheaper than rewriting the log.

The active segment

Only the latest segment is being written to (the "active" segment). All older segments are read-only. When the active segment hits segment.bytes or segment.ms, it's "rolled" — closed and a new segment is created.

Indexes

Each segment has two sparse indexes:

  • Offset index — maps logical offset → byte position in the .log file. Sparse: an entry every index.interval.bytes (default 4096 bytes).
  • Timestamp index — maps timestamp → offset. Used for seekToTimestamp consumer operations.

Why Kafka is so fast on disk

  • Sequential I/O — appends only. SSDs and spinning disks are both very fast at sequential writes.
  • Zero-copy reads via sendfile syscall — data goes directly from kernel page cache to socket without copying into Kafka's user space.
  • Page cache — Linux caches recent reads; "hot" consumers read from RAM, never touch disk.
  • Batching & compression — producers send batches; broker writes the batch as one append.

Retention & cleanup

Two cleanup policies:

  • delete (default) — drop whole segments older than retention.ms or beyond retention.bytes.
  • compact — keep at least the latest record per key (see Module 9).
  • compact,delete — both, combined.

Module 8
Replication & ISR

Kafka's durability guarantee comes from replication. Every partition has a replication factor (RF) — typically 3 in production.

How replication works

  1. One replica is the leader; the rest are followers.
  2. Producer sends record to leader.
  3. Leader appends to its log.
  4. Each follower issues a fetch request to the leader (just like a consumer would). Followers pull, leader doesn't push.
  5. Followers append, then send a fetch with their new "high water mark" so the leader knows they're caught up.
  6. The leader maintains the ISR set — followers caught up within replica.lag.time.max.ms (default 30s).

The High Water Mark (HWM)

Consumers can only see records that have been replicated to all ISR members. This boundary is the high water mark. Records past the HWM exist on the leader but aren't visible until replication catches up. This prevents consumers from seeing data that could be lost in a leader failover.

Leader log:    [r0][r1][r2][r3][r4][r5][r6][r7]
                                       ^ HWM = 5
                                       └── visible to consumers up to r5
                                          r6 and r7 not yet replicated to all ISR

Consumers see: [r0][r1][r2][r3][r4][r5]

Leader failover

If the leader broker dies:

  1. The controller detects it (no heartbeat for broker.session.timeout.ms).
  2. The controller picks a new leader from the ISR set (preferring the "preferred replica" if it's in ISR).
  3. Producers/consumers refresh metadata, reconnect to the new leader.

Min in-sync replicas

min.insync.replicas (topic config) — the minimum number of replicas that must be in ISR for the leader to accept writes when the producer uses acks=all. Typical: RF=3, min.insync.replicas=2. This means you can lose 1 replica and still write, but not 2.

Unclean leader election

If unclean.leader.election.enable=true and ISR becomes empty, Kafka will elect an out-of-sync replica as leader. This restores availability but loses data. The default is false — prefer correctness over availability.

Module 9
Log Compaction

Sometimes you want Kafka to keep the latest value per key, forever. Example: a topic of user profiles, keyed by userId. You only care about each user's current state, not the history.

Set cleanup.policy=compact on the topic. Kafka runs a background "log cleaner" that periodically rewrites old segments, keeping only the most recent record per key.

Before compaction:
  [k=alice, v=v1][k=bob, v=v1][k=alice, v=v2][k=carol, v=v1][k=alice, v=v3][k=bob, v=v2]

After compaction:
  [k=carol, v=v1][k=alice, v=v3][k=bob, v=v2]

Tombstones

To "delete" a key in a compacted topic, produce a record with value=null. The compactor keeps the tombstone for delete.retention.ms (so consumers can see the deletion), then removes both the tombstone and prior values for that key.

Use cases for compaction

  • Materialized state (current user profiles, account balances).
  • Kafka Streams' internal state stores use compacted topics.
  • Configuration broadcasting.
  • Database CDC where you only care about latest row state.

Partitioner strategies

  • DefaultPartitioner: if key is set, hash(key) % numPartitions; if not, sticky partitioning (pick a random partition, stay there until batch is sent — improves batching).
  • UniformStickyPartitioner: similar, used in older versions.
  • Custom: implement Partitioner for routing logic.

Idempotent producer

With enable.idempotence=true:

  1. Producer registers with a Producer ID (PID) on first send.
  2. Each record gets a sequence number per partition.
  3. Broker tracks the highest sequence per (PID, partition) and rejects duplicates.

This eliminates duplicates from producer retries. It does not protect against application-level retries (e.g., if your code calls send() twice for the same business event).

Async vs sync send

// Async (fast, recommended)
producer.send(record, (metadata, exception) -> {
    if (exception != null) handleError(exception);
});

// Sync (slow, only when you really must wait)
RecordMetadata md = producer.send(record).get();

Common producer pitfalls

  • Calling send() in a loop without batching — fix with linger.ms=5–20.
  • Forgetting to flush() or close() on shutdown — buffered records lost.
  • Using sync sends for high-volume — kills throughput.
  • Using key=null when ordering matters — round-robin breaks ordering.

Consumers Deep Dive

Consumer poll loop

while (running) {
    ConsumerRecords records = consumer.poll(Duration.ofMillis(500));
    for (ConsumerRecord r : records) {
        process(r);
    }
    consumer.commitSync();   // or commitAsync()
}

Kafka uses a pull model. The consumer polls; the broker doesn't push. This gives the consumer flow control.

Consumer group coordination

When consumers join/leave a group, Kafka does a rebalance:

  1. One broker is the group coordinator for this group (chosen by hash of group.id).
  2. One consumer in the group is elected the group leader. It computes the assignment.
  3. The coordinator distributes the assignment to all members.
  4. Each consumer starts fetching from its assigned partitions.

Rebalance protocols

  • Eager rebalancing (legacy): all consumers stop, surrender assignments, get new ones, resume. "Stop the world." Causes latency spikes.
  • Cooperative rebalancing (incremental, default in newer versions): only consumers losing partitions pause briefly; everyone else keeps going. Much smoother.
  • Static membership (group.instance.id): consumers identify themselves with a stable ID; transient restarts don't trigger rebalances.

Offset management

Three ways to commit:

  • Auto-commit — Kafka commits every auto.commit.interval.ms. Easy but can lose messages on crash.
  • Sync commit — commitSync(). Blocks, retries, durable. Slower.
  • Async commit — commitAsync(). Non-blocking, doesn't retry by default. Fastest, riskier.

Recommended pattern: commitAsync() in the loop, commitSync() on shutdown.

Manual partition assignment

Skip groups entirely with consumer.assign(partitions). Useful for batch jobs or when you need full control. No rebalancing, no auto-offset-reset.

Seeking

consumer.seek(partition, offset);              // jump to specific offset
consumer.seekToBeginning(partitions);           // rewind
consumer.seekToEnd(partitions);                 // skip to live tail
consumer.offsetsForTimes(timestampMap);         // find offset by timestamp

Common consumer pitfalls

  • Auto-commit + slow processing → messages "committed" before processed → lost on crash.
  • Processing taking longer than max.poll.interval.ms → kicked out → rebalance storm.
  • Not closing the consumer → no graceful leave → 45s wait for the group to rebalance.
  • Sharing a consumer across threads — not thread-safe.

Module 12
Delivery Semantics

Three possible guarantees. Pick what your use case needs:

At-most-once

Records may be lost, never duplicated. Achieved by committing the offset before processing.

poll → commit offset → process record
                       (if crash here, record is lost)

Use when: dropping data is OK, duplicates are unacceptable. Rare in practice.

At-least-once (default)

Records may be duplicated, never lost. Achieved by committing offset after processing.

poll → process record → commit offset
       (if crash here, record is re-delivered)

Use when: you can dedupe downstream or the operation is idempotent (e.g., upsert by primary key).

Exactly-once

Records processed once, no duplicates, no losses. Requires:

  • Idempotent producer.
  • Transactional producer + consumer (next module).
  • Or: at-least-once + downstream idempotency by message ID.
Hard truth: end-to-end exactly-once across all systems (Kafka → DB, Kafka → external API) is hard. Kafka-to-Kafka exactly-once works via transactions. Kafka-to-DB exactly-once requires the transactional outbox pattern or 2PC alternatives.

Module 13
Transactions & Exactly-Once

Kafka transactions let you atomically write to multiple topics/partitions and commit consumer offsets together. Either everything is visible, or nothing.

Transactional producer setup

props.put("transactional.id", "my-app-v1");  // unique per producer instance
props.put("enable.idempotence", "true");      // implied by transactional.id

producer.initTransactions();

producer.beginTransaction();
try {
    producer.send(record1);
    producer.send(record2);
    producer.sendOffsetsToTransaction(offsets, consumerGroupMetadata);
    producer.commitTransaction();
} catch (Exception e) {
    producer.abortTransaction();
}

How it works internally

  1. Producer registers a transactional.id; gets a Producer ID (PID) and epoch.
  2. Each record in the transaction is marked with PID + epoch.
  3. On commit, the broker writes a commit marker; on abort, an abort marker.
  4. Consumers with isolation.level=read_committed skip records from aborted transactions and don't see in-progress ones.

Consume-process-produce loop with EOS

The classic pattern: consume from topic A, transform, produce to topic B, commit consumer offset — all atomically.

while (true) {
    ConsumerRecords records = consumer.poll(...);
    producer.beginTransaction();
    for (ConsumerRecord r : records) {
        producer.send(transform(r));
    }
    producer.sendOffsetsToTransaction(consumer.endOffsets(...), consumer.groupMetadata());
    producer.commitTransaction();
}

Limitations

  • Only Kafka-to-Kafka. Doesn't extend to external sinks.
  • ~10–20% throughput cost vs non-transactional.
  • Transactions have a max duration (transaction.timeout.ms, default 60s).

  • Throughput: estimate target MB/sec. A single partition handles 10–25 MB/sec write reliably. Divide.
  • Consumers: you can't have more parallel consumers (in one group) than partitions.
  • Ordering: more partitions = less per-key contention but harder to maintain global order.
  • Don't go overboard: each partition has overhead (file handles, replication traffic, controller memory). Thousands per broker is fine; tens of thousands stresses the cluster.

Rule of thumb: start with 6–12 partitions for most topics. Easy to under-partition; hard to fix over-partitioning later.

import org.apache.kafka.clients.consumer.*;
import java.time.Duration;
import java.util.*;

public class SimpleConsumer {
    public static void main(String[] args) {
        Properties props = new Properties();
        props.put("bootstrap.servers", "localhost:9092");
        props.put("group.id", "order-processor");
        props.put("key.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
        props.put("value.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
        props.put("auto.offset.reset", "earliest");
        props.put("enable.auto.commit", "false");

        try (KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props)) {
            consumer.subscribe(Collections.singletonList("orders"));

            Runtime.getRuntime().addShutdownHook(new Thread(consumer::wakeup));

            try {
                while (true) {
                    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
                    for (ConsumerRecord<String, String> record : records) {
                        System.out.printf("p=%d off=%d k=%s v=%s%n",
                            record.partition(), record.offset(), record.key(), record.value());
                    }
                    consumer.commitAsync();
                }
            } catch (WakeupException e) {
                // graceful shutdown
            } finally {
                consumer.commitSync();
            }
        }
    }
}

Schema Registry & Avro

Plain JSON works fine until two teams disagree on a field rename. Then production breaks. The fix is a Schema Registry.

What it does

  • Stores schemas (Avro, Protobuf, or JSON Schema) versioned per topic.
  • Producer fetches/registers schema before publishing; the schema's ID is encoded in the first 5 bytes of every message.
  • Consumer reads the schema ID, fetches the matching schema, deserializes.
  • Enforces compatibility rules — rejects breaking schema changes at publish time.

Compatibility modes

ModeOld data + new codeNew data + old code
BACKWARD (default)✓✗
FORWARD✗✓
FULL✓✓
NONE——

Avro schema example

{
  "type": "record",
  "name": "Order",
  "namespace": "com.example",
  "fields": [
    { "name": "orderId", "type": "string" },
    { "name": "userId",  "type": "string" },
    { "name": "amount",  "type": "double" },
    { "name": "currency","type": "string", "default": "USD" }
  ]
}

Adding a field

Add fields with a default value to maintain BACKWARD compatibility — old records (without the field) deserialize using the default.

Avro vs Protobuf vs JSON Schema

  • Avro: compact binary, schema evolution by name. Best for streaming.
  • Protobuf: compact, very fast. Field-tag based; renames are non-breaking.
  • JSON Schema: human-readable, larger payloads.

Kafka Streams

Kafka Streams is a Java library (no separate cluster!) for building streaming applications that consume from Kafka, transform, and produce back to Kafka.

Why it's different from a regular consumer

  • High-level DSL: map, filter, groupBy, aggregate, join, windowedBy.
  • Stateful operations backed by RocksDB + a compacted Kafka topic (so state survives restarts).
  • Exactly-once processing guarantees (Kafka-to-Kafka).
  • Auto-scales by consumer group rebalance.

Tiny example

StreamsBuilder builder = new StreamsBuilder();

KStream<String, String> orders = builder.stream("orders");

KTable<String, Long> ordersPerUser = orders
    .groupByKey()
    .count(Materialized.as("orders-per-user"));

ordersPerUser.toStream().to("orders-count", Produced.with(Serdes.String(), Serdes.Long()));

KafkaStreams streams = new KafkaStreams(builder.build(), props);
streams.start();

Core abstractions

  • KStream — stream of records (each is a fact).
  • KTable — changelog stream interpreted as a table (latest value per key).
  • GlobalKTable — like KTable but each instance has the full table (for star-schema joins).

Windowing

Kafka Streams supports tumbling, hopping, sliding, and session windows for time-based aggregations.

  • num.network.threads ≈ number of cores.

Module 29
Operations

Rolling restart of brokers

  1. Take broker out of leadership: kafka-leader-election.sh --election-type preferred --all-topic-partitions.
  2. Stop broker; wait for ISR to stabilize (UnderReplicatedPartitions=0).
  3. Restart broker.
  4. Wait for ISR to fully catch up.
  5. Move on to next broker.

Adding a broker

  1. Start a new broker with a unique node.id pointing at the same controllers.
  2. It joins the cluster but holds no partitions.
  3. Use kafka-reassign-partitions.sh to generate a balanced reassignment plan.
  4. Execute the plan; verify completion.

Decommissioning a broker

  1. Generate a reassignment that moves all partitions off it.
  2. Execute and verify.
  3. Stop the broker.

Increasing partitions

kafka-topics.sh --bootstrap-server ... --alter --topic orders --partitions 12

Warning: this rebalances the key-to-partition mapping. Records previously sent for userId=42 stay where they are; new ones go where the new hash lands. Ordering per key is broken across the boundary.

Backing up

  • MirrorMaker 2 to a backup cluster (Module 30).
  • Snapshot log directories (with broker offline or use a tool like Kafka-Vault).
  • For compacted state, just replay from the source topic.

Disaster recovery checklist

  • Replication factor ≥ 3 across racks/AZs.
  • min.insync.replicas=2 for critical topics.
  • unclean.leader.election.enable=false.
  • Backup cluster via MirrorMaker.
  • Tested restore runbook.

Module 30
Multi-Cluster & MirrorMaker

Reasons to run multiple clusters:

  • Geo-distribution (low-latency reads in each region).
  • Disaster recovery (warm standby in another region).
  • Environment isolation (prod, staging, dev).
  • Tenant isolation (per-customer cluster).

MirrorMaker 2 (MM2)

Replicates topics from a source cluster to a target cluster. Built on Kafka Connect.

# mm2.properties
clusters = us, eu
us.bootstrap.servers = kafka-us:9092
eu.bootstrap.servers = kafka-eu:9092

us->eu.enabled = true
us->eu.topics = orders, payments
us->eu.groups = order-processor

# Active-active
eu->us.enabled = true
eu->us.topics = orders, payments

Topics on the target are renamed: orders from cluster us appears as us.orders on cluster eu. This prevents loops in active-active.

Patterns

  • Active-Passive: producers always go to primary; secondary is replication only. On failover, consumers + producers cut over to secondary.
  • Active-Active: producers in each region write locally; data is replicated both ways.
  • Hub & Spoke: regional clusters replicate to a central analytics cluster.

Module 31
Architectural Patterns

Event-Driven Microservices

Each service publishes events about what happened; other services react. No direct service-to-service calls. Loose coupling, easy to add new services.

Event Sourcing

Store the state of an entity as the sequence of events that changed it. Rebuild state by replaying events. Kafka's append-only log fits perfectly. Combine with compaction for snapshots.

CQRS (Command Query Responsibility Segregation)

Commands write to one model (e.g., events into Kafka); queries read from a denormalized read model populated by Kafka consumers. Decouples write and read scaling.

Transactional Outbox

How to atomically write to your DB and Kafka:

  1. In the same DB transaction, insert into your business tables AND into an outbox table.
  2. A separate process (Debezium CDC, or a poller) reads outbox and publishes to Kafka.
  3. If publish fails, retry — the row is still in outbox.

This avoids the dual-write problem (DB succeeds but Kafka fails, or vice versa).

Saga Pattern

Long-running multi-service workflows (e.g., place order → reserve inventory → charge card → ship). Each step publishes an event; the next service reacts. On failure, compensating events undo prior steps. Implement as choreography (each service knows the next step) or orchestration (a central coordinator drives the saga).

Stream Enrichment

Join an event stream with a reference table (KTable or GlobalKTable) to add context. Example: enrich an order event with the customer's tier from a customer table.

Dead Letter Queue (DLQ)

When a message can't be processed after N retries, push it to a separate topic (e.g., orders.dlq) and commit the original. Inspect the DLQ later via tools or scheduled jobs.

  • Need fanout, replay, high throughput, real ecosystem → Kafka.

  • Microsecond latency, in-memory only → Redis Streams.
  • Want tiered storage built-in → Pulsar.

Glossary

ACK (Acknowledgement)
The confirmation a broker sends back to the producer after writing a record. Configured by acks=0/1/all.
ACL (Access Control List)
Permissions binding a principal (user) to allowed operations (read, write) on a resource (topic, group).
Active Segment
The newest segment file being written for a partition. All older segments are read-only.
Avro
A compact, schema-driven binary serialization format. Common in Kafka with Schema Registry.
Batch
A group of records the producer sends together to one partition. Improves throughput.
Broker
A single Kafka server. Hosts partition replicas.
Cluster
A set of brokers working together with a shared cluster ID.
Compaction
A retention strategy keeping the latest record per key.
Consumer
A client reading records from one or more topics.
Consumer Group
A set of consumers that share a group.id and split topic partitions.
Controller
The broker (or KRaft node) responsible for cluster metadata and leader elections.
DLQ (Dead Letter Queue)
A separate topic for messages that consistently fail processing.
Group Coordinator
The broker hosting the offsets and metadata for a particular consumer group.
HWM (High Water Mark)
The largest offset visible to consumers — replicated to all ISR.
Idempotent Producer
Producer that uses sequence numbers to prevent duplicate writes from retries.
ISR (In-Sync Replicas)
The set of replicas (including leader) caught up to the leader.
KRaft
Kafka Raft mode — replaces Zookeeper for metadata. Default since 3.3.
Leader
The replica handling reads and writes for a partition. One per partition.
Log
The on-disk structure of a partition: a sequence of segment files.
Offset
Sequential position of a record within a partition.
Partition
An ordered, append-only subset of a topic. The unit of parallelism.
Producer
A client publishing records to topics.
Rebalance
Re-distribution of partitions among consumers in a group when membership changes.
Replica
A copy of a partition on a specific broker.
Replication Factor
The number of replicas (including leader) per partition.
Retention
How long Kafka keeps records before deleting them.
Segment
A single file holding part of a partition's log.
Schema Registry
A service that stores and versions schemas, used to ensure producer/consumer compatibility.
Tombstone
A record with null value, used to delete a key in a compacted topic.
Topic
A named stream of records.
Transactional Producer
A producer using transactions to atomically commit writes across multiple partitions.
Zero-Copy
Linux sendfile syscall used by Kafka to skip user-space buffers when serving fetches.
Zookeeper
Legacy metadata service for Kafka. Replaced by KRaft.

Module 36
Interview Questions

Q: What's the difference between a topic and a partition?
A topic is the logical name for a stream. A partition is a physical, ordered subdivision of that topic. A topic has 1+ partitions; ordering is per partition, not per topic.
Q: How does Kafka achieve high throughput on commodity disks?
Sequential I/O (append-only logs), batching at producer and broker, page cache for hot reads, zero-copy sendfile for fetch responses, and compression at the producer.
Q: What happens when a consumer joins or leaves a consumer group?
The group coordinator triggers a rebalance: the group leader recomputes assignments, and each member is told its new partitions. With cooperative rebalancing, only consumers losing partitions briefly pause; everyone else keeps consuming.
Q: Explain the difference between acks=1 and acks=all.
acks=1 waits for the leader replica to write; can lose data if the leader fails before replicating. acks=all waits for all in-sync replicas; safer but slower. With min.insync.replicas=2 and RF=3, acks=all tolerates one replica failure.
Q: What is the ISR and why does it matter?
The In-Sync Replica set is the subset of replicas caught up to the leader. Only ISR members can be elected leader. A producer with acks=all waits for all ISR members. The ISR shrinks if a follower lags > replica.lag.time.max.ms, and grows when it catches up.
Q: How does Kafka guarantee ordering?
Per partition. Records with the same key always land in the same partition (assuming partition count doesn't change), so they're consumed in order. Across partitions, no global ordering.
Q: What is exactly-once semantics in Kafka?
The combination of idempotent producer + transactional producer + read_committed consumer. It guarantees Kafka-to-Kafka pipelines see each record exactly once, even with retries and failures. End-to-end EOS to non-Kafka systems requires additional patterns (transactional outbox).
Q: Why can you increase but not decrease partitions?
Partitioning is hash-based: hash(key) % N. If you decreased N, the mapping would change for nearly every key, breaking ordering and consumer offset tracking. Increasing also breaks per-key ordering across the change but is supported.
Q: How is consumer offset stored?
In an internal compacted topic __consumer_offsets, keyed by (group, topic, partition). The group coordinator broker manages it.
Q: What is log compaction and when is it useful?
A retention policy that keeps at least the latest record per key, removing older versions. Useful for materialized state (user profiles, account balances), Kafka Streams state stores, and configuration broadcasts.
Q: Difference between Kafka and a traditional queue (RabbitMQ)?
Kafka: durable log, multiple independent consumers (groups), replay supported, partitioned for parallelism, high throughput. RabbitMQ: queue model (delete on consume), rich routing (exchanges, headers), per-message TTL, lower throughput. Different tools for different needs.
Q: How would you handle a poison message that always fails?
Implement a retry counter (in headers or external store). After N retries, push to a Dead Letter Queue topic and commit the original offset to unblock the partition. Have a separate process (or human) inspect the DLQ.
Q: What happens if all replicas of a partition go offline?
The partition becomes unavailable. With unclean.leader.election.enable=false, Kafka waits for an in-sync replica to come back. With it enabled, it elects an out-of-sync replica — restoring availability but losing data.
Q: Why is Kafka pull-based instead of push-based?
Pull lets each consumer control its own pace. A slow consumer doesn't get overwhelmed; a fast one isn't throttled by the broker; and consumers can replay easily. Push systems require complex backpressure protocols.
Q: What does min.insync.replicas do?
Sets the minimum number of in-sync replicas required for a write to succeed when acks=all. If fewer than this many ISRs exist, the producer gets a NotEnoughReplicasException. Trades availability for durability.
Q: Can you have more consumers than partitions in a group?
Yes, but the extras sit idle — each partition is owned by exactly one consumer in the group. So partition count is your maximum useful parallelism per group.
Q: What's the controller's job?
One broker (or KRaft node) is the controller. It detects broker failures, drives leader elections, and is the authority for cluster metadata changes (topic create/delete, partition reassignment).
Q: How does Schema Registry prevent breakage?
Producers register schemas before publishing. The registry checks compatibility (BACKWARD/FORWARD/FULL/NONE) against existing versions and rejects changes that violate the policy. The schema ID is embedded in each message so consumers can fetch the right schema.
Q: How would you back up a Kafka cluster?
Best: replicate to a secondary cluster with MirrorMaker 2 (continuously). Worst case: snapshot log directories with brokers offline. For state that's downstream of a topic, you can usually rebuild by replaying.
Q: How do you handle a hot partition?
(1) Use a higher-cardinality key. (2) Add a synthetic suffix to the key to spread it. (3) Increase partition count and reassign. (4) If ordering matters within "user", and the user is the hot one, you may need to rearchitect.

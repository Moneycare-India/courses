Module 1
QA vs QC

The two terms — often confused

Prevents defectsIdentifies defects

ProactiveReactive
Examples: code reviews, standards, training, auditsExamples: testing, inspections, walkthroughs of finished work

The simplest framing

  • QA = the system you set up so quality happens (review processes, CI/CD, definition-of-done, coding standards).
  • QC = the actual checks you do to verify it happened (running tests, finding bugs, signing off).

The blurry line

In practice, "QA Engineer" usually does both: designs test approaches (QA), executes tests (QC), files bugs, automates regression. Modern teams don't draw a hard line. The phrase "quality is a team responsibility" is the modern stance.

Testing — the most visible part

Testing is one part of QC, which is part of QA. But colloquially, "QA team" usually means "the people who test." This course uses the practical meaning: everything related to making sure software works correctly.

Common misconceptions

  • "QA finds all bugs" — impossible. QA reduces risk; can't eliminate it.
  • "Developers shouldn't test" — wrong. Devs catch most bugs at the unit level.
  • "100% test coverage = bug-free" — coverage measures execution, not correctness.
  • "QA is a phase at the end" — the most expensive bugs are caught earliest. Shift-left (Module 70).
  • "Manual testing is dying" — exploratory and usability testing are still human work.

The cost of finding bugs late

StageRelative cost to fix
Requirements / design1×
Coding5×
Testing (QA phase)10×
UAT / staging50×
Production100×+ (plus reputation, legal, customer trust)

This is why QA shifts left — bugs found by the developer at coding cost orders of magnitude less than bugs found by a customer.

Module 2
Software Quality & Models

What does "quality" mean?

Multiple valid definitions:

  • Conformance to requirements — the system does what's specified.
  • Fitness for purpose — the system solves the user's problem.
  • Absence of defects — the system doesn't fail in unexpected ways.
  • Customer satisfaction — users enjoy using it.

Real quality is all of these. A system that meets every spec but is unusable isn't quality software.

ISO 25010 — the standard quality model

Eight categories of "quality characteristics" you can measure:

CharacteristicWhat it covers
Functional SuitabilityDoes it do what's required? Completeness, correctness, appropriateness
Performance EfficiencyTime behavior, resource use, capacity
CompatibilityCo-existence, interoperability with other systems
UsabilityLearnability, operability, accessibility, error protection
ReliabilityMaturity, availability, fault tolerance, recoverability
SecurityConfidentiality, integrity, authenticity, accountability
MaintainabilityModularity, reusability, modifiability, testability
PortabilityAdaptability, installability, replaceability

You'll see these mapped to non-functional requirements (System Design Module 4–5) and test types throughout this course.

ISTQB — the testing certification

ISTQB (International Software Testing Qualifications Board) is the most widespread testing certification framework. Tiers:

  • Foundation Level — entry, broad overview.
  • Advanced Level — Test Manager, Test Analyst, Technical Test Analyst.
  • Expert Level — specialist roles.
  • Specialist — Mobile, Performance, Security, Test Automation Engineer, Agile Tester.

Useful for vocabulary and getting hired. Some companies require it. Skills matter more than the certificate, but the certificate opens doors.

CMMI — process maturity

Capability Maturity Model Integration. Five levels of organizational process maturity:

  1. Initial — chaotic, ad hoc.
  2. Managed — basic project management.
  3. Defined — processes documented and standardized.
  4. Quantitatively Managed — process performance measured.
  5. Optimizing — continuous improvement.

Mostly relevant in enterprise / government context. Smaller modern teams often skip the formal CMMI path and adopt practices instead.

Module 3
Why Testing Matters

The famous failures

Software bugs have:

  • Crashed Mars probes (NASA Mariner 1, 1962 — typo cost $80M).
  • Killed people (Therac-25 radiation overdoses; Boeing 737 MAX MCAS).
  • Cost billions (Knight Capital lost $440M in 45 minutes from a deployment bug).
  • Brought down whole markets (2010 Flash Crash).
  • Leaked everyone's data (countless breaches enabled by missing input validation).

Testing isn't a "nice to have." For systems that matter, untested = irresponsible.

What testing actually buys you

  • Confidence to ship — you can change code without fearing what breaks.
  • Faster development long-term — fixing later costs more (Module 1).
  • Living documentation — tests show how the code is meant to be used.
  • Refactor safety net — you can clean up code without fearing regressions.
  • Onboarding aid — new devs see expected behavior in tests.
  • Compliance — regulated industries demand testing evidence.

Testing is risk management

You'll never test everything. The goal isn't 100% perfection — it's reducing risk to an acceptable level. Critical paths get heavy testing; rarely-used edge cases get less. Decisions made deliberately, not by accident.

What testing CANNOT do

  • Prove software is bug-free. Only that some bugs aren't there.
  • Replace good design and clean code.
  • Compensate for unclear requirements.
  • Find bugs in code that wasn't written yet.
  • Substitute for production observability.

The bug discovery curve

Diminishing returns: the first 80% of testing finds 80% of bugs cheaply. The next 19% takes much more work. The last 1% costs more than the rest combined. Smart QA stops when remaining risk is acceptable, not when bugs hit zero.

Module 4
The 7 Testing Principles

From the ISTQB foundation syllabus — these aren't just for the exam. Each captures something real about testing.

1. Testing shows the presence of defects, not their absence

You can find bugs by testing. You can never prove there are none. "Tests passed" means "no bugs found by these tests" — not "no bugs."

2. Exhaustive testing is impossible

For non-trivial software, the input space is effectively infinite. You can't test every combination. Test design (Modules 23–29) is about picking the right small subset.

3. Early testing saves time and money

Module 1's cost table. The Shift-Left principle (Module 70).

4. Defects cluster together

Bugs aren't evenly distributed — they cluster in complex modules, recently-changed code, low-quality components, and around technical debt. Risk-based testing (Module 29) prioritizes these.

5. The pesticide paradox

If you run the same tests over and over, they stop finding new bugs. Tests need to evolve — review, update, add. Otherwise you're testing only what worked yesterday.

6. Testing is context-dependent

You don't test a banking app the same way you test a cat-photo app. Risks, regulations, expected behavior, user expectations — all vary by context. Same tests would be too much for one and too little for the other.

7. Absence-of-errors fallacy

A system can pass every test and still be wrong — because it solves the wrong problem. Software that doesn't meet user needs has zero value, however technically defect-free. Validation matters as much as verification.

Verification vs Validation

VerificationValidation
"Are we building it right?""Are we building the right thing?"
Code matches the specThe system solves the user's problem
Reviews, unit tests, integration testsUAT, user research, A/B testing

You need both. Software that passes verification but fails validation is technically correct and practically useless.

Module 6
SDLC & STLC

SDLC — Software Development Life Cycle

The end-to-end process of creating software:

  1. Requirements — gather what's needed.
  2. Design — architect the solution.
  3. Implementation — write the code.
  4. Testing — verify it works (this is where QA traditionally lives).
  5. Deployment — release.
  6. Maintenance — fix, support, evolve.

SDLC models

ModelStyleBest for
WaterfallSequential phases; each completes before the nextStable requirements; regulated industries
V-ModelWaterfall + matched test phase per dev phaseCritical systems; medical / aerospace
IterativeBuild a chunk, refine, repeatEvolving requirements
Agile / ScrumSprints; continuous delivery; cross-functional teamsMost modern software
DevOpsContinuous integration + delivery + deploymentWeb-scale services
SpiralRisk-driven iterationsLarge, complex, high-risk

STLC — Software Testing Life Cycle

The QA mirror of SDLC. Six phases:

  1. Requirements analysis — read specs, identify what's testable, clarify ambiguity.
  2. Test planning — scope, schedule, resources, deliverables, risks.
  3. Test case design — write test cases using design techniques (Modules 23–29).
  4. Test environment setup — get DBs, accounts, fixtures, devices ready.
  5. Test execution — run tests, log results, file bugs.
  6. Test closure — report, retrospective, archive.

The V-Model — testing parallels development

    Requirements ──────────────► Acceptance Testing
        │                                ▲
        ▼                                │
     Design  ─────────────────► System Testing
        │                                ▲
        ▼                                │
    Architecture ─────────► Integration Testing
        │                                ▲
        ▼                                │
    Coding ─────────────► Unit Testing
        │                                ▲
        └────────────────────────────────┘

Each dev artifact has a corresponding test artifact. Useful conceptual model even if you're not strictly waterfall — every requirement should have a UAT, every architectural decision should be tested at integration level.

Entry & exit criteria

Each STLC phase has:

  • Entry criteria — what must be true before the phase starts (e.g., "code complete," "test environment ready").
  • Exit criteria — what must be true to leave (e.g., "100% test cases executed," "no critical defects open," "> 90% pass rate").

Defining these explicitly avoids the "are we done?" debate.

Regular meeting (daily for fast-paced teams, weekly for slower) where new bugs get reviewed:

Module 8
Unit Testing

What it is

Testing one small piece of code (typically a class or function) in isolation. The smallest, fastest, most numerous tests in your suite.

Properties of good unit tests

  • Fast — milliseconds. You run them constantly.
  • Isolated — no DB, no network, no file system. Use mocks/stubs.
  • Repeatable — same result every time, regardless of environment.
  • Self-validating — passes or fails clearly; no human inspection.
  • Timely — written close to (or before) production code.

Together: FIRST — Fast, Isolated, Repeatable, Self-validating, Timely.

Who writes them

Developers, almost always. QA may review or pair on tricky cases. SDETs may write them for shared utilities.

Example: C# / xUnit

public class CalculatorTests
{
    [Fact]
    public void Add_TwoPositives_ReturnsSum()
    {
        var c = new Calculator();
        var result = c.Add(2, 3);
        Assert.Equal(5, result);
    }

    [Theory]
    [InlineData(0, 0, 0)]
    [InlineData(-5, 5, 0)]
    [InlineData(int.MaxValue, 0, int.MaxValue)]
    public void Add_VariousInputs(int a, int b, int expected)
    {
        Assert.Equal(expected, new Calculator().Add(a, b));
    }
}

The Arrange-Act-Assert pattern

[Fact]
public void Withdraw_InsufficientFunds_ReturnsError()
{
    // Arrange
    var account = new BankAccount(balance: 100);

    // Act
    var result = account.Withdraw(150);

    // Assert
    Assert.False(result.Success);
    Assert.Equal("Insufficient funds", result.Error);
    Assert.Equal(100, account.Balance);    // unchanged
}

Mocking external dependencies

[Fact]
public async Task GetUser_NotFound_ReturnsNull()
{
    // Arrange
    var repo = new Mock<IUserRepository>();
    repo.Setup(r => r.FindAsync(42)).ReturnsAsync((User?)null);

    var sut = new UserService(repo.Object);

    // Act
    var user = await sut.GetUserAsync(42);

    // Assert
    Assert.Null(user);
    repo.Verify(r => r.FindAsync(42), Times.Once);
}

Coverage — useful but limited

Code coverage measures which lines/branches your tests execute. 80% is a common target.

  • High coverage doesn't mean high quality — you can execute every line and assert nothing.
  • Low coverage almost always means missing tests.
  • Aim for high-value coverage: business logic, edge cases, error paths.
  • Don't chase 100% — last 5% costs more than it returns.

Module 9
Integration Testing

What it tests

How multiple components work together. Either:

  • Inside one process — e.g., service + real DB; controller + service + repository.
  • Across services — e.g., API A calls API B; producer to Kafka to consumer.

Why integration tests catch what unit tests miss

  • Wiring bugs — DI registrations wrong.
  • Configuration mismatches — connection strings, env vars.
  • Real-world quirks of databases — case sensitivity, collation, transactions.
  • Serialization issues — JSON shapes, datetime formats.
  • Behavior differences between mocks and reality.

The strategy

         ┌─────────┐
         │   E2E   │  few — slow, full stack
         └─────────┘
       ┌─────────────┐
       │ Integration │  some — components together, often with real DB
       └─────────────┘
     ┌──────────────────┐
     │   Unit tests     │  many — fast, isolated
     └──────────────────┘

API integration tests in .NET

// dotnet add package Microsoft.AspNetCore.Mvc.Testing

public class UsersApiTests : IClassFixture<WebApplicationFactory<Program>>
{
    private readonly HttpClient _client;

    public UsersApiTests(WebApplicationFactory<Program> factory)
    {
        _client = factory.WithWebHostBuilder(b =>
        {
            b.ConfigureServices(s =>
            {
                s.RemoveAll<DbContextOptions<AppDbContext>>();
                s.AddDbContext<AppDbContext>(opt =>
                    opt.UseInMemoryDatabase("test"));
            });
        }).CreateClient();
    }

    [Fact]
    public async Task GetUser_Existing_Returns200()
    {
        var resp = await _client.GetAsync("/api/users/42");
        resp.StatusCode.Should().Be(HttpStatusCode.OK);
    }
}

Real DB with Testcontainers

InMemory DB doesn't behave like real SQL Server. Testcontainers spins up a real DB in a Docker container per test run:

// dotnet add package Testcontainers.MsSql

public class DbFixture : IAsyncLifetime
{
    private readonly MsSqlContainer _container = new MsSqlBuilder()
        .WithPassword("Test_pass_123!")
        .Build();

    public string ConnectionString => _container.GetConnectionString();

    public async Task InitializeAsync() => await _container.StartAsync();
    public Task DisposeAsync() => _container.DisposeAsync().AsTask();
}

What to integration-test

  • API endpoints end-to-end (auth, validation, response shape).
  • EF Core queries against a real DB.
  • Pipeline behavior — middleware ordering, auth flow.
  • Critical business workflows.

What NOT to over-do

  • Don't write integration tests for trivial CRUD — covered at the unit level.
  • Don't replicate every unit test at the integration level.
  • Be strategic — slow tests cost CI time and engineer attention.

Module 10
System Testing

What it is

Testing the complete system as a whole, in an environment that resembles production. Black-box: you don't peek inside; you exercise it like a user would.

What system testing covers

  • End-to-end functional flows (login → use feature → log out).
  • Cross-module interactions.
  • Configuration in target-like environment.
  • Performance, security, and other NFRs (often as separate sub-types).
  • Compatibility (browsers, devices).

vs Integration vs E2E

LevelScopeEnvironment
UnitOne class/functionIn-process, mocks
IntegrationFew componentsMixed: real DB sometimes
SystemWhole applicationProduction-like
End-to-end (E2E)Complete user journey through the UIProduction-like

System and E2E overlap heavily. The difference is mostly perspective: system testing emphasizes "the whole product works"; E2E emphasizes "user journeys complete successfully."

Typical system test scope

  • Functional — every documented feature.
  • Security — auth flows, authorization edges, injection tests.
  • Performance — load patterns expected in production.
  • Recovery — what happens when DB is down? Network blips?
  • Compatibility — browser matrix, mobile devices.
  • Localization — every supported language.
  • Documentation — verify docs match actual behavior.

System test environment

Should mirror production as closely as possible:

  • Same OS, runtime versions.
  • Same DB engine and version.
  • Realistic data volume.
  • Real (or sandbox) integrations to external systems.
  • Same auth flow.

Not always feasible. The closer the better. Discrepancies = production surprises.

Module 11
Acceptance Testing

UAT — User Acceptance Testing

The system goes through testing by actual users (or stakeholder reps) who decide whether to accept it. This is the final gate before release.

UAT focus

  • "Does this solve my actual problem?" — validation, not verification.
  • Real workflows on realistic data.
  • Checking against the original business requirements.

Who runs UAT

  • Business analysts.
  • Product owners.
  • Customer representatives / actual users (in B2B).
  • Domain experts.

QA engineers usually facilitate but don't drive UAT.

Alpha testing

Internal testing — your own employees use the product before public release. Catches usability issues, workflow problems, edge cases the dev team didn't think of.

Beta testing

External users — invited customers, public beta — try the product and report issues. The "real-world conditions" filter:

  • Devices and browsers you didn't test on.
  • Network conditions (slow connections, intermittent).
  • Workflows you didn't anticipate.
  • Real usage patterns (volume, timing).

Beta testing tools

  • TestFlight (iOS), Google Play Internal Testing (Android).
  • Microsoft App Center — distributing pre-release builds.
  • Feature flags (LaunchDarkly, Unleash) — selectively enable for beta users in production.
  • Telemetry — collect usage data + error reports automatically.

Operational Acceptance Testing (OAT)

Ops perspective. Verifies operational readiness:

  • Monitoring & alerts work.
  • Backups work and restores succeed.
  • Logs are searchable.
  • Failover / DR drills succeed.
  • Documentation for runbooks exists.
  • Capacity headroom is sufficient.

Contract Acceptance Testing

For software developed under contract: testing against the contractual spec. Common in enterprise / government work.

Module 12
Regression Testing

The problem

You fixed bug X. Did you accidentally break working feature Y? Regression testing verifies existing functionality still works after changes.

The pesticide paradox revisited

Static regression tests catch only what they were written for. Periodically refresh:

  • Add tests for recently-found production bugs (so they never come back).
  • Update tests as features evolve.
  • Remove tests for removed features.
  • Cull duplicates.

Selecting what to regression-test

Running ALL tests after every change is ideal but often impractical for big systems. Selection strategies:

StrategyWhat
Retest AllRun every test. Safe, slow.
Regression Test SelectionRun tests covering changed code. Faster; needs traceability.
Test Case PrioritizationRun highest-risk / highest-failure-rate tests first.
Smart selection / impact analysisTools (NCrunch, Continuous Testing) detect which tests touch changed code.

Sanity vs Smoke vs Regression

TypePurposeScope
Smoke"Did the build deploy without obvious breakage?"Very narrow — login, home page loads, etc.
Sanity"Does the bug fix / new feature work?"Narrow — affected area only
Regression"Did anything else break?"Broad — all major flows

Automation is essential

Manual regression doesn't scale. Every release adds tests. Without automation, regression becomes the bottleneck and gets skipped — which is when production bugs slip in.

Cadence

  • Per commit — unit tests, fast integration.
  • Per PR — broader regression suite.
  • Per build — smoke tests on every artifact.
  • Pre-release — full regression suite + manual exploratory.
  • Nightly — long-running tests (load, full E2E matrix).

Module 13
Functional vs Non-Functional

Functional testing

Does the system do what it's supposed to? Verifying features against requirements.

  • Login with correct credentials → success.
  • Submit invalid email → validation error.
  • Order placement deducts inventory.
  • Calculation matches expected formula.

Most testing falls into functional. Black-box: you give input, check output, don't peek inside.

Non-functional testing

How well does it do what it does? The "ilities" — quality attributes from ISO 25010 (Module 2).

TypeWhat it checks
PerformanceSpeed, throughput
LoadBehavior under expected user load
StressBehavior beyond capacity
ScalabilityAdding resources scales linearly?
ReliabilityFailures recovered gracefully?
SecurityAttacks blocked?
UsabilityEasy to use?
AccessibilityUsable by disabled users?
CompatibilityWorks on target browsers/devices?
MaintainabilityCode is changeable?
PortabilityMoves between environments?
LocalizationAdapts to languages/regions?

The split in practice

Most teams over-invest in functional testing and under-invest in non-functional. Functional bugs are visible; non-functional bugs ("slow," "fails under load," "inaccessible") often only show up in production.

Modern QA strategies treat NFRs as first-class — automated performance smoke tests, accessibility audits in CI, security scans on every PR.

Module 14
Smoke, Sanity, Exploratory

Smoke testing

"Does it turn on?" Quick sanity check that the build is testable at all. If smoke fails, no point running deep tests.

Typical smoke checks:

  • App starts.
  • Health endpoint returns 200.
  • Login works.
  • Home page loads.
  • Critical API responds.

Runs in seconds-to-minutes. Should be automated. Acts as an entry criterion for deeper testing.

Sanity testing

Narrow check that a specific change works. After bug fix or small feature: verify the change does what it claims.

  • Bug X fixed → reproduce-the-bug test now passes.
  • Validation rule changed → new rule applies.
  • UI tweak → looks right.

Scope: just the affected area, not the whole product.

Exploratory testing

Unscripted, learning-based testing. Tester explores the product, designing tests as they go.

It's not "random clicking" — there's structure. Session-based exploratory testing:

  1. Define a charter — "explore the search feature, focus on edge cases for query length."
  2. Time-box the session — typically 60–120 minutes.
  3. Take notes as you go.
  4. Debrief at the end — what was tested, what bugs found, what to follow up.

When exploratory shines

  • New features without complete specs.
  • Catching what scripted tests miss.
  • Usability assessment.
  • Quick coverage of low-risk areas.
  • Investigation after a defect is found.

Charters — the structuring tool

Explore: the user search feature
With: queries longer than the input field (50+ chars), special chars,
      empty input, multi-word, RTL languages, paste-bombing
To discover: validation gaps, performance issues, escape bugs,
             unexpected results

Time: 90 min

Ad-hoc testing

Unstructured exploratory — no charter, no notes. Has its place (quick "let me try this") but doesn't scale and doesn't produce a reusable record.

Module 18
Usability & UX Testing

The question usability testing answers

"Can a real person use this without training, frustration, or errors?"

Heuristic evaluation — Nielsen's 10

Apply each to your screens; flag violations:

  1. Visibility of system status — does the user know what's happening?
  2. Match between system and real world — uses the user's vocabulary, not internal jargon.
  3. User control and freedom — can undo / cancel mistakes.
  4. Consistency and standards — same terms / patterns throughout.
  5. Error prevention — design out the most common mistakes.
  6. Recognition rather than recall — show options, don't make them remember.
  7. Flexibility and efficiency — shortcuts for power users.
  8. Aesthetic and minimalist design — only relevant info, no clutter.
  9. Help users recognize, diagnose, recover from errors — clear messages, fixes suggested.
  10. Help and documentation — easy to find.

Methods

Moderated user testing

5 users complete tasks while you observe. Most insight per dollar — Nielsen's research shows 5 users find 80% of usability issues. Sessions of 30–60 min.

Unmoderated remote testing

Tools like UserTesting, Maze, Lookback. Users complete tasks at home; you watch the recordings. Faster, cheaper, less interactive.

A/B testing

Two variants live in production; compare metrics (conversions, errors, time-on-task). Quantitative.

Cognitive walkthrough

Walk through every step of a key task as if you were a new user. At each step ask: would I know what to do here? Would I succeed?

Metrics

  • Task success rate — % completing without help.
  • Time on task — seconds.
  • Error rate — wrong clicks / dead ends.
  • SUS (System Usability Scale) — standardized 10-question survey, 0–100 score.
  • NPS — would you recommend this?
  • SEQ (Single Ease Question) — "how easy was that task?"

Module 21
Localization & Internationalization (i18n)

Two related concepts

  • Internationalization (i18n) — designing the system so it CAN be adapted to different languages/regions. Foundation work.
  • Localization (l10n) — actually adapting content for a specific locale. Translation, date formats, currency, etc.

What to test

Translation completeness

  • Every screen translated — no English fallthroughs in non-English locales.
  • No hard-coded strings.
  • Pluralization rules correct (Russian has different forms for 1 / 2-4 / 5+).
  • Gender-aware translations where applicable.

Layout under translation

  • German strings can be 30% longer than English — does layout break?
  • Asian characters (CJK) are wider per glyph — alignment changes.
  • RTL languages (Arabic, Hebrew) — entire layout mirrors. Icons, scrollbars, navigation flip.

Date / time / number / currency

  • "5/3/2026" — May 3 or March 5? Depends on locale.
  • Decimal separator — 1,234.56 (US) vs 1.234,56 (DE) vs 1 234,56 (FR).
  • Currency placement and symbol.
  • Time zones.

Sorting

Locale-aware sort orders — Spanish "ñ" comes after "n", not after "n" in unicode order.

Character encoding

UTF-8 throughout. Forms accept Unicode input. DB stores Unicode (NVARCHAR, not VARCHAR).

Pseudo-localization

Replace strings with elongated, accented versions for testing without translators:

"Save" → "[Šåvé!! ## ##]"
"Settings" → "[Šéttîngś!!]"

Catches: missing translations, layout overflow, character encoding bugs. Run early; you don't need translators.

Tools

  • i18next, react-i18next — JS i18n libraries.
  • Crowdin, Lokalise, Phrase, Transifex — translation management platforms.
  • Pseudo-localization — most i18n libs have this built in.

Recovery & Failover Testing

What it covers

Verify the system handles failures gracefully. Inspired by the chaos engineering discipline (see System Design course Module 55).

Scenarios to test

FailureExpected behavior
DB primary failsAuto-failover to replica; brief disruption ≤ N seconds

Module 23
Black / White / Gray Box

The three testing perspectives

ApproachTester seesTests focus on
Black boxInputs & outputs onlyBehavior — does the function do what it says?
White box (clear/glass box)Source code, structureCode paths, branches, internal state
Gray boxSome internal knowledgeAPI + DB state; interface + structure

Black box techniques

The test designer treats the system as an opaque function: given input X, expect output Y. No code visibility.

  • Equivalence partitioning (Module 24).
  • Boundary value analysis (Module 25).
  • Decision tables (Module 26).
  • State transition (Module 27).
  • Use case testing (Module 28).

Black-box testing typically aligns with QA roles, integration tests, system tests.

White box techniques

Tester reads the code and designs tests to exercise specific paths.

  • Statement coverage — every line executes.
  • Branch coverage — every if-true and if-false path.
  • Path coverage — every possible path through the code (combinatorially explosive).
  • Condition coverage — every boolean sub-expression evaluates to true and false.

White-box testing typically aligns with developer-written unit tests.

Gray box

The tester knows enough about internals to craft better black-box tests:

  • Knowing the schema, design SQL injection probes.
  • Knowing the API's caching layer, design cache-busting tests.
  • Knowing data flows, hit specific edge cases.

Most modern API/system testing is effectively gray box — testers have access to docs, schemas, sometimes code.

Which to use when

  • Unit tests → mostly white box (developer knows the code).
  • Integration tests → gray box (knows interfaces, not internals).
  • System tests → black box (user perspective).
  • E2E / UAT → black box.

Module 24
Equivalence Partitioning

The idea

Divide inputs into groups where the system should behave the same way, then test ONE representative from each group. If it works for one, it should work for all in that group.

Example

Input: integer age, valid 0–120.

PartitionRangeRepresentative test valueExpected
Below valid< 0-5Error
Valid range0–12030Accepted
Above valid> 120200Error
Non-numeric—"abc"Error
Empty—""Error
Whitespace—" "Error

Six tests instead of testing every age 0..120 individually.

Multiple inputs

For combined inputs, test combinations of partitions. Don't blow up combinatorially — pair-wise testing helps:

  • All combinations — N×M×K tests; explodes fast.
  • Pair-wise — every pair of values appears at least once. ~N² tests covers most defects (research shows most bugs come from interactions of 2 variables).

Tools

  • PICT (Microsoft) — generates pair-wise test cases.
  • ACTS — NIST tool for combinatorial coverage.
  • AllPairs — Python lib.

Practical use

For any input field, ask: "what equivalence classes apply here?" Don't write 50 tests for the same input; write a representative for each class. Saves time, catches the same bugs.

Module 25
Boundary Value Analysis

The idea

Bugs cluster at boundaries. < vs <=, off-by-ones, edges of arrays, min/max values. Test the boundaries explicitly.

For a range 1–100, test these values

ValueWhy
0One less than minimum
1Minimum
2One more than minimum
50Middle (or any in-range value)
99One less than maximum
100Maximum
101One more than maximum

3-value or 7-value boundary analysis. The 7-value version catches more.

Where boundaries matter

  • Numeric ranges (age 0–150).
  • String lengths (max 280 chars).
  • Array indices (0 vs length-1; empty vs single-item).
  • Date ranges (start vs end of month, year, leap day Feb 29).
  • Pagination (page 0, 1, last, last+1).
  • Permission boundaries (admin vs non-admin, just-above vs just-below threshold).
  • Money (zero, negative, max int, decimal precision edges).

Famous boundary bugs

  • Y2K — 4-digit years; nothing accounted for 1999 → 2000 transition.
  • Year 2038 — 32-bit Unix timestamp overflows on 19 January 2038.
  • Patriot missile (1991) — accumulated time error after 100 hours of running. 28 lives.
  • 32-bit overflow in YouTube view counter — Gangnam Style broke it (over 2.1B views).

Combine with equivalence partitioning

EP gives you the partitions; BVA picks the test values within and at the edges. Together they're the most efficient black-box test design.

Module 26
Decision Tables

When to use

For features with multiple inputs whose combinations affect output. Examples: pricing rules, discount eligibility, role-based access, tax calculations.

Building a decision table

Example: shipping cost calculation.

  • Input: customer type (Regular / Premium), order amount (≥$100 or <$100), country (Domestic / International).
  • Output: shipping cost.
Rule Premium? Order ≥ $100? Domestic? Shipping
R1YYYFree
R2YYNFree
R3YNYFree
R4YNN$5
R5NYYFree
R6NYN$10
R7NNY$5
R8NNN$15

Each row is a test case. 3 binary inputs → 2³ = 8 combinations. All covered.

Why this is powerful

  • Forces you to think through every combination.
  • Surfaces ambiguities in requirements ("what about Premium with order ≥ $100 AND international?").
  • Translates directly to test cases.
  • Useful for stakeholder review — shows logic in a table they can verify.

Reducing decision tables

Sometimes outputs don't depend on certain inputs. "Don't care" entries collapse rules. Above example: when Premium = Y and Order ≥ $100, shipping is free regardless of country. Two rules merge into one.

Cause-effect graphs

Visual cousin of decision tables — draw causes (inputs) and effects (outputs) as a graph; trace which combinations produce which effects. Less common today but conceptually useful.

Module 27
State Transition Testing

When to use

Features where the entity's allowed actions depend on its current state. Examples: order workflow, document approval, user account states, video player.

Modeling — state transition diagram

    [Created] ──pay──► [Paid] ──ship──► [Shipped] ──deliver──► [Delivered]
        │                  │                                          │
        │                  │                                          ▼
        ▼                  ▼                                       [Closed]
   [Cancelled]        [Refunded]

What to test

  1. Each state — does the system look right in each one?
  2. Each valid transition — Created → Paid succeeds.
  3. Each invalid transition — Created → Shipped should be rejected.
  4. Edge cases — terminal states; double-fire of an event.

State table — easier than diagram for complex flows

From state Event To state Action
CreatedpayPaidCharge card; record payment
CreatedcancelCancelled—
Createdship(error)"Cannot ship unpaid order"
PaidshipShippedReduce inventory; create shipment
PaidrefundRefundedRefund payment
ShippeddeliverDelivered—
Deliveredrefund(error)"Use returns flow"

The trick: test invalid transitions too

Most teams test the happy path and forget the bad path. Half the bugs are "what if I try to do X from state Y?" Invalid transitions should be rejected with a clear error, not crash or silently succeed.

0-switch, 1-switch, N-switch coverage

  • 0-switch — every single transition tested.
  • 1-switch — every pair of consecutive transitions.
  • N-switch — every sequence of N+1 transitions.

0-switch is usually sufficient. 1-switch catches state-dependent bugs that depend on history.

Module 28
Use Case / Scenario Testing

What it is

Test cases derived from end-to-end user journeys, not from individual features. Connects QA to actual user behavior.

Use case structure

Use case: Place an order

Actors: Customer, Payment system, Inventory system
Preconditions: Customer logged in; cart has ≥ 1 item

Main success scenario:
  1. Customer clicks "Checkout"
  2. System shows order summary
  3. Customer selects payment method
  4. Customer confirms
  5. System charges payment
  6. System decrements inventory
  7. System sends confirmation email
  8. System shows order confirmation page

Alternative flows:
  3a. Customer adds new payment method
  4a. Customer cancels at confirmation
  5a. Payment fails → show error, allow retry
  6a. Inventory insufficient → release reservation, refund

Postconditions:
  - Order recorded with status = Paid
  - Inventory updated
  - Confirmation email sent

Deriving test cases

  • One test per main success path.
  • One test per alternative flow.
  • One test per error condition (5a, 6a, etc.).
  • One test where preconditions aren't met.

Why scenarios beat feature-by-feature testing

  • Catches integration bugs across features.
  • Reflects real user value — not "all checkboxes work" but "users can buy."
  • Stakeholders understand them.
  • Naturally extend to E2E automation.
  • Useful for UAT — "go through this flow and tell me if it works."

User stories & acceptance criteria

The Agile equivalent. Format:

As a customer
I want to place an order
So that I can buy products

Acceptance criteria:
- I can add items to a cart
- I can review cart contents before paying
- Payment options I've saved are available
- I receive a confirmation email within 1 minute
- I can view the order in "My Orders"

Each acceptance criterion → one or more tests. The "definition of done" for the story.

  • High-risk: detailed test cases, automation, multi-browser, performance, security.

For regression: prioritize tests for areas that

  1. Were touched in this release.
  2. Have high impact if broken.
  3. Have past defect history.

Good test case characteristics

  • Atomic — one purpose. Don't combine "test login" with "test profile edit."
  • Independent — runs in any order. No assumptions about previous test state.
  • Clear steps — anyone can run it without context.
  • Specific expected result — not "it works"; describe what "works" means.
  • Reproducible — same steps → same result.
  • Maintainable — easy to update when requirements change.

Reusable test data

Don't hardcode test data in every test case. Maintain test data fixtures:

  • Standard test accounts: tester+admin@, tester+regular@, tester+locked@.
  • Standard test orgs / tenants.
  • Sample data sets (1k, 10k, 100k records) for performance.

Refresh between test runs from a known baseline.

Test cases vs test scripts

  • Test case — what to test (scenarios, expected outcomes).
  • Test script — how to test it, in code (automated).

One test case may have multiple scripts (one per browser, one per locale). Cases live in test management; scripts live in your code repo.

Test Execution

Before execution

  • Verify entry criteria — environment ready, code deployed, smoke passes.
  • Test data is loaded.
  • Test cases reviewed.
  • Tools / accounts ready.

During execution

  • Follow test cases step by step. Don't skip.
  • Note actual result for each test.
  • If a step fails, capture: screenshot, browser console, network log, DB state.
  • Mark status: Pass / Fail / Blocked / Skipped.
  • If blocked, note the blocker and move to the next test.

You'll rarely have time to run every test. Prioritize:

  1. Smoke first — verify the build is testable.
  2. Highest-priority / highest-risk test cases (Module 29).
  3. Bug-fix verification + regression around the fix.
  4. Then broader regression.
  5. Finally, exploratory.

Exit criteria from the test plan. Common conditions:

  • All P1/P2 test cases passed.
  • Critical bugs resolved.
  • Test coverage target met.

  • Stakeholder sign-off.

Module 35
When to Automate

Automation is not free

The myth: "automate everything; manual testing is dead."
The reality: every automated test costs to write AND to maintain. If a test is run once, manual is cheaper.

Automate when

  • Run frequently — regression, smoke, every PR.
  • Stable — feature won't change next sprint.
  • Repetitive — same scenario, different data.
  • Critical path — login, checkout, money flows.
  • Hard to do manually — load, performance, race conditions.
  • Cross-browser / cross-device — combinatorics impractical manually.
  • Long-term value — will be useful for years.

Don't automate when

  • One-off — quick verification of a bug fix, then never again.
  • Highly volatile — feature is changing weekly; tests rot faster than they pay back.
  • Subjective — usability, look-and-feel.
  • Exploratory — you're learning the system; automation is for known scenarios.
  • Setup cost > benefit — complex test data setup for one assertion.
  • Visual changes — pixel-perfect comparisons are flaky; humans see pixel issues better.

The ROI calculation

Time to automate test:  T_automate
Time to run manually:   T_manual
Times we'll run it:     N

Manual total: N × T_manual
Auto total:   T_automate + (N × T_run_auto) + maintenance

Auto wins when:
   T_automate < N × (T_manual - T_run_auto - per-run-maintenance)

For a 5-min test that runs every PR for a year (250 runs), automation easily pays back. For a one-off check, never.

The 80/20 of automation effort

  • 80% — happy paths, regression, smoke.
  • 20% — exploratory, edge cases, subjective.

Automation handles the boring repetitive 80%; humans focus their attention on the high-value 20%.

UI Test Best Practices

Make tests robust

  • Test user-visible behavior, not implementation. Don't test "this CSS class is present"; test "the button is visible and labeled correctly".
  • Use accessibility-first locators — getByRole, getByLabel. Last resort: data-testid.
  • Avoid CSS class / structural selectors — break on every refactor.
  • Avoid hard waits — use auto-waits; if you need a delay, wait for a condition (URL changed, element visible).
  • Stable test data — known accounts / known fixtures, refreshed between runs.

Make tests independent

  • Each test sets up its own state.
  • No "test B depends on test A having run."
  • Order shouldn't matter.
  • Parallel-safe — no shared mutable state.

Speed up

  • Skip the UI for setup — log in via API to get a token, then load the page authenticated. UI login takes seconds; API login takes ms.
  • Pre-load test data via API or DB seeds, not by clicking through forms.
  • Reset to known state between tests via API, not by reverting all UI changes manually.
// Bad — UI login in every test
beforeEach(() => cy.visit('/login').type('email').type('pwd').click('submit'));

// Good — programmatic login
beforeEach(() => {
    cy.request('POST', '/api/auth/login', { email, password })
      .then(r => window.localStorage.setItem('Token', r.body.token));
    cy.visit('/dashboard');
});

Handle flakiness

  • Investigate every flaky test. They're a signal of a real timing issue, not "just retry."
  • Quarantine truly intermittent tests — better to skip than retry blindly.
  • Use trace viewer / video / screenshots on failure.
  • Common flakiness sources: animations, network race, time-dependent assertions, third-party widgets.

What to E2E-test (and what to skip)

YesNo
Critical user flows (login, checkout)Edge cases of validation logic
Cross-feature integrationLogic better tested at unit level
Permission-based scenariosCosmetic styling
Error states with toastsEvery input field separately

Per-test cost rule of thumb

If a test takes > 30 seconds to run, you're probably testing too much in one test. Split it. Faster tests = faster feedback = more confidence.

Module 42
Page Object Model (POM)

The problem POM solves

Without it, locators and actions are scattered across tests. When a button's selector changes, you fix it in 50 tests.

Without POM

test('login works', async ({ page }) => {
    await page.goto('/login');
    await page.fill('#email', 'alice@example.com');
    await page.fill('#password', 'Secret123!');
    await page.click('#submit-btn');
});

test('login fails on bad password', async ({ page }) => {
    await page.goto('/login');
    await page.fill('#email', 'alice@example.com');
    await page.fill('#password', 'wrong');
    await page.click('#submit-btn');
    // ...
});

With POM

// LoginPage.ts
export class LoginPage {
    constructor(private page: Page) {}

    async goto() { await this.page.goto('/login'); }

    async login(email: string, password: string) {
        await this.page.getByLabel('Email').fill(email);
        await this.page.getByLabel('Password').fill(password);
        await this.page.getByRole('button', { name: /sign in/i }).click();
    }

    async errorMessage() {
        return this.page.getByRole('alert').textContent();
    }
}

// In tests
test('login works', async ({ page }) => {
    const login = new LoginPage(page);
    await login.goto();
    await login.login('alice@example.com', 'Secret123!');
});

The principle

One Page Object per page (or per major UI section). It encapsulates:

  • Locators (private to the page object).
  • Actions (high-level operations: login(), addToCart()).
  • Assertions about the page (sometimes — opinions vary).

Tests use the page objects; tests don't use raw locators directly.

Modern alternatives — fixtures

Playwright's fixture system is a more flexible option:

// fixtures.ts
export const test = base.extend({
    loginAsAdmin: async ({ page }, use) => {
        await page.goto('/login');
        // ... login as admin
        await use(page);
    },
});

test('admin can edit users', async ({ loginAsAdmin: page }) => {
    // already logged in
});

POM pitfalls

  • Over-abstraction — too many layers; tests become unreadable.
  • Returning page objects from page objects — call chains get nutty.
  • Putting assertions in page objects — couples assertion logic; some prefer to keep assertions only in tests.
  • One giant page object — should be one per logical page; split big ones.

Small-app alternative

For small apps (< 20 tests), POM might be overkill. Inline locators are fine. Adopt POM when tests start duplicating locators.

Module 43
Why API Testing

The under-appreciated layer

UI testing is glamorous; API testing is high-ROI:

  • Fast — milliseconds vs seconds for UI.
  • Stable — APIs change less often than UIs.
  • Independent — test backend before frontend exists.
  • Comprehensive — easier to test edge cases & errors.
  • Catches real bugs — much business logic lives in APIs.

What to test at the API level

  • Status codes — 200, 201, 400, 401, 403, 404, 409, 422, 500.
  • Response shape — schema, required fields.
  • Response values — correct data returned.
  • Error responses — proper structure, helpful messages.
  • Headers — Content-Type, security headers, CORS.
  • Authentication — anonymous / valid token / expired token / wrong scope.
  • Authorization — same endpoint, different users; check who can do what.
  • Validation — required fields, format rules, length limits.
  • Side effects — DB changes after POST/PUT/DELETE.
  • Idempotency — repeating PUT/DELETE doesn't break.
  • Concurrency — parallel requests don't corrupt state.
  • Performance — response time per endpoint.
  • Rate limiting — throttling kicks in.
  • Versioning — old API version still works.

The API testing pyramid

       ┌───────┐
       │  E2E  │     few via UI
       └───────┘
   ┌───────────────┐
   │  API tests    │   many — fast, stable
   └───────────────┘
 ┌─────────────────────┐
 │   Unit tests        │
 └─────────────────────┘

For a typical web app: 100 unit tests, 50 API tests, 5 UI tests is healthier than 100 UI tests with no API tests.

Pick your tool

  • Postman + Newman — GUI-driven, low barrier; non-devs can write tests.
  • k6 — code-based JS; performance + functional in one tool.
  • REST Assured (Java) — code-based.
  • SuperTest (Node) — for tests right next to the API code.
  • Karate — BDD-style, no code.
  • Pact — contract testing (Module 47).

GraphQL Testing

Different from REST

Module 47
Contract Testing (Pact)

The microservice problem

Service A calls Service B. They evolve independently. How do you ensure A's expectations match B's reality without running them together (slow, brittle, late)?

Contract testing

The consumer (A) declares: "I expect B to return responses shaped like X for request Y." This becomes a contract. The producer (B) verifies it can satisfy every contract from every consumer. Run in CI on each side.

  Consumer (A) tests          Producer (B) verifies
  ┌──────────────┐            ┌────────────────────┐
  │ "I'll call B │            │ "All consumer      │
  │  with X and  │ ── pact ──►│  contracts pass    │
  │  expect Y"   │   broker   │  against my code"  │
  └──────────────┘            └────────────────────┘

How Pact works (consumer side)

// Consumer test (Pact in JS)
const provider = new Pact({ consumer: 'A', provider: 'B' });

it('returns user details', async () => {
    await provider.addInteraction({
        state: 'user 42 exists',
        uponReceiving: 'a request for user 42',
        withRequest: { method: 'GET', path: '/users/42' },
        willRespondWith: {
            status: 200,
            body: { id: 42, name: 'Alice', email: 'a@x.com' }
        }
    });

    const result = await fetchUser(42);
    expect(result.name).toBe('Alice');
});
// Produces: pact-A-B.json — the contract

Producer side

// Producer's CI: run all consumers' pacts against the real service
pact-verifier --provider B --pact-broker-url ... --provider-base-url http://localhost:8080

If a producer's code change breaks any consumer's contract, the producer's CI fails. The break is caught BEFORE deployment.

Why contract testing matters

  • No more "team B broke us in production."
  • Faster than integration tests (no orchestration of multiple services).
  • Documents what each consumer actually uses.
  • Enables independent deployment with confidence.

When to use it

  • Microservices with multiple consumers.
  • Teams owning different services.
  • Independent deploy cadences.

When it's overkill

  • Single team, monolith.
  • Two-service systems with co-deploy.
  • External consumers you don't control (use OpenAPI compliance instead).

Pact Broker

Central server that stores contracts and verification results. Pact Foundation hosts a free version; commercial PactFlow available for enterprises.

Module 48
Performance Testing Fundamentals

The mindset

Performance tests answer "how fast / how many" questions. Unlike functional tests (pass/fail), perf tests produce numbers you compare against targets.

Define your performance targets first

Without targets, perf testing is a fishing trip. Examples of measurable targets:

  • p95 login latency < 200 ms.
  • System sustains 1000 concurrent users.
  • Throughput ≥ 500 orders/second.
  • Error rate < 0.1% under expected load.
  • CPU < 70% under peak load (room to spare).
  • Memory grows ≤ 5% over a 24-hour soak test.

Realistic load profiles

Don't test "1000 users hammering one endpoint." Real users have a workflow:

  10% — login
  30% — browse catalog
  20% — view product detail
  15% — add to cart
   8% — checkout
   5% — view order status
   2% — admin / reports
  10% — search

Get the actual breakdown from production logs / analytics; replay it.

Workload patterns

  • Constant — flat load.
  • Ramp-up — gradually increase to target.
  • Step load — increase, hold, increase, hold.
  • Burst — spike from low to high suddenly.
  • Random / realistic — replay actual production patterns.

Environment matters

Performance tests in the wrong environment lie. Best:

  • Production-like infrastructure — same cloud region, same instance sizes.
  • Realistic data volume — 1000-row test DB tells you nothing about a 10M-row prod DB.
  • Realistic data distribution — hot/cold rows, indexes used, query patterns.
  • Network conditions — same latency between tiers.

Output: actionable findings

Every perf run produces:

  • p50 / p95 / p99 latency per endpoint.
  • Throughput sustained.
  • Error rate, types of errors.
  • Resource utilization (CPU / RAM / I/O / network).
  • DB query times, slow queries.
  • External dependency latencies.

Compare against previous runs to detect regressions before they reach prod.

Metrics & Analysis

The four golden signals (Google SRE)

SignalWhat
LatencyTime to serve a request (success and failure separately)
TrafficDemand — req/sec, bytes/sec
ErrorsRate of failed requests
SaturationHow full your resources are (CPU/RAM/queue)

Percentiles, not averages

Average latency hides outliers. A handful of 5-second requests don't move the average much, but those users had a bad time.

PercentileMeaning
p50 (median)Half of users see this or better
p955% see worse
p991% see worse
p99.90.1% see worse

For 1M requests/day: p99 = 10,000 unhappy users daily. p99.9 = 1000. Always look at the tail.

Throughput tells you capacity

Sustained throughput at acceptable latency = capacity ceiling. Often discovered as the "knee" — load beyond which latency spikes:

  Latency
    │
    │                              ╱ exponential
    │                            ╱
    │   stable ─────╱─── knee ─/
    │      latency
    └─────────────────────────────────► Throughput

Resource utilization patterns

  • CPU-bound — CPU 100%, latency rising; need more compute.
  • Memory-bound — high memory, GC thrashing; need more RAM or memory leak fix.
  • I/O-bound — disk wait high; need faster storage or fewer DB queries.
  • Network-bound — bandwidth saturated; need bigger pipes / less data.
  • Lock-bound — DB blocking; needs concurrency tuning.

Common findings & fixes

Latency spike at moderate loadConnection pool exhaustedIncrease pool / fix slow queries
Memory grows over hoursMemory leakProfile, find unclosed resources
Errors only under loadRace condition / pool exhaustionConcurrency review
One endpoint dominates timeN+1 query / missing indexModule 41–48 of SQL course
External API timeouts under loadDownstream slowCaching, circuit breaker, batching
Throughput plateaus at low numberSingle-threaded code pathAsync / parallelization

  • Run summary: dates, duration, target/actual concurrency.
  • Pass/fail vs targets.
  • Latency table by endpoint (p50/p95/p99).
  • Error breakdown by type.
  • Resource graphs (CPU, RAM, etc.).

Module 56
Penetration Testing Basics

What pen testing is

Authorized simulated attack on a system to find weaknesses before adversaries do. Conducted by humans (often 3rd-party specialists), uses tools but applies creativity automated tools can't.

Types of engagement

TypeTester knowledgeCloser to
Black boxNothing (just URL)External attacker
Gray boxSome details (test account, architecture overview)Insider with limited access
White boxFull source + docsMaximum coverage

The PTES methodology

  1. Pre-engagement — scope, rules of engagement, contracts.
  2. Intelligence gathering — recon: what's exposed, what tech.
  3. Threat modeling — what's worth attacking.
  4. Vulnerability analysis — find weaknesses.
  5. Exploitation — actually break in.
  6. Post-exploitation — what could attacker do once in.
  7. Reporting — findings, severity, remediation.

Common findings on web apps

  • Authentication issues — weak password policy, no rate limit.
  • Authorization issues — IDOR, missing function-level checks.
  • Session management — predictable tokens, no expiry.
  • Input validation — XSS, injection.
  • Cryptographic weaknesses — weak algorithms, short keys.
  • Misconfigurations — exposed admin endpoints, debug pages.
  • Server vulnerabilities — outdated software.

Bug bounty programs

Crowdsource pen testing. Researchers find bugs; you pay per validated finding. Platforms: HackerOne, Bugcrowd, Intigriti. Lower setup cost than formal pen tests; ongoing coverage; attracts talent.

When to pen test

  • Annually for any production system.
  • Before any major release.
  • After significant architecture changes.
  • For compliance (SOC 2, ISO 27001, PCI-DSS).
  • After acquisitions / integrations.

QA's role

Most QA engineers don't do pen testing themselves but should:

  • Coordinate with pen testers.
  • Triage their findings.
  • Verify fixes for security bugs.
  • Add regression tests for fixed vulnerabilities.
  • Run automated security scans (ZAP / Burp) regularly.

List of every component (and version) in your build. Generated automatically by Syft, Trivy, or your container builder. Enables:

  • "Is this CVE in our deployment?" — answer in seconds.
  • License compliance.
  • Supply-chain attack response.

Pipeline gates

  • Block on critical / high vulnerabilities — must fix or document why ignored.
  • Warn on medium / low — visible but not blocking.
  • Suppress false positives explicitly with a justification.

The DevSecOps mindset

Security isn't a separate team gate. It's the team's responsibility, with tools and processes that make secure-by-default easy. QA participates by adding security tests to the regression suite (login lockouts, permission checks, header validation) and reviewing findings.

Module 64
KPIs & Metrics

Useful metrics

Coverage

  • Code coverage — % lines / branches executed by tests. 70–80% is typical target.
  • Requirements coverage — % requirements with at least one test.
  • Test execution coverage — % planned tests actually run this cycle.

Effectiveness

  • Defect detection rate — bugs found per test cycle.
  • Defect leakage — bugs found in production / total bugs. Lower is better.
  • Defect density — bugs per KLOC or per feature.
  • Test pass rate — % of executed tests passing.
  • First-time pass rate — % of fixes that pass verification on first try.

Efficiency

  • Test execution time — total CI runtime trend.
  • Mean time to detect (MTTD) — how fast do we find bugs?
  • Mean time to fix.
  • Automation % — automated vs manual tests.
  • Flaky test rate — tests that pass/fail intermittently.

Quality of QA process

  • Reopen rate — % of bugs marked fixed that reopen. < 10% healthy.
  • Bug rejection rate — bugs marked "not a bug" / total. High = unclear specs or weak QA.
  • Open defect age — how long bugs sit open.
  • Test maintenance cost — time spent updating tests vs writing new.

The metrics trap

Metrics drive behavior. Bad metrics = bad behavior:

  • "Test cases written" → 50-step bloated cases that aren't useful.
  • "Bugs found" → false positives, duplicates, "minor cosmetic" inflation.
  • "Pass rate" → skipping or marking-pass under pressure.
  • "Coverage %" → trivial tests that execute lines without asserting.

The DORA metrics — for the whole engineering org

From Google's State of DevOps research:

  • Deployment frequency.
  • Lead time for changes.
  • Change failure rate.
  • Mean time to recovery.

QA contributes to all four. Faster, more reliable testing = faster, more reliable releases.

Module 65
Test Estimation

The eternal question: "how long will testing take?"

Stakeholders need a number. Bad estimates → unrealistic deadlines → corner-cutting → bugs in prod.

Estimation techniques

Top-down — by experience

"Past similar features took ~30 hours of QA. This one's similar size; estimate 30 hours." Quick; relies on similar past data.

Bottom-up — by test case

"Estimate effort per test case (designing + executing + bugs)."

ActivityAvg hours
Design + write a test case0.25–1
Execute manual test case0.1–0.5
Reproduce + report a bug0.3–1
Verify a fix0.1–0.3
Automate a test1–4 (one-time)

For 100 test cases: design 50h, run 30h, ~30 bugs × 0.5h = 15h, verify 10h. ~105 hours = ~3 person-weeks.

Function point analysis

Score the system's complexity in standardized "function points"; multiply by historical hours-per-FP. More formal; used in regulated environments.

3-point estimation (PERT)

Estimate = (Optimistic + 4×Most likely + Pessimistic) / 6

Reduces overconfidence. Good for risky / unfamiliar work.

Story points (Agile)

Relative sizing — "this is bigger than that." Doesn't translate to hours directly; tracked over time as velocity.

Add buffer for the unknowns

Common contingency:

  • Stable / known feature: +10–20%.
  • New feature, familiar tech: +30%.
  • New tech / external dependencies: +50–100%.
  • "How would Hofstadter's Law apply here?" — it always takes longer than you expect, even when you account for Hofstadter's Law.

What to include in your estimate

  • Test case design.
  • Test case execution.
  • Bug reporting + retesting.
  • Test data setup / cleanup.
  • Environment troubleshooting (often eats hours).
  • Regression testing.
  • Reporting / status meetings.
  • Communication with dev / product.
  • Buffer for blockers.

Tracking actuals vs estimates

After each cycle: did it take what you said? Track your accuracy. Over time, estimates improve.

Module 67
TDD — Test-Driven Development

The cycle

     Red   ──►  Green  ──►  Refactor
       │            │             │
       │            │             │
   write a       make it       improve
   failing       pass           the code
   test                         (tests still pass)
       ▲                              │
       └──────────────────────────────┘

The discipline

  1. Write a test for a tiny new behavior.
  2. Run it — it fails (red).
  3. Write the simplest code to make it pass.
  4. Run all tests — green.
  5. Refactor — clean up while keeping tests green.
  6. Repeat.

Key rule: never write production code without a failing test that requires it.

Why TDD works

  • Forces you to design API from the consumer's perspective first.
  • Coverage near 100% by construction.
  • Refactor fearlessly — tests catch breakage.
  • Tests document intent (better than comments).
  • Small steps prevent big mistakes.

Why TDD is hard

  • Slows initial coding.
  • Requires discipline to not skip the test.
  • Hard for code with heavy I/O / framework integration.
  • Wrong tests = wrong code; quality of tests matters.
  • Many devs were never taught it.

Mocks and stubs

  • Stub — returns canned answers ("when called, return X").
  • Mock — verifies interactions ("expect this to be called once with Y").
  • Fake — working but simplified implementation (in-memory DB).
  • Spy — records calls; you assert later.

Test doubles in C# / Moq

var mock = new Mock<IUserRepository>();
mock.Setup(r => r.GetByEmail("a@x.com"))
    .ReturnsAsync(new User { Id = 1, Email = "a@x.com" });

var service = new UserService(mock.Object);
var user = await service.LoginAsync("a@x.com", "password");

mock.Verify(r => r.GetByEmail("a@x.com"), Times.Once);

Where TDD is gold

  • Pure logic — calculations, parsing, transformations.
  • Algorithms.
  • Domain models.
  • Bug fixes — write the test that reproduces the bug, then fix.

Where TDD is awkward

  • UI — visual changes are hard to TDD.
  • Integration with external systems — write an integration test instead.
  • Throwaway prototypes / spikes.

Module 68
BDD — Behavior-Driven Development

What BDD adds to TDD

TDD is technical — devs writing tests for code. BDD adds a shared language so business and tech align on what "correct" means.

Gherkin syntax — Given/When/Then

Feature: User login

  Scenario: Successful login with valid credentials
    Given a user "alice@example.com" with password "Secret123!"
    And the user is on the login page
    When they enter their email and password
    And click "Sign in"
    Then they should be redirected to the dashboard
    And see "Welcome, Alice"

  Scenario: Failed login with wrong password
    Given a user "alice@example.com"
    When they enter the wrong password
    Then they should see "Invalid credentials"
    And remain on the login page

Stakeholders read this

Product, business, even legal can read Gherkin scenarios and confirm: "yes, that's what we mean by login." This collaborative writing is the real value of BDD.

Step definitions — code behind the scenes

// SpecFlow (.NET)
[Given(@"a user ""(.*)"" with password ""(.*)""")]
public async Task GivenUser(string email, string password)
{
    await _db.Users.AddAsync(new User { Email = email, ... });
    await _db.SaveChangesAsync();
}

[When(@"they enter their email and password")]
public async Task EnterCredentials()
{
    await _page.GetByLabel("Email").FillAsync(_email);
    await _page.GetByLabel("Password").FillAsync(_password);
}

[Then(@"they should be redirected to the dashboard")]
public async Task SeeDashboard()
{
    await _page.WaitForURLAsync("**/dashboard");
}

Module 69
ATDD — Acceptance Test-Driven Development

The variant

ATDD = write acceptance tests (from user perspective) BEFORE building. Sometimes used interchangeably with BDD, sometimes distinguished:

  • BDD focuses on the language — Gherkin scenarios.
  • ATDD focuses on the practice — start with acceptance tests, then build.

The cycle

  1. Customer / product describes a feature with examples.
  2. Team writes acceptance tests from those examples.
  3. Tests fail (red).
  4. Devs use TDD internally to build the implementation.
  5. Acceptance tests pass — feature is done.

Specification by Example

Same idea by another name. The example IS the specification:

Discount rules:
| Customer type | Order amount | Discount |
| Regular       | < 100        | 0%       |
| Regular       | 100-500      | 5%       |
| Regular       | > 500        | 10%      |
| Premium       | < 500        | 10%      |
| Premium       | >= 500       | 15%      |

This table becomes both specification and tests. No ambiguity.

Why ATDD/BDD matter for QA

  • QA participates in defining "done" before code exists.
  • Eliminates the "that's not what I asked for" loop.
  • Creates living documentation.
  • Naturally automates regression.

Module 70
Shift-Left Testing

The principle

Testing as early as possible — to the LEFT in the SDLC timeline. Find bugs when they're cheap to fix.

  Traditional ────────────────────────────► Test phase ────► Production
                  cheap to fix                   expensive

  Shift-Left ──┬─► Unit ──► Integration ──► E2E ──► Production
               │     ▲           ▲           ▲
               │     │           │           │
               └── Tests written before/with the code ──┘

Practices that shift left

  • Requirements review — QA reads requirements before coding starts; spots ambiguity, missing cases.
  • 3 amigos per story — define acceptance criteria collaboratively.
  • TDD / BDD / ATDD — tests before code.
  • Code review — QA sees the diff; reviews testability.
  • Static analysis — linters, SAST in PR.
  • Pair programming with QA — bugs caught at typing time.
  • Tests run on every commit — minutes, not days, to catch regressions.
  • Local pre-commit hooks — checks before code even reaches CI.

Shift-right too

Modern QA also shifts RIGHT — testing IN production:

  • Feature flags — release gradually, test with real users.
  • Canary deployments — small % of traffic on new version, monitor.
  • A/B testing — quantitatively compare variants.
  • Synthetic monitoring — production smoke tests every few minutes.
  • Real user monitoring (RUM) — observe actual user experience.
  • Chaos engineering — inject failures to verify resilience.

Together

Shift-left + shift-right = continuous testing across the entire lifecycle. Pre-prod and post-prod are equally important. The traditional "QA phase" disappears; quality is everywhere.

Risk-Based & Exploratory in Agile

Why these matter in Agile

Agile delivers software faster. You don't have time to test everything every sprint. Risk-based + exploratory let you focus where it matters and find what scripted tests miss — fast.

Risk-based prioritization per sprint

For each story:

  1. What's the impact if it breaks? (Low / Medium / High / Critical.)
  2. How likely is breakage? (Complexity, novelty, dev's track record.)
  3. Risk = impact × likelihood. Sort.

Test high-risk stories deeply. Sample low-risk ones.

Time-boxed exploratory in Agile

  • Reserve 20–30% of QA time for exploratory.
  • Charters per sprint, scoped to areas changed in the sprint.
  • Bugs found in exploratory often hit highest severity.

Test pyramid in Agile

  • Devs maintain unit tests near 80% coverage.
  • SDETs / devs write integration + key E2E tests.
  • QA does exploratory, UAT-style scenarios, edge-case design.
  • Performance / security tests run on a slower cadence (weekly / per release).

The "minimum testing burden" question

Each story: what's the minimum test coverage that lets us ship with acceptable risk?

  • Trivial CSS change: visual review + smoke.
  • Validation rule change: unit tests + 1 happy + 1 edge case manual.
  • New feature: full Modules 23–28 design techniques applied.
  • Auth / payment / data: maximum, including security + perf.

Common Agile QA mistakes

  • Treating QA as a phase at sprint end → bottleneck.
  • Writing exhaustive test cases for every story → no time.
  • QA-only ownership of automation → bottleneck again.
  • Skipping retrospectives → never improve.
  • Keeping bug count down by not running tests.

The principle

Every test that protects production runs automatically in CI. If it's a manual checklist, it eventually gets skipped.

Quality gates

Explicit pass/fail criteria. Examples:

  • Code coverage ≥ 75%.
  • Zero critical / high security findings.
  • p95 latency regression < 10%.
  • No new accessibility violations (axe).
  • All E2E pass.

Gates that fail block the pipeline. No release without them.

Parallelization

Tests should run in parallel:

  • Unit + lint in parallel jobs.
  • E2E split by feature, run in N parallel containers.
  • Cross-browser / cross-OS as separate jobs.

What used to take an hour serial can run in 10 minutes parallel.

Flakiness control

Flaky tests erode trust. When a flaky test exists, devs start ignoring failures: "ah, it's the flaky one again." Fixes:

  • Quarantine flaky tests immediately — mark as @Flaky or skip.
  • Investigate root cause within a fixed time (24h).
  • Don't merge flaky tests in the first place.
  • Track flake rate per test; deprioritize high-flake suites.

Test reporting in CI

  • JUnit XML output → pretty CI views.
  • Allure / ReportPortal for richer reports.
  • Upload screenshots, videos, logs on failure.
  • Comment on PRs with failure summary.
  • Slack / email on broken main builds.

Module 74
Test Data Management

The problem

Tests need data. Bad approaches:

  • Use prod data — privacy / GDPR violations.
  • Hard-code data in tests — they conflict with each other.
  • Manual data setup — tests aren't repeatable.
  • One shared dataset — tests interfere.

Strategies

1. Generate fresh data per test

Each test creates its own data, uses it, optionally cleans up. Most isolated. Slowest setup but most reliable.

// Each test creates a unique user
[Fact]
public async Task LoginTest()
{
    var email = $"test+{Guid.NewGuid():N}@example.com";
    await _factory.CreateUserAsync(email, "Secret");
    // ...
}

2. Shared fixtures

Pre-loaded test data, refreshed between test runs. Faster setup; tests must avoid mutation.

// Test bootstrapper
public static class SeedData
{
    public static User AdminUser => new() { ... };
    public static User RegularUser => new() { ... };
    public static Order PaidOrder => new() { ... };
}

3. Anonymized prod data

Copy prod schema + data; mask PII (email → fake, name → fake, but keep distribution). Realistic data for perf testing without legal issues.

  • Tools: Tonic, Mockaroo, Faker libraries.
  • Process must be repeatable; documented.

4. Synthetic data generators

  • Bogus (.NET): new Faker<User>().RuleFor(u => u.Email, f => f.Internet.Email())
  • Faker.js, Faker (Python).
  • Mockaroo: web tool generating CSVs.

Cleanup strategies

  • Transactional rollback — wrap each test in a transaction; rollback at end. Fastest if your DB supports it.
  • Per-test DB — create a fresh DB for each test (Testcontainers). Slow but bulletproof isolation.
  • Cleanup queries — explicit DELETE in tear-down.
  • Snapshot & restore — restore DB to a known state between runs.

Privacy & compliance

  • Never use real customer data in test environments.
  • If you must use prod-shaped data, mask: emails, names, SSNs, credit cards, phone numbers.
  • Audit who has access to which test environments.
  • GDPR / HIPAA may apply even to test environments.

Test data for performance

Performance tests need realistic volumes. 1000 rows in test ≠ 10M rows in prod. Pre-populate large datasets:

  • Bulk INSERT scripts.
  • Generated data via Bogus or similar.
  • Anonymized snapshot of prod.

Environment characteristics

  • Production-like — staging should mirror prod's infrastructure as closely as possible.
  • Isolated — one env's bugs don't affect another.
  • Reproducible — recreatable from infrastructure-as-code.
  • Reset-able — can be wiped clean.
  • Monitored — same observability as prod.

Modern alternatives

Ephemeral environments per PR

Spin up a fresh staging environment per pull request. Tear down after merge. Trends:

  • Vercel / Netlify do this for frontend automatically.
  • Kubernetes namespaces per PR with sealed config.
  • GitOps tools (Argo CD) deploy preview branches.

Result: every PR has its own URL with the new code; reviewers + QA can poke around without local setup.

Feature flags

Deploy code dark; enable per-user / per-tenant. Effectively merges "test in staging" with "test in prod safely":

  • Deploy → off for everyone.
  • Enable for QA team in prod.
  • Enable for 1% of users → monitor.
  • Enable for 50%, 100%.
  • Remove the flag once stable.

Tools: LaunchDarkly, Unleash, Split.io, ConfigCat. Or build minimal in-house.

Environment debt

Common problem: 5 environments named "dev1, qa1, staging-old, staging-new, hotfix" — nobody remembers which is current. Cleanup:

  • Document each environment's purpose in code (IaC repo).
  • Auto-tear-down environments not used for N days.
  • Tag every resource with owner + purpose + retention.
  • Periodic environment audit (quarterly).

Multi-tenant testing — the EasyAudit-specific concern

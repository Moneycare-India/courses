Module 1
Programming & C# Intro

What is programming?

Programming is writing instructions a computer can execute. Code is read by humans (your team, future-you) far more often than by computers — so clarity matters as much as correctness.

Programming paradigms

ParadigmIdeaExample languages
ProceduralStep-by-step instructions, functions on dataC, Pascal
Object-Oriented (OOP)Bundle data + behavior into objectsC#, Java, C++
FunctionalCompose pure functions; minimize stateF#, Haskell, Elixir
DeclarativeDescribe what not howSQL, HTML

C# is multi-paradigm — primarily OOP with strong functional features (LINQ, lambdas, records, pattern matching).

What is C#?

C# (pronounced "C sharp") is a strongly-typed, garbage-collected, OOP-first language created by Microsoft (Anders Hejlsberg, 2000). It runs on the .NET runtime. Modern C# (versions 10–13) borrows heavily from F# and TypeScript — pattern matching, records, switch expressions, immutability.

Module 2
Classes & Objects

The core idea

A class is a blueprint. An object is one concrete thing built from that blueprint. The class defines what data instances hold (fields/properties) and what behavior they offer (methods).

public class User
{
    // Fields (data)
    private string _name;
    private int _age;

    // Constructor — runs when an object is created
    public User(string name, int age)
    {
        _name = name;
        _age = age;
    }

    // Methods (behavior)
    public string Greet() => $"Hello, I'm {_name}";
    public bool IsAdult() => _age >= 18;
}

// Using it
var alice = new User("Alice", 30);    // create object
Console.WriteLine(alice.Greet());     // "Hello, I'm Alice"
Console.WriteLine(alice.IsAdult());   // True

Properties — preferred over public fields

public class User
{
    public string Name { get; set; } = "";          // auto-property
    public int Age { get; private set; }            // read-only outside

    public User(string name, int age)
    {
        Name = name;
        Age = age;
    }
}

// Why properties? They look like fields but are methods underneath —
// you can add validation later without breaking callers.
public class Account
{
    private decimal _balance;
    public decimal Balance
    {
        get => _balance;
        set
        {
            if (value < 0) throw new ArgumentException("Balance cannot be negative");
            _balance = value;
        }
    }
}

The this keyword

public class User
{
    private string _name;
    public User(string name)
    {
        this._name = name;   // 'this' refers to the current instance
    }
}

Static vs instance

public class MathUtil
{
    // Instance — needs an object
    public int Counter { get; set; }

    // Static — belongs to the class itself
    public static int Add(int a, int b) => a + b;
    public static double Pi => 3.14159;
}

var sum = MathUtil.Add(2, 3);                // no object needed
var util = new MathUtil { Counter = 5 };     // object needed

Object lifecycle

  1. Allocation — new reserves memory on the managed heap.
  2. Initialization — fields default-initialized, then constructor runs.
  3. Use — methods called, properties accessed.
  4. Eligible for collection — when no references remain.
  5. Finalization & collection — GC reclaims memory.

Module 3
Encapsulation

Encapsulation = hiding the internal state and exposing a controlled API. The class decides what callers can see and change. Internals can be refactored freely without breaking callers.

Access modifiers

ModifierVisible from
publicAnywhere
privateSame class only (default for class members)
protectedSame class & derived classes
internalSame assembly (default for top-level types)
protected internalSame assembly OR derived classes
private protectedSame assembly AND derived classes
fileSame source file only

Bad: leaky abstraction

Bad — public fields, no validation

public class BankAccount
{
    public decimal Balance;       // anyone can set
    public List<Transaction> Tx;  // anyone can mutate the list
}

var a = new BankAccount();
a.Balance = -1_000_000;           // oops

Good — private state, controlled mutations

public class BankAccount
{
    private decimal _balance;
    private readonly List<Transaction> _tx = new();

    public decimal Balance => _balance;
    public IReadOnlyList<Transaction> Transactions => _tx;

    public void Deposit(decimal amount)
    {
        if (amount <= 0) throw new ArgumentException(nameof(amount));
        _balance += amount;
        _tx.Add(new Transaction(amount, DateTime.UtcNow));
    }

    public bool TryWithdraw(decimal amount, out string error)
    {
        if (amount <= 0) { error = "Amount must be positive"; return false; }
        if (amount > _balance) { error = "Insufficient funds"; return false; }
        _balance -= amount;
        _tx.Add(new Transaction(-amount, DateTime.UtcNow));
        error = "";
        return true;
    }
}
Rule of thumb: default to private. Open up access only when there's a concrete reason.

Read-only collections

Returning List<T> from a property lets callers mutate your internal state. Return IReadOnlyList<T>, IReadOnlyCollection<T>, or IEnumerable<T> instead.

Module 4
Inheritance

Inheritance = a class derives from another, getting its members and adding/overriding behavior. "Is-a" relationship — a SavingsAccount is a BankAccount.

public class BankAccount
{
    public string AccountNumber { get; }
    protected decimal Balance { get; set; }

    public BankAccount(string number)
    {
        AccountNumber = number;
    }

    public virtual void Deposit(decimal amount)
    {
        Balance += amount;
    }

    public virtual decimal CalculateInterest() => 0;
}

public class SavingsAccount : BankAccount
{
    public decimal InterestRate { get; }

    public SavingsAccount(string number, decimal rate) : base(number)
    {
        InterestRate = rate;
    }

    public override decimal CalculateInterest() => Balance * InterestRate;
}

public class CheckingAccount : BankAccount
{
    public decimal OverdraftLimit { get; set; }
    public CheckingAccount(string number) : base(number) { }
    // Inherits Deposit, CalculateInterest from BankAccount
}

virtual / override / new / sealed

  • virtual — base method that derived classes can override.
  • override — derived class replaces a virtual method.
  • new — hides a base member without overriding (rarely correct; usually a bug).
  • sealed on class — can't be inherited from.
  • sealed override on method — final override; subclasses can't re-override.

Constructor chaining

public class Animal
{
    public string Name { get; }
    public Animal(string name) { Name = name; }
}

public class Dog : Animal
{
    public string Breed { get; }
    public Dog(string name, string breed) : base(name)   // call base ctor
    {
        Breed = breed;
    }
}

The object root

Every type ultimately derives from System.Object. That's where ToString(), GetHashCode(), Equals(), GetType() come from.

Single inheritance

C# allows only one base class — but a class can implement many interfaces. (We'll cover interfaces in Module 6.)

Inheritance trap: deep inheritance hierarchies are brittle. Changes to a base class ripple through everything. Many modern designs prefer composition (Module 7) over inheritance.

Module 5
Polymorphism

Polymorphism = the same method name behaves differently for different types. Code can hold a reference of base type, but calling a method dispatches to the actual derived type's implementation.

Runtime polymorphism (overriding)

public abstract class Shape
{
    public abstract double Area();
}

public class Circle : Shape
{
    public double Radius { get; }
    public Circle(double r) { Radius = r; }
    public override double Area() => Math.PI * Radius * Radius;
}

public class Rectangle : Shape
{
    public double W { get; }  public double H { get; }
    public Rectangle(double w, double h) { W = w; H = h; }
    public override double Area() => W * H;
}

// Polymorphism in action
Shape[] shapes = { new Circle(5), new Rectangle(3, 4) };
foreach (var s in shapes)
    Console.WriteLine(s.Area());      // dispatched to actual type

Compile-time polymorphism (overloading)

Same method name, different parameter lists.

public class Logger
{
    public void Log(string message)            { /* ... */ }
    public void Log(string message, Exception e){ /* ... */ }
    public void Log(int level, string message)  { /* ... */ }
}

Why polymorphism matters

It lets you write code against an abstraction (Shape) without knowing the concrete type. Adding a Triangle class doesn't require changing the loop above. This is the Open/Closed Principle in action (Module 9).

Interface polymorphism

public interface IExportable
{
    byte[] Export();
}

public class PdfReport : IExportable { public byte[] Export() => ...; }
public class ExcelReport : IExportable { public byte[] Export() => ...; }

void Save(IExportable r) => File.WriteAllBytes("out", r.Export());

Save(new PdfReport());
Save(new ExcelReport());

Module 6
Abstraction

Abstraction = exposing only what callers need to know; hiding the rest. In C# this is expressed primarily through abstract classes and interfaces.

Abstract class

A class that can't be instantiated directly. It may have implemented members AND abstract members that derived classes must implement.

public abstract class Notification
{
    public string Recipient { get; }
    protected Notification(string recipient) { Recipient = recipient; }

    // Implemented — shared behavior
    public void Log() => Console.WriteLine($"Sending to {Recipient}");

    // Abstract — derived class MUST implement
    public abstract Task SendAsync(string body);
}

public class EmailNotification : Notification
{
    public EmailNotification(string email) : base(email) { }
    public override Task SendAsync(string body) { /* SMTP */ return Task.CompletedTask; }
}

public class SmsNotification : Notification
{
    public SmsNotification(string phone) : base(phone) { }
    public override Task SendAsync(string body) { /* SMS API */ return Task.CompletedTask; }
}

Interface

A pure contract — names and signatures, no state. A class can implement many interfaces.

public interface IEmailSender
{
    Task SendAsync(string to, string subject, string body);
}

public interface IRetryable
{
    int MaxAttempts { get; }
    Task RetryAsync();
}

// Multi-interface implementation
public class SmtpEmailSender : IEmailSender, IRetryable
{
    public int MaxAttempts => 3;
    public Task SendAsync(string to, string subj, string body) { ... }
    public Task RetryAsync() { ... }
}

Default interface methods (C# 8+)

Interfaces can have default implementations now — useful for adding methods to existing interfaces without breaking implementers.

public interface ILogger
{
    void Log(string msg);
    void LogError(string msg) => Log("ERROR: " + msg);  // default impl
}

Abstract class vs interface — when to use which?

Use abstract class when…Use interface when…
You want to share state & partial implementationYou only define behavior contracts
Strong "is-a" relationship"Can do X" capability (multi-interface OK)
Hierarchy will evolve carefullyMany unrelated types should expose the same API
Constructor logic mattersYou need maximum flexibility / DI mocking
Modern .NET preference: default to interfaces for testability and DI. Use abstract classes only when there's real shared state to encapsulate.

Module 7
Composition vs Inheritance

Two ways to reuse code:

  • Inheritance ("is-a"): SavingsAccount is a BankAccount.
  • Composition ("has-a"): OrderService has a PaymentGateway.

The composition example

// Composition: OrderService doesn't INHERIT payment behavior; it HAS a gateway.
public class OrderService
{
    private readonly IPaymentGateway _payments;
    private readonly IEmailSender _email;
    private readonly ILogger _log;

    public OrderService(IPaymentGateway payments, IEmailSender email, ILogger log)
    {
        _payments = payments;
        _email = email;
        _log = log;
    }

    public async Task PlaceOrderAsync(Order o)
    {
        await _payments.ChargeAsync(o.Total);
        await _email.SendAsync(o.CustomerEmail, "Order placed", "...");
        _log.Log($"Order {o.Id} placed");
    }
}

Note: collaborators are injected via the constructor — that's Dependency Injection (Module 27). Each dependency can be swapped out (real, mock, decorator).

Why "Favor Composition Over Inheritance"

IssueInheritanceComposition
CouplingTight — derived knows base internalsLoose — depends only on a contract
FlexibilityLocked at compile timeCan swap collaborators at runtime
TestingHard to isolateEasy — inject mocks
EvolutionBase changes ripple to all subclassesEach component evolves independently
Reuse across typesOnly via shared baseAny type can hold any component

Rule of thumb

  • Use inheritance sparingly — for true "is-a" with stable, well-understood hierarchies (Stream → FileStream, Exception → ArgumentException).
  • Use composition + interfaces for almost everything else.

Module 8
SRP — Single Responsibility Principle

"A class should have one, and only one, reason to change." — Robert C. Martin

If a class touches multiple unrelated concerns (database, email, validation, formatting), each concern is a reason it might need to change. Splitting them keeps changes local.

Bad — God class

public class UserService
{
    public void RegisterUser(User u)
    {
        // Validation
        if (string.IsNullOrEmpty(u.Email)) throw ...;

        // Hashing
        u.PasswordHash = BCrypt.HashPassword(u.Password);

        // DB access
        using var conn = new SqlConnection(...);
        conn.Execute("INSERT INTO Users ...");

        // Email
        var smtp = new SmtpClient("mail.corp");
        smtp.Send("Welcome", u.Email);

        // Logging
        File.AppendAllText("log.txt", $"{u.Email} registered");
    }
}

Good — split responsibilities

public class UserService
{
    private readonly IUserValidator _val;
    private readonly IPasswordHasher _hasher;
    private readonly IUserRepository _repo;
    private readonly IEmailSender _email;
    private readonly ILogger _log;

    public UserService(IUserValidator v, IPasswordHasher h,
        IUserRepository r, IEmailSender e, ILogger l)
    { _val = v; _hasher = h; _repo = r; _email = e; _log = l; }

    public async Task RegisterAsync(User u)
    {
        _val.Validate(u);
        u.PasswordHash = _hasher.Hash(u.Password);
        await _repo.AddAsync(u);
        await _email.SendWelcomeAsync(u.Email);
        _log.LogInformation("User {Email} registered", u.Email);
    }
}

Now changing the email provider doesn't touch UserService. Changing the password hash algorithm doesn't either.

SRP at the method level

The same idea applies to methods. A 200-line method usually does too much. Extract small, well-named helpers.

Module 9
OCP — Open/Closed Principle

"Open for extension, closed for modification." Adding new behavior should not require editing existing tested code.

Bad — switch statement that grows forever

public class DiscountCalculator
{
    public decimal Calculate(string customerType, decimal total)
    {
        switch (customerType)
        {
            case "Regular":  return total;
            case "Silver":   return total * 0.95m;
            case "Gold":     return total * 0.90m;
            // every new tier requires editing this method
            default: throw new ArgumentException();
        }
    }
}

Good — strategy via interface

public interface IDiscountStrategy
{
    decimal Apply(decimal total);
}

public class RegularDiscount : IDiscountStrategy
{ public decimal Apply(decimal t) => t; }

public class SilverDiscount : IDiscountStrategy
{ public decimal Apply(decimal t) => t * 0.95m; }

public class GoldDiscount : IDiscountStrategy
{ public decimal Apply(decimal t) => t * 0.90m; }

// Adding "Platinum" = new class, no edits to existing.
public class PlatinumDiscount : IDiscountStrategy
{ public decimal Apply(decimal t) => t * 0.80m; }

The "closed for modification" half matters most when code is widely used or under test. Constantly editing a battle-tested class to add new branches risks regressions.

Where OCP applies most

  • Domain logic that grows over time (pricing, rules, validations).
  • Plugin-like systems (export formats, payment providers).
  • Anywhere you find yourself touching the same big switch repeatedly.

Module 10
LSP — Liskov Substitution Principle

"Subtypes must be substitutable for their base types." If your code works with a base class, it should work with any derived class without surprise.

Classic violation: Square inheriting Rectangle

public class Rectangle
{
    public virtual int Width  { get; set; }
    public virtual int Height { get; set; }
    public int Area => Width * Height;
}

public class Square : Rectangle
{
    public override int Width
    {
        set { base.Width = value; base.Height = value; }
    }
    public override int Height
    {
        set { base.Width = value; base.Height = value; }
    }
}

void Test(Rectangle r)
{
    r.Width = 5;
    r.Height = 4;
    Debug.Assert(r.Area == 20);   // FAILS for Square (16)
}

Better: don't force the inheritance

public interface IShape
{
    int Area { get; }
}

public class Rectangle : IShape
{
    public int Width { get; }
    public int Height { get; }
    public Rectangle(int w, int h) { Width = w; Height = h; }
    public int Area => Width * Height;
}

public class Square : IShape
{
    public int Side { get; }
    public Square(int s) { Side = s; }
    public int Area => Side * Side;
}

LSP red flags

  • Subclass throws NotSupportedException for inherited methods.
  • Subclass tightens preconditions (refuses inputs the base accepted).
  • Subclass weakens postconditions (returns less than the base promised).
  • Code does if (obj is Square) { … } else { … } — you've already broken substitutability.

Module 11
ISP — Interface Segregation Principle

"Clients should not be forced to depend on methods they don't use." Many small focused interfaces beat one fat interface.

Bad — fat interface forces empty implementations

public interface IWorker
{
    void Work();
    void Eat();
    void Sleep();
}

public class HumanWorker : IWorker
{
    public void Work() { ... }
    public void Eat() { ... }
    public void Sleep() { ... }
}

public class RobotWorker : IWorker
{
    public void Work() { ... }
    public void Eat() => throw new NotSupportedException();   // smell
    public void Sleep() => throw new NotSupportedException(); // smell
}

Good — focused interfaces

public interface IWorkable { void Work(); }
public interface IFeedable  { void Eat(); }
public interface ISleepable { void Sleep(); }

public class HumanWorker : IWorkable, IFeedable, ISleepable
{
    public void Work() { ... }
    public void Eat() { ... }
    public void Sleep() { ... }
}

public class RobotWorker : IWorkable
{
    public void Work() { ... }
    // No need to implement what robots don't do
}

Practical guideline

Aim for interfaces with 1–5 methods. If you find yourself implementing parts as no-ops or throwing exceptions, split the interface.

Module 12
DIP — Dependency Inversion Principle

"High-level modules should not depend on low-level modules. Both should depend on abstractions." And: "Abstractions should not depend on details. Details should depend on abstractions."

Bad — hard dependency on concrete class

public class OrderService
{
    private readonly SqlOrderRepository _repo = new SqlOrderRepository();
    //                ^^^ tied to SQL forever; can't unit-test in isolation

    public void Place(Order o) => _repo.Save(o);
}

Good — depend on an abstraction

public interface IOrderRepository
{
    Task SaveAsync(Order order);
}

public class OrderService
{
    private readonly IOrderRepository _repo;
    public OrderService(IOrderRepository repo) => _repo = repo;

    public Task PlaceAsync(Order o) => _repo.SaveAsync(o);
}

// Wire up at composition root (Program.cs)
services.AddScoped<IOrderRepository, SqlOrderRepository>();
// In a test, swap for InMemoryOrderRepository.

Why "inversion"?

Without DIP, the high-level OrderService depends on the low-level SqlOrderRepository — control flows downward through the dependency graph. With DIP, both depend on the IOrderRepository abstraction — the dependency direction is "inverted" so the low-level adapter conforms to the high-level contract.

DIP enables

  • Testability — inject fakes/mocks.
  • Pluggability — swap implementations without recompiling consumers.
  • Layered architecture — domain layer doesn't know about EF Core or SMTP.

Module 13
Creational Patterns

Factory Method

Defer instantiation to a method (often virtual). Caller asks for an object without naming the concrete class.

public abstract class ReportFactory
{
    public abstract IReport Create();
}
public class PdfReportFactory : ReportFactory
{
    public override IReport Create() => new PdfReport();
}
public class ExcelReportFactory : ReportFactory
{
    public override IReport Create() => new ExcelReport();
}

Abstract Factory

Factory of factories — produce families of related objects (e.g., a UI theme produces matching Button + TextBox + Window).

Builder

Construct complex objects step by step. .NET uses this everywhere — WebApplication.CreateBuilder(), StringBuilder, EF Core query building.

public class EmailBuilder
{
    private string _to = "", _subject = "", _body = "";
    private readonly List<string> _cc = new();

    public EmailBuilder To(string a)   { _to = a; return this; }
    public EmailBuilder Cc(string a)   { _cc.Add(a); return this; }
    public EmailBuilder Subject(string s){ _subject = s; return this; }
    public EmailBuilder Body(string b) { _body = b; return this; }

    public Email Build() => new Email(_to, _cc, _subject, _body);
}

var email = new EmailBuilder()
    .To("alice@x.com")
    .Cc("bob@x.com")
    .Subject("Hi")
    .Body("Hello")
    .Build();

Singleton

Exactly one instance. Avoid hand-rolled singletons. Use the DI container with AddSingleton<T>() instead — easier to test, easier to dispose.

// AVOID:
public sealed class Logger
{
    private static readonly Logger _instance = new();
    public static Logger Instance => _instance;
    private Logger() { }
}

// PREFER:
services.AddSingleton<ILogger, FileLogger>();
// then inject ILogger anywhere it's needed

Prototype

Clone existing instances instead of constructing fresh. Less common in C# (records have with expressions; classes use copy constructors).

Module 14
Structural Patterns

Adapter

Wrap an incompatible interface so it fits the one your code expects.

// You have:
public class LegacyXmlParser
{
    public XmlDocument Parse(string xml) { ... }
}
// You want everywhere to use:
public interface IDocumentParser
{
    Document Parse(string text);
}

// Adapter:
public class XmlToDocumentAdapter : IDocumentParser
{
    private readonly LegacyXmlParser _legacy = new();
    public Document Parse(string text)
    {
        var xml = _legacy.Parse(text);
        return new Document(xml.OuterXml);
    }
}

Decorator

Wrap an object to add behavior without changing its class. Excellent for cross-cutting concerns: caching, logging, retry.

public interface IUserRepository { Task<User?> GetAsync(int id); }

public class SqlUserRepository : IUserRepository
{
    public async Task<User?> GetAsync(int id) { /* DB */ }
}

public class CachingUserRepository : IUserRepository
{
    private readonly IUserRepository _inner;
    private readonly IMemoryCache _cache;

    public CachingUserRepository(IUserRepository inner, IMemoryCache cache)
    { _inner = inner; _cache = cache; }

    public async Task<User?> GetAsync(int id)
    {
        if (_cache.TryGetValue(id, out User? cached)) return cached;
        var user = await _inner.GetAsync(id);
        _cache.Set(id, user, TimeSpan.FromMinutes(5));
        return user;
    }
}

// In DI:
services.AddScoped<SqlUserRepository>();
services.AddScoped<IUserRepository>(sp =>
    new CachingUserRepository(sp.GetRequiredService<SqlUserRepository>(),
                              sp.GetRequiredService<IMemoryCache>()));

Facade

One simple API in front of a complex subsystem. Hides internal complexity from callers.

Proxy

A stand-in for another object — controls access, lazy-loads, or adds remote calls. EF Core uses proxies for change tracking.

Composite

Treat individual objects and groups uniformly via a common interface. Tree-shaped data.

Bridge

Decouple abstraction from implementation so they vary independently. Less common day-to-day; useful in cross-platform UIs.

Module 15
Behavioral Patterns

Strategy

Encapsulate algorithms behind an interface; pick one at runtime. (We saw this in Module 9 with discounts.)

Observer

Subjects publish events; observers subscribe and react. C# bakes this into the language with event + delegates.

public class OrderProcessor
{
    public event EventHandler<Order>? OrderPlaced;
    public void Place(Order o)
    {
        // ...
        OrderPlaced?.Invoke(this, o);
    }
}

Async / Await

async/await turns asynchronous code into something that reads like sync code. Critical for I/O-bound work — DB queries, HTTP calls, file I/O.

Basic shape

public async Task<User> GetUserAsync(int id)
{
    var user = await _db.Users.FindAsync(id);
    return user;
}
  • async on the method = "this method may suspend".
  • await = "wait for this Task; release the thread until it completes".
  • Returns Task, Task<T>, or ValueTask<T> for hot paths.

Why not just use threads?

A web request waiting on a DB call shouldn't tie up a thread for 50 ms doing nothing. async/await releases the thread back to the pool while the OS waits. Same hardware serves far more concurrent requests.

Common rules

  • Async all the way down. Don't mix .Result/.Wait() with await — risk of deadlocks.
  • Don't use async void except for event handlers — exceptions can't be caught.
  • Configure await in libraries: .ConfigureAwait(false) avoids capturing the sync context. Not needed in ASP.NET Core (no sync context).
  • Pass CancellationToken through async methods.
  • Naming convention: methods returning Task should end in Async.

Parallel awaits

// Sequential — 200ms total
var a = await GetAAsync();
var b = await GetBAsync();

// Parallel — 100ms if both take 100ms
var taskA = GetAAsync();
var taskB = GetBAsync();
await Task.WhenAll(taskA, taskB);
var a = await taskA;
var b = await taskB;

Cancellation

public async Task DoAsync(CancellationToken ct)
{
    await Task.Delay(1000, ct);
    ct.ThrowIfCancellationRequested();
    await _http.GetAsync("https://...", ct);
}

Module 25
Memory & GC

The managed heap

Reference types live on the heap. The Garbage Collector (GC) reclaims memory when objects are no longer reachable.

Generations

GenWhat lives thereGC frequency
Gen 0Brand-new short-lived objectsVery frequent (cheap)
Gen 1Survived one collectionLess frequent
Gen 2Long-livedRare (expensive — full collection)
LOHLarge Object Heap (≥ 85 KB)Collected with Gen 2

The "generational hypothesis": most objects die young. So GC focuses on Gen 0 — fast and cheap.

How the GC works (very short)

  1. Mark phase — start from roots (statics, locals, registers), walk the object graph, mark live objects.
  2. Sweep/compact — unmarked objects are dead; live objects compacted to remove fragmentation.

Performance-friendly habits

  • Avoid unnecessary allocations in hot paths (loops, request paths).
  • Use StringBuilder for many concatenations.
  • Reuse objects with pools (ArrayPool<T>, ObjectPool<T>).
  • Span<T> / Memory<T> — slice arrays without copying.
  • Avoid boxing — don't put value types into object needlessly.
  • struct for small short-lived data — but profile first.
  • Dispose IDisposable promptly — releases unmanaged handles even before GC.

Diagnostics

public string CreateJwt(User user)
{
    var claims = new[]
    {
        new Claim(JwtRegisteredClaimNames.Sub, user.Id.ToString()),
        new Claim(JwtRegisteredClaimNames.Email, user.Email),
        new Claim("role", user.Role),
        new Claim(JwtRegisteredClaimNames.Jti, Guid.NewGuid().ToString())
    };

    var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(_jwt.Key));
    var creds = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);

    var token = new JwtSecurityToken(
        issuer: _jwt.Issuer,
        audience: _jwt.Audience,
        claims: claims,
        expires: DateTime.UtcNow.AddMinutes(60),
        signingCredentials: creds);

    return new JwtSecurityTokenHandler().WriteToken(token);
}

Strategies explained

StrategyWhat
RetryRe-attempt failed operations (transient errors). Add exponential backoff + jitter.
Circuit breakerIf too many failures, stop calling for a cool-down. Prevents thundering herd against a sick service.
TimeoutCap how long an operation can take.
BulkheadLimit concurrent calls — protects against cascading exhaustion.
FallbackDefault value when everything fails.
HedgingIssue parallel requests; return first to succeed.

Don't blindly retry

  • Only retry idempotent operations (GET, PUT) or operations with explicit idempotency keys.
  • Don't retry 4xx (your fault — won't change). Do retry 5xx, network errors, timeouts.
  • Always add jitter to backoffs.

Module 47
Layered Architecture

The classic split: separate concerns into horizontal layers. Each layer only depends on the layer directly below.

┌────────────────────────────────────────┐
│  Presentation                          │   Controllers, ViewModels, DTOs
├────────────────────────────────────────┤
│  Application / Service                 │   Use cases, orchestration
├────────────────────────────────────────┤
│  Domain                                │   Entities, value objects, rules
├────────────────────────────────────────┤
│  Data Access / Infrastructure          │   EF Core, SMTP, Redis, files
└────────────────────────────────────────┘

Pros

  • Familiar, easy to onboard new devs.
  • Clear file homes — "where do controllers go?".
  • Reasonable for CRUD-heavy apps.

Cons

  • Domain layer often depends on infrastructure (e.g., entities annotated with EF attributes) — a leak.
  • Risk of "anemic domain" — entities are just bags of properties; logic lives in services.
  • Cross-cutting concerns get tangled.

When to use it

Smaller apps, simple CRUD, small teams. EasyAudit's existing backends look layered today.

Module 49
Domain-Driven Design (DDD)

DDD is a set of practices for modeling complex domains. The core idea: software should reflect how the business actually works — not the database.

Tactical building blocks

ConceptWhat
EntityHas identity that persists through changes (User by Id).
Value ObjectDefined entirely by its attributes (Money, Address). Immutable.
AggregateCluster of entities + VOs that change together. One root entity.
Aggregate RootThe "head" of an aggregate; the only entry point.
RepositoryPersists/loads aggregates. One per aggregate root.
Domain EventSomething that happened in the domain (UserRegistered).
Domain ServiceLogic that doesn't naturally fit in any one entity.

Value object example

public record Money(decimal Amount, string Currency)
{
    public static Money Zero(string currency) => new(0, currency);
    public Money Add(Money other)
    {
        if (Currency != other.Currency) throw new InvalidOperationException();
        return this with { Amount = Amount + other.Amount };
    }
}

Aggregate example

public class Order
{
    private readonly List<OrderLine> _lines = new();
    public int Id { get; private set; }
    public IReadOnlyList<OrderLine> Lines => _lines;
    public Money Total => _lines.Aggregate(Money.Zero("USD"), (s, l) => s.Add(l.SubTotal));

    public void AddLine(Product p, int qty)
    {
        if (Status != OrderStatus.Draft)
            throw new InvalidOperationException("Cannot modify a placed order");
        _lines.Add(new OrderLine(p.Id, p.Price, qty));
    }

    public void Place()
    {
        if (!_lines.Any()) throw new EmptyOrderException();
        Status = OrderStatus.Placed;
    }
}

Note: business rules live inside the aggregate. The repository can only load and save the whole thing — clients can't bypass invariants.

Strategic DDD

  • Bounded Context — explicit boundary where a model has one meaning. "Customer" in Sales is different from "Customer" in Support.
  • Ubiquitous Language — code, docs, conversations all use the same domain terms.
  • Context Map — how bounded contexts relate (shared kernel, customer-supplier, anti-corruption layer).

When to apply DDD

  • Domain is complex (banking, healthcare, logistics).
  • Business rules change frequently and matter for correctness.
  • Team has time to understand the domain deeply.

Don't apply full DDD to a CRUD admin panel — overkill.

CQRS — Command Query Responsibility Segregation

Split write operations (commands) from read operations (queries). Each has its own model. Commands change state and return little; queries are read-only and shaped for the UI.

          ┌─ Commands ──► Handler ──► Domain ──► Write DB
Client ──┤
          └─ Queries ────► Handler ────────────►  Read DB / projections

Why?

  • Reads and writes scale independently.
  • Reads can use denormalized views, joins, or a different DB entirely.
  • Commands stay focused on business rules.

Unit of Work

Coordinates writing to multiple repositories in one transaction.

public interface IUnitOfWork
{
    IUserRepository Users { get; }
    IOrderRepository Orders { get; }
    Task<int> SaveChangesAsync(CancellationToken ct = default);
}

public class EfUnitOfWork : IUnitOfWork
{
    private readonly AppDbContext _db;
    public IUserRepository Users { get; }
    public IOrderRepository Orders { get; }

    public EfUnitOfWork(AppDbContext db,
        IUserRepository users, IOrderRepository orders)
    {
        _db = db; Users = users; Orders = orders;
    }

    public Task<int> SaveChangesAsync(CancellationToken ct = default)
        => _db.SaveChangesAsync(ct);
}
Note: EF Core's DbContext is already a Unit of Work and a Repository. Wrapping it adds a layer that doesn't always pay for itself. Module 61
Interview Questions

Q: Difference between value type and reference type?
Value types (struct, primitives) hold data directly, copied on assignment, usually on the stack. Reference types (class) hold a reference to data on the heap; copying a reference copies the pointer. string is a reference type but behaves like a value due to immutability and value equality.
Q: What are the four pillars of OOP?
Encapsulation, Inheritance, Polymorphism, Abstraction. Encapsulation hides internals; inheritance extends; polymorphism lets the same call behave differently per type; abstraction exposes only what callers need.
Q: Abstract class vs interface — when to use which?
Use abstract class when you want to share state and partial implementation; use interface for pure contracts and when a type needs many capabilities (multi-interface). Modern preference leans toward interfaces for testability.
Q: Explain SOLID briefly.
S — one reason to change. O — extend without editing existing code. L — subtypes must work where the base works. I — small focused interfaces. D — depend on abstractions, not concretes.
Q: What is dependency injection and why?
Passing collaborators to a class instead of having it create them. Decouples consumer from concrete implementation, enables testing with mocks, allows swapping implementations.
Q: Three DI lifetimes in ASP.NET Core?
Singleton (one for app lifetime), Scoped (one per request), Transient (new every time). Mixing lifetimes wrongly (e.g., scoped service injected into singleton) is a classic bug.
Q: How does async/await work?
The compiler rewrites the method into a state machine. await means "if the awaited Task isn't complete, save state and return; resume here when it completes." On I/O the thread is released back to the pool — same hardware serves more concurrent requests.
Q: What's the GC's generational hypothesis?
"Most objects die young." Gen 0 collects new objects (frequent, cheap); survivors promote to Gen 1, then Gen 2 (rare, expensive). LOH for objects ≥ 85 KB.
Q: Difference between IEnumerable and IQueryable?
IEnumerable: in-memory iteration, LINQ runs on objects. IQueryable: expression tree that providers (EF Core) translate (e.g., to SQL). Materializing IQueryable too early forces in-memory work — keep it IQueryable until ToListAsync().
Q: How do you avoid an N+1 query in EF?
Eager-load with Include / ThenInclude, or project to a DTO with Select. Profile with logging or MiniProfiler.
Q: What is middleware?
A pipeline component that handles HTTP requests/responses. Each piece can short-circuit, transform, or pass on. Order matters — auth before authorization, exception handler first, etc.
Q: Cookie vs JWT auth?
Cookie: server-side session, browser auto-sends, susceptible to CSRF. JWT: stateless, sent in Authorization header, easy for APIs/SPAs/mobile, but token revocation is harder (need a blocklist).
Q: What does using do?
Calls Dispose() on the resource at the end of the block, even on exception. Modern using-declarations scope to the enclosing block. await using for IAsyncDisposable.
Q: Difference between throw and throw ex?
throw rethrows preserving the original stack trace. throw ex resets the trace to the rethrow line — almost always wrong.
Q: What is a DTO and why use one?
Data Transfer Object — a shape for moving data across boundaries (API, layers). Decouples your wire format from your domain entities. Lets you evolve internal types without breaking clients.
Q: What's the Repository pattern's tradeoff?
Pro: abstracts persistence, simplifies testing, lets you switch ORMs. Con: EF's DbContext is already a repository + UoW; wrapping it can be redundant. Decide based on your architecture.
Q: Records vs classes?
Records auto-implement value equality, support with expressions for non-destructive mutation, and have concise syntax. Use for DTOs, value objects, immutable data. Classes for entities with identity and behavior.
Q: How do nullable reference types help?
Compiler flow analysis catches potential null dereferences at compile time. string is non-null; string? is nullable. You handle nullability explicitly instead of getting runtime NullReferenceExceptions.
Q: How do you handle transient HTTP failures?
Polly: retry with exponential backoff + jitter, plus circuit breaker for sustained failures, plus timeouts. .NET 8 has AddStandardResilienceHandler for HttpClient.
Q: What's CQRS and when does it help?
Splitting commands (writes) from queries (reads). Helps when reads need different shapes than writes, or when read/write scaling differs. Don't apply universally — adds complexity.
Q: Clean Architecture's main rule?
The Dependency Rule: source dependencies always point inward. Domain has no dependencies on infrastructure. Outer layers (Web, Infra) implement interfaces defined by inner layers (Application).
Q: What is ConfigureAwait(false)?
Tells the await not to capture and resume on the original synchronization context. Important in library code to prevent deadlocks. Not needed in ASP.NET Core (no sync context).
Q: How do you keep secrets out of source control?
User Secrets in dev, environment variables in containers, Azure Key Vault / AWS Secrets Manager / HashiCorp Vault in production. Never commit appsettings.Production.json with real values.
Q: What's the difference between unit and integration tests?
Unit tests isolate a single class with mocks, run in milliseconds. Integration tests exercise multiple components (often including DB and HTTP). Have many unit tests, fewer integration tests.

public class LoggingBehavior<TReq,TRes> : IPipelineBehavior<TReq,TRes>
    where TReq : notnull
{
    private readonly ILogger<LoggingBehavior<TReq,TRes>> _log;
    public LoggingBehavior(ILogger<LoggingBehavior<TReq,TRes>> log) => _log = log;

    public async Task<TRes> Handle(TReq req, RequestHandlerDelegate<TRes> next,
                                   CancellationToken ct)
    {
        var sw = Stopwatch.StartNew();
        var name = typeof(TReq).Name;
        try
        {
            var res = await next();
            _log.LogInformation("{Request} handled in {Ms}ms", name, sw.ElapsedMilliseconds);
            return res;
        }
        catch (Exception ex)
        {
            _log.LogError(ex, "{Request} failed after {Ms}ms", name, sw.ElapsedMilliseconds);
            throw;
        }
    }
}

    public override string ToString() => Value;
    public static implicit operator string(EmailAddress e) => e.Value;

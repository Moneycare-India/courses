Module 1
What & Why of Redis

What is Redis?

Redis ("REmote DIctionary Server") is an open-source, in-memory data structure server. It's not a generic database — it's a server that exposes rich data structures (strings, lists, hashes, sets, sorted sets, streams, bitmaps, geo) over a network protocol.

It was created by Salvatore Sanfilippo in 2009. The license changed in 2024 to a dual-license model (RSALv2 / SSPLv1), which led to a community fork called Valkey (Linux Foundation, BSD-licensed). For learning purposes, Redis and Valkey are essentially identical — pick whichever fits your licensing needs.

Why is it so popular?

  • Sub-millisecond latency — everything is in RAM.
  • Rich data structures — not just key/value; you get atomic operations on lists, sets, sorted sets, etc.
  • Simplicity — single binary, simple text protocol (RESP), small config file.
  • Huge throughput — 100k–1M ops/sec on a single core.
  • Versatile — cache, session store, queue, pub/sub, rate limiter, leaderboard, lock service.
  • Battle-tested — used by Twitter, Stack Overflow, GitHub, Pinterest, Snapchat, and millions of smaller apps.

What problem does Redis solve?

Most apps spend a lot of time fetching small things repeatedly — user sessions, configuration, rate counters, "is this user logged in?" checks. Hitting a SQL database for these is overkill: it costs disk I/O, locks, query parsing, network round-trips. Redis answers in microseconds.

Common use cases

  • Caching — DB query results, API responses, computed values.
  • Session store — replace sticky sessions with shared state.
  • Rate limiting — atomic counters with TTL.
  • Distributed locks — coordinate work across instances.
  • Job queues — using Lists or Streams.
  • Leaderboards — Sorted Sets are made for this.
  • Pub/Sub messaging — light real-time fanout.
  • Real-time analytics — counters, HyperLogLog cardinality estimates.
  • Geo queries — "find restaurants within 5km".
  • Token / OTP storage — short-lived keys with TTL.

Module 2
When (Not) to Use Redis

Redis is a great fit when…

  • You need extremely low latency (<1ms).
  • The dataset fits in RAM (or you're OK with sharding across nodes).
  • You need atomic operations on data structures (counters, sets, lists).
  • You can tolerate eventual durability (or use AOF for stronger durability).
  • You want a simple operational footprint.

Redis is the wrong choice when…

  • Your dataset is far larger than affordable RAM (use a disk-based DB).
  • You need strong ACID transactions across many keys.
  • You need complex queries (joins, full-text search at scale, analytical SQL).
  • You need long-term durable storage with strict guarantees (Redis can lose seconds of data on crash with default settings).
Reality check: Redis is not your primary database. It's a high-speed companion. Always treat Redis data as regenerable from your source of truth (SQL, Kafka, etc.) — even if you enable persistence.

Module 3
The Mental Model

Picture a giant in-memory dictionary on a server you can talk to over TCP. The keys are strings. The values can be one of about a dozen rich types, and Redis exposes operations on those types as commands.

┌────────────────────── Redis (one process) ──────────────────────┐
│                                                                 │
│  Keyspace (database 0):                                         │
│    "user:42"        → Hash    {name: alice, age: 30}            │
│    "leaderboard"    → SortedSet { (alice,500),(bob,300) }       │
│    "queue:emails"   → List     [msg1, msg2, msg3]               │
│    "session:abc..." → String   "...JSON..." (TTL: 30 min)       │
│    "rate:ip:1.2.3"  → String   "127" (TTL: 60s)                 │
│    "tags:42"        → Set      {kafka, redis, devops}           │
│                                                                 │
│  Single-threaded event loop processes one command at a time.    │
│  Persistence (optional): RDB snapshots + AOF log to disk.       │
└─────────────────────────────────────────────────────────────────┘

The crucial things to internalize:

  • Everything fits in RAM. Plan capacity around RAM, not disk.
  • Single-threaded for command execution. Each command is atomic — no other client can interleave inside one command.
  • Operations are O(complexity) per command. Most commands are O(1) or O(log N). Some are O(N) and dangerous on big keys.
  • Keys can have TTL. They auto-delete when expired.

Module 4
Core Vocabulary

Key

A binary-safe string identifying a value. Convention: colon-separated hierarchies — user:42:profile, session:abc-123, rate:ip:10.0.0.1.

Value

One of: String, List, Hash, Set, Sorted Set, Stream, Bitmap, HyperLogLog, Geo (geo is a sorted set with special encoding). Optional modules add JSON, BloomFilter, TimeSeries, Search.

Database (DB)

A logical namespace inside one Redis instance. Numbered 0–15 by default. SELECT 2 switches. Different DBs share the same RAM and process — so they're not real isolation, just a quick partition.

Instance

One redis-server process. Listens on a port (default 6379), serves clients, holds RAM, has its own persistence files.

RESP

REdis Serialization Protocol. Simple text-line protocol over TCP. Easy to debug with telnet. Latest is RESP3.

Pipeline

A way to send many commands without waiting for each reply, drastically cutting round-trip overhead.

Transaction (MULTI/EXEC)

A batch of commands queued and executed atomically. Note: not isolation in the SQL sense — see Module 14.

Lua scripting

You can ship Lua scripts to Redis with EVAL. They run server-side, atomically, in the single thread.

Pub/Sub

Lightweight publish/subscribe channels. Fire-and-forget — no persistence.

Replication

One master, N replicas asynchronously copying writes.

Sentinel

Daemon set that monitors master/replicas and automates failover.

Cluster

Built-in horizontal sharding across multiple Redis nodes.

Module 5
Client-Server Flow

┌────────────┐                              ┌─────────────────────┐
│   Client   │                              │  Redis Server       │
└─────┬──────┘                              └────────┬────────────┘
      │ 1. TCP connect to host:6379                  │
      │ 2. AUTH (if password)                        │
      │ 3. SELECT db (optional)                      │
      │ 4. Send command (RESP encoded)               │
      │      e.g. SET user:42 alice EX 60            │
      │─────────────────────────────────────────────►│
      │                                              │ 5. Parse, execute
      │                                              │    in event loop
      │                                              │    (atomic for
      │                                              │     this command)
      │ 6. Reply (RESP)                              │
      │   "+OK\r\n"                                  │
      │◄─────────────────────────────────────────────│
      │                                              │
      │ 7. Reuse connection for next command         │
      ▼                                              ▼

Key observations:

  • Connections are long-lived. Reuse via a connection pool in your client.
  • Each command is a small request/response. Network round-trip dominates if you don't batch.
  • The pipeline sends N commands, then reads N replies — eliminates per-command latency.

Module 6
Strings

The simplest type. A string can hold any binary data up to 512 MB. Used for cached values, counters, session blobs.

SET name "alice"               # set
GET name                       # → "alice"
SET counter 100
INCR counter                   # → 101  (atomic increment)
INCRBY counter 5               # → 106
DECR counter                   # → 105
APPEND name " smith"           # → "alice smith"
STRLEN name                    # → 11
SET token "xyz" EX 60          # auto-expire in 60s
SET key val NX                 # only if not exists ("Not eXists")
SET key val XX                 # only if exists
GETSET key newval              # set and return old
MGET k1 k2 k3                  # multi-get

Common uses:

  • Cache for expensive computations.
  • Counters (page views, API hits).
  • Distributed flags / feature toggles.
  • OTP storage with TTL.

Module 7
Lists

Doubly linked lists of strings. Push/pop at either end is O(1). Up to ~4 billion elements.

LPUSH queue "job1"               # push to head
RPUSH queue "job2"               # push to tail
LRANGE queue 0 -1                # all elements
LLEN queue                       # length
LPOP queue                       # pop from head
RPOP queue                       # pop from tail
BLPOP queue 5                    # blocking pop, wait up to 5s
LMOVE src dst LEFT RIGHT         # atomic move (good for reliable queue)
LTRIM mylist 0 99                # keep only first 100 elements

Common uses:

  • Producer/consumer queues (with LPUSH + BRPOP).
  • Recent activity feeds (LPUSH + LTRIM).
  • Simple chat history.
Watch out: for reliable queues prefer Streams (Module 12) over Lists. Lists lose messages if a consumer crashes mid-process.

Module 8
Hashes

A hash is a map of field → string value, all under one Redis key. Perfect for representing objects compactly.

HSET user:42 name "alice" age "30" email "a@x.com"
HGET user:42 name                # → "alice"
HGETALL user:42                  # → all fields
HMGET user:42 name age           # multi-field get
HINCRBY user:42 age 1            # → 31  (atomic)
HEXISTS user:42 phone            # → 0
HDEL user:42 email
HLEN user:42                     # → 2

Why use a hash instead of N strings?

  • One key holds many fields → far less memory overhead per "object".
  • Atomic per-field updates (HINCRBY).
  • Small hashes use a compact listpack encoding — < 100 bytes for a small object.

Module 9
Sets

Unordered collections of unique strings. O(1) add/remove/contains.

SADD tags:post:42 "redis" "kafka" "devops"
SMEMBERS tags:post:42            # all members
SISMEMBER tags:post:42 "redis"   # → 1
SCARD tags:post:42               # → 3
SREM tags:post:42 "kafka"

# Set algebra
SADD a 1 2 3
SADD b 2 3 4
SINTER a b                       # intersection → {2,3}
SUNION a b                       # union → {1,2,3,4}
SDIFF  a b                       # difference → {1}

Common uses:

  • Tags / labels.
  • "Who liked this post" → store user IDs.
  • Unique visitors (rough — for precise dedupe over huge sets, use HyperLogLog).
  • Friend graph operations (mutual friends = SINTER).

Module 10
Sorted Sets (ZSET)

The most powerful data structure in Redis. A set where each member has a score (a double). Members are kept ordered by score.

ZADD leaderboard 500 "alice"
ZADD leaderboard 300 "bob"
ZADD leaderboard 750 "carol"

ZRANGE leaderboard 0 -1 WITHSCORES                # ascending
ZREVRANGE leaderboard 0 9 WITHSCORES              # top 10 descending
ZSCORE leaderboard "alice"                        # → 500
ZRANK leaderboard "alice"                         # → 1 (asc)
ZREVRANK leaderboard "alice"                      # → 1 (desc)
ZINCRBY leaderboard 50 "alice"                    # alice now 550
ZRANGEBYSCORE leaderboard 400 600                 # range query
ZREMRANGEBYRANK leaderboard 0 -101                # keep top 100
ZCARD leaderboard                                 # member count

Common uses:

  • Leaderboards (game scores).
  • Priority queues (score = priority).
  • Time-series indexing (score = timestamp).
  • Rate-limited sliding windows (score = timestamp).
  • Geospatial indexes (Redis builds GEO on top of ZSET).

Module 11
Bitmaps, HyperLogLog, Geo

Bitmaps

Strings treated as a bit array. Compact way to track on/off facts per ID.

SETBIT user:active:2026-05-07 42 1     # mark user 42 active today
GETBIT user:active:2026-05-07 42       # → 1
BITCOUNT user:active:2026-05-07        # how many active users
BITOP AND dest k1 k2                   # AND across day-bitmaps

Use case: "daily active users" — 1 bit per user, ~125 KB for 1M users per day.

HyperLogLog

Probabilistic counter for distinct elements. Constant 12 KB regardless of input size, with 0.81% error.

PFADD visitors:2026-05-07 "user-1" "user-2" "user-3"
PFCOUNT visitors:2026-05-07            # ≈ 3
PFMERGE total visitors:2026-05-07 visitors:2026-05-08

Geo

Stored as a Sorted Set with a special geohash score. Range queries by distance.

GEOADD shops 72.8777 19.0760 "shop-mumbai" \
              77.5946 12.9716 "shop-bangalore"
GEODIST shops shop-mumbai shop-bangalore km     # → 837.36
GEOSEARCH shops FROMLONLAT 72.88 19.07 BYRADIUS 100 km

Module 12
Streams

An append-only log similar to Kafka, built into Redis (since 5.0). Records have IDs (auto-generated as ms-seq) and field-value maps. Supports consumer groups, acknowledgements, persistent state.

XADD events * action "login" user "42"           # * = auto-id
XLEN events                                       # length
XRANGE events - +                                 # all
XREAD COUNT 100 STREAMS events 0                  # read from start

# Consumer groups
XGROUP CREATE events processors $ MKSTREAM
XREADGROUP GROUP processors worker-1 COUNT 10 STREAMS events >
XACK events processors 1700000000000-0
XPENDING events processors                        # see unacked

Streams vs Lists: streams have IDs, consumer groups, acknowledgements, persistence. Use streams for reliable async work; lists for simple queues.

Streams vs Kafka: Redis Streams is great for ~100K msg/sec, in-memory, low latency. Kafka scales to millions/sec on disk. Streams is simpler to operate; Kafka is the durable backbone.

Module 13
Modules: JSON, Search, etc.

Redis can be extended with modules. The most popular are part of the "Redis Stack" bundle:

ModuleWhat it adds
RedisJSONNative JSON values. JSON.SET, JSON.GET, JSONPath queries.
RediSearchSecondary indexes, full-text search, vector search.
RedisBloomBloom filters, Cuckoo filters, Top-K, Count-Min Sketch.
RedisTimeSeriesTime-series data with downsampling and retention.
RedisGraph(Discontinued in 2024 — use other graph DBs.)

Quick JSON example:

JSON.SET user:42 $ '{"name":"alice","age":30,"tags":["a","b"]}'
JSON.GET user:42 $.name                           # → "alice"
JSON.ARRAPPEND user:42 $.tags '"c"'

Quick search example:

FT.CREATE idx:users ON JSON PREFIX 1 user: \
   SCHEMA $.name AS name TEXT $.age AS age NUMERIC
FT.SEARCH idx:users "@name:alice"

Module 14
Single-Threaded Engine

Redis runs commands in a single thread (the "main thread"). This is a deliberate design choice:

  • No locks on data structures — atomicity is free.
  • Cache-friendly — the entire keyspace lives near one CPU.
  • Simple to reason about — execution order is the order of arrival.

What about modern CPUs with many cores?

  • Redis 6+ uses I/O threads for reading/writing socket data — but command execution is still serial.
  • To use more cores, run multiple Redis instances on the same machine (each is a process pinned to one core).
  • Or use Redis Cluster to spread keys across nodes.

The big consequence — slow commands hurt everyone

If one client runs KEYS * on a 50M-key keyspace, every other client waits. The SLOWLOG tracks these. Avoid:

  • KEYS * in production — use SCAN instead.
  • SMEMBERS on a huge set.
  • HGETALL on a 1M-field hash.
  • Big LRANGE spans.
  • Long Lua scripts.

Transactions: MULTI/EXEC

MULTI
INCR counter
INCR counter
EXEC

Queues commands then runs them atomically. No rollback if a command errors mid-transaction (Redis is not SQL).

Optimistic locking with WATCH

WATCH balance
val = GET balance
MULTI
SET balance (val - 10)
EXEC                              # nil if balance changed since WATCH

Module 15
Memory & Encoding

Redis automatically picks compact encodings for small data structures, and switches to standard encodings when they grow.

TypeSmall encodingThreshold (default)Big encoding
Stringembstr≤ 44 bytesraw
Hashlistpack≤ 128 fields, each ≤ 64 byteshashtable
Listlistpack (small) / quicklist≤ 128 elementsquicklist
Set (integers)intset≤ 512 integershashtable
Set (strings)listpack≤ 128 elementshashtable
Sorted Setlistpack≤ 128 elementsskiplist+hashtable

Memory overhead per key

Every key has fixed overhead (~50–90 bytes for key metadata + dictionary entry + expire slot). Then add value size.

Rough rules of thumb:

  • 1 million empty/short strings ≈ 80–100 MB.
  • 1 million small hashes (5 fields each) ≈ 200–300 MB.
  • Large blobs: dominated by their actual size.

Inspect memory usage

INFO memory                       # process-wide
MEMORY USAGE user:42              # specific key (in bytes)
MEMORY DOCTOR                     # heuristic advice
MEMORY STATS                      # detailed breakdown
DEBUG OBJECT user:42              # encoding, refcount, etc.

Tips to reduce memory

  • Use Hashes instead of many keys for "objects".
  • Stay under listpack thresholds for small structures.
  • Keep keys short: u:42 beats users:profile:identifier:42 at scale.
  • Use integers as values where possible (cheaper than strings).
  • Enable activedefrag yes to reduce fragmentation.

Module 16
Persistence: RDB & AOF

Redis offers two persistence modes (and a hybrid). They write in the background, so the main thread isn't blocked.

RDB (Redis Database snapshots)

Periodic point-in-time snapshots of the entire dataset to a binary dump.rdb file.

# redis.conf
save 3600 1                       # save if >=1 key changed in 1h
save 300 100                      # or 100 keys in 5m
save 60 10000                     # or 10000 keys in 1m
dbfilename dump.rdb
dir /var/lib/redis

Pros: compact file, fast to restart from, low overhead at runtime.
Cons: between snapshots you can lose minutes of data.

AOF (Append-Only File)

Logs every write command to appendonly.aof. On restart, replays the log.

appendonly yes
appendfsync everysec              # fsync once per second (default)
                                  # always = each command (slow, durable)
                                  # no    = OS decides (fast, lossy)

Pros: at most ~1 sec data loss with everysec.
Cons: bigger file, slower restart on huge AOFs.

Hybrid (recommended)

appendonly yes
aof-use-rdb-preamble yes

The AOF starts with an RDB snapshot, then appends post-snapshot commands. Best of both: fast restart + minimal data loss.

AOF rewrite

Without compaction the AOF grows forever. Redis runs BGREWRITEAOF automatically when the file doubles in size, replacing it with a minimal one that produces the same final state.

What to pick?

  • Pure cache (data is regenerable): no persistence (set save "", AOF off).
  • Important state (sessions, business data): hybrid.
  • Strict durability needed: AOF with appendfsync always (slow).

Module 17
Eviction Policies

When Redis hits maxmemory, it has to drop something. The eviction policy decides what.

PolicyWhat it dropsUse when
noevictionNothing — writes start failingYou don't want silent data loss; not for pure caches
allkeys-lruLeast-recently-used among all keysGeneral-purpose cache
allkeys-lfuLeast-frequently-used among all keysCache where access frequency matters more than recency
allkeys-randomRandom keyUniform access patterns
volatile-lruLRU among keys with TTLMixed: keep TTL-less keys forever
volatile-lfuLFU among keys with TTLSame idea, freq-based
volatile-randomRandom TTL keyRare
volatile-ttlKey with shortest TTLYou want to expire soon-to-die keys first

Set in config:

maxmemory 512mb
maxmemory-policy allkeys-lru
Default is noeviction. If you intend Redis as a cache, change it — otherwise writes will start failing the moment RAM fills up.

Module 18
Expiration & TTL

Any key can have a TTL — it auto-deletes when expired.

SET token "xyz" EX 60               # expire in 60s
SET token "xyz" PX 5000             # expire in 5000 ms
EXPIRE existing_key 30              # set TTL on an existing key
PEXPIRE existing_key 30000          # ms version
EXPIREAT existing_key 1735689600    # Unix timestamp
TTL key                             # → seconds left, -1 if no TTL, -2 if not exists
PTTL key                            # ms version
PERSIST key                         # remove TTL

How does Redis actually delete expired keys?

  1. Lazy expiration: when a key is accessed, if expired, delete it.
  2. Active expiration: every 100ms a sampler picks 20 random keys with TTL; deletes expired ones; if >25% were expired, repeats. Caps at 25% CPU time.

Practical implication: a key with TTL that's never read might stay in RAM for a while past expiry. Generally fine for caches; if you must reclaim memory faster, use shorter active expiration.

Use cases for TTL

  • Sessions (e.g., 30 min).
  • OTPs (5 min).
  • Cached query results (1 min – 1 hour).
  • Rate limiter buckets (1 min).
  • Lock ownership (auto-release if holder crashes).

Module 19
Pub/Sub & Notifications

Pub/Sub

A simple fanout channel. Subscribers receive every message published while subscribed. No persistence — late subscribers miss everything.

# Subscriber
SUBSCRIBE news

# Publisher
PUBLISH news "hello world"

# Pattern matching
PSUBSCRIBE news.*

Use it for: real-time UI updates, cache invalidation broadcasts, light chat.
Don't use it for: reliable messaging, queues — use Streams instead.

Keyspace notifications

Redis can publish events when keys change (set, delete, expire, etc.). Off by default; enable with config:

CONFIG SET notify-keyspace-events "KEA"

# Then subscribe:
PSUBSCRIBE "__keyevent@0__:expired"
PSUBSCRIBE "__keyspace@0__:user:42"

Useful for "do something when this key expires" — but be careful, it's fire-and-forget.

Module 20
Replication

Redis supports asynchronous master → replica replication out of the box.

┌──────────────┐  writes  ┌──────────────┐
│   Client     │─────────►│   Master     │
└──────────────┘          └──────┬───────┘
                                 │ async replication
                  ┌──────────────┼──────────────┐
                  ▼              ▼              ▼
           ┌──────────┐   ┌──────────┐   ┌──────────┐
           │ Replica1 │   │ Replica2 │   │ Replica3 │  (read-only by default)
           └──────────┘   └──────────┘   └──────────┘

How it works

  1. Replica connects to master with REPLICAOF host port.
  2. Master sends a snapshot (RDB) for initial sync.
  3. Replica loads it.
  4. Master streams ongoing writes via a replication backlog.
  5. If a replica drops and reconnects within the backlog window, partial sync resumes; otherwise full resync.

Reads from replicas

Replicas are read-only by default. You can run reads against them to scale read traffic, but reads may be slightly stale (eventual consistency).

Failover

Replication alone doesn't do failover — if master dies, replicas just sit there. Failover automation needs Sentinel (Module 21) or Cluster (Module 22).

Module 21
Sentinel

Sentinel is a separate process that watches a master and its replicas, and orchestrates failover.

      ┌─────────────┐ monitor  ┌──────────┐
      │ Sentinel #1 │─────────►│  Master  │
      ├─────────────┤          └────┬─────┘
      │ Sentinel #2 │               │ replication
      ├─────────────┤          ┌────▼─────┐
      │ Sentinel #3 │──monitor►│ Replica  │
      └─────────────┘          └──────────┘

Responsibilities

  • Monitoring: pings master/replicas and checks if they're up.
  • Notification: alerts admins when something changes.
  • Automatic failover: if master is down per a quorum of Sentinels, promotes a replica.
  • Configuration provider: clients ask Sentinel "who's the master right now?" and reconnect.

Why ≥ 3 Sentinels?

To avoid split-brain — failover needs majority quorum. With 3 Sentinels, 2 must agree.

Minimal sentinel.conf

port 26379
sentinel monitor mymaster 192.168.1.10 6379 2
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 60000

Use Sentinel when you need HA but don't need horizontal sharding. Otherwise, jump to Cluster.

Module 22
Cluster

Redis Cluster is built-in horizontal sharding. Data is split across 16384 hash slots, each owned by one master node.

           Client (cluster-aware)
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
  ┌────────┐  ┌────────┐  ┌────────┐
  │Master A│  │Master B│  │Master C│   slots: 0–5460 / 5461–10922 / 10923–16383
  └───┬────┘  └───┬────┘  └───┬────┘
      │           │           │
  ┌───▼────┐  ┌───▼────┐  ┌───▼────┐
  │ Repl A │  │ Repl B │  │ Repl C │   replication for HA
  └────────┘  └────────┘  └────────┘

How keys are placed

slot = CRC16(key) % 16384. The cluster tells the client which node owns each slot. The client caches the map and goes directly to the right node.

Multi-key operations

Multi-key commands (e.g., MSET, SUNION) only work if all keys hash to the same slot. Use a hash tag in {...} to force colocation:

SET {user:42}:name alice
SET {user:42}:email a@x.com
# Both keys go to the same slot, both can be in one transaction.

When to use Cluster

  • Dataset bigger than one machine's RAM.
  • Need both HA and horizontal write scaling.
  • You're prepared to deal with: hash tags, no SELECT (only DB 0), some commands restricted.

Min size

3 master nodes + 3 replicas (one replica per master). 6 processes total. Smaller setups don't have proper quorum.

Configuration Reference

The default config file is redis.conf. The most common settings:

# Network
bind 0.0.0.0
port 6379
protected-mode yes
tcp-keepalive 300

# General
daemonize no
loglevel notice
logfile ""
databases 16

# Memory
maxmemory 512mb
maxmemory-policy allkeys-lru

# Persistence
save 3600 1
save 300 100
save 60 10000
dbfilename dump.rdb
dir /var/lib/redis
appendonly yes
appendfsync everysec
aof-use-rdb-preamble yes

# Replication
replicaof <masterip> <masterport>     # uncomment on replicas
masterauth somepassword
replica-read-only yes

# Security
requirepass mySecretPassword
# user default on +@read ~cached:* >readonlypass

# Slow log
slowlog-log-slower-than 10000          # microseconds
slowlog-max-len 128

# Latency monitor
latency-monitor-threshold 100

# Cluster (if used)
cluster-enabled yes
cluster-config-file nodes.conf
cluster-node-timeout 15000

Live tweaks without restart:

CONFIG GET maxmemory
CONFIG SET maxmemory 1gb
CONFIG REWRITE                    # persist current runtime config to file

ACL (Access Control Lists, Redis 6+)

Multiple users with fine-grained permissions on commands and keys.

# Allow user "reader" only read commands on cache:* keys

# Allow user "writer" all commands on session:*

Module 29
Performance Tuning

Eliminate round-trips

  • Pipeline when sending many commands.
  • MGET / MSET / HMGET for batch reads/writes.
  • Lua scripts for multi-step atomic operations.

Pipeline example (Python)

# Without pipeline: 10000 round-trips
for i in range(10000): r.set(f'k{i}', i)

# With pipeline: 1 round-trip
with r.pipeline(transaction=False) as p:
    for i in range(10000): p.set(f'k{i}', i)
    p.execute()
# 50–100× faster on the wire.

Avoid O(N) commands on big collections

  • Use SCAN instead of KEYS.
  • Use HSCAN/SSCAN/ZSCAN for cursors over hashes/sets/zsets.
  • Page through large lists with LRANGE k 0 99, LRANGE k 100 199, …

Avoid huge keys

Find them: redis-cli --bigkeys. Split them — partition a 10M-element set into 100 sets of 100k each.

Connection pooling

Establishing TCP per command kills performance. All major clients ship pools; use them.

Persistence trade-offs

  • Pure cache → disable persistence entirely (save "", appendonly no).
  • Need state? → AOF + hybrid mode.
  • Don't run BGSAVE on a tiny-RAM machine — fork copies page tables.

Linux tuning

  • vm.overcommit_memory=1 — required for safe BGSAVE forks.
  • Disable Transparent Huge Pages (echo never > /sys/kernel/mm/transparent_hugepage/enabled).
  • net.core.somaxconn=1024 for high connection rates.

Module 30
Caching Patterns

Cache-aside (lazy loading)

App checks cache first; on miss, loads from DB and populates cache. Most common pattern.

v = redis.get(key)
if v is None:
    v = db.query(key)
    redis.set(key, v, ex=300)
return v

Write-through

App writes to both cache and DB on every update. Cache is always fresh; DB latency added on writes.

Write-behind (write-back)

Write to cache only; an async job flushes to DB. Fast writes, but data loss possible on cache crash.

Read-through

Cache layer (e.g., a sidecar) handles DB load on miss. App only talks to cache.

Cache invalidation

Hardest problem in computer science. Approaches:

  • TTL-based — entries expire automatically. Simplest. Eventual consistency.
  • Explicit DEL on write — invalidate the key when DB changes.
  • Pub/Sub broadcast — other instances flush their local caches.
  • Versioned keys — change the key prefix to invalidate everything (e.g., cache:v3:*).

Stampede / dogpile protection

When a hot key expires, every concurrent request rebuilds it. Mitigations:

  • Probabilistic early refresh — refresh before expiry, randomly.
  • Lock around rebuild — use SET NX as a mutex.
  • Stale-while-revalidate — serve stale, refresh in background.

Module 31
Distributed Locking

Simple lock with SET NX

# Acquire
SET lock:resource:42 myUuid NX EX 30

# Release (must check ownership!)
EVAL "if redis.call('GET',KEYS[1])==ARGV[1] then
        return redis.call('DEL',KEYS[1])
      else return 0 end" 1 lock:resource:42 myUuid

Why the Lua script? To make GET-and-DEL atomic. Without it, you might delete someone else's lock.

Redlock (multi-master)

For higher safety guarantees, Redlock acquires the lock on a majority of N independent Redis masters. Most language clients have a Redlock implementation. Trade-off: more complex, debated correctness under clock drift — many use single-master locks for practical workloads.

What can go wrong

  • Lock holder GC pause — a process holding a lock pauses, lock expires, two holders. Mitigate with fencing tokens.
  • Network partition — split-brain. Redlock helps but is debated.
Practical advice: for non-critical coordination (cache rebuilds, scheduled jobs), single-Redis SET NX with TTL is fine. For correctness-critical work (financial), use a real consensus system (etcd, ZooKeeper).

Module 32
Rate Limiting

Fixed window counter

key = f"rate:{user}:{minute}"
n = redis.incr(key)
if n == 1: redis.expire(key, 60)
if n > 100: deny()

Simple, but suffers from "burst at boundary" (200 requests in 2 seconds spanning the minute mark).

Sliding window with sorted set

# Lua to keep it atomic
EVAL "
  local now = tonumber(ARGV[1])
  local window = tonumber(ARGV[2])
  redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, now - window)
  local count = redis.call('ZCARD', KEYS[1])
  if count < tonumber(ARGV[3]) then
    redis.call('ZADD', KEYS[1], now, now)
    redis.call('EXPIRE', KEYS[1], math.ceil(window/1000))
    return 1
  else return 0 end
" 1 "rate:user:42" 1700000000000 60000 100

Token bucket

Tokens added at a fixed rate; each request consumes one. Allows bursts up to bucket capacity. Implementable in Redis with a hash + Lua.

AOF (Append-Only File)
Persistence log of every write command, replayed on restart.
BGSAVE
Background RDB snapshot — fork + write to disk without blocking.

Built-in horizontal sharding across multiple Redis nodes (16384 hash slots).

Dropping keys when memory is full, governed by maxmemory-policy.

One of 16384 buckets keys map to in a cluster, via CRC16(key) % 16384.

The substring in {...} in a key, used to force colocation in cluster.

Probabilistic distinct-count structure (12 KB, 0.81% error).

The set of all keys in one database.

Key expiry checked at access time.

Hard cap on memory; triggers eviction when reached.

Sending multiple commands without waiting for individual replies.

Periodic binary snapshot file (dump.rdb).

Redis serialization protocol — simple text-line wire format.
Replica
Asynchronous read-only copy of a master.

Daemon process that monitors and fails over master/replicas.

Internal log of commands slower than a threshold.

Append-only log type with consumer groups, akin to Kafka.

Time-to-live in seconds; auto-deletes key on expiry.

Linux Foundation BSD-licensed fork of Redis 7.2.

Optimistic locking primitive paired with MULTI/EXEC.

Module 40
Interview Questions

Q: Why is Redis fast?
It's in-memory (no disk in hot path), single-threaded for command execution (no locks), uses simple data structures with O(1)/O(log N) ops, and amortizes I/O via batching/pipelining and the RESP protocol.
Q: How does Redis keep data after a crash?
Two persistence options: RDB (periodic snapshots) and AOF (append-only log). Hybrid mode combines them — best of both.
Q: What's the difference between Redis and Memcached?
Memcached is multi-threaded but only does string K/V, no persistence, no replication. Redis adds rich data structures, persistence, replication, cluster, scripting.
Q: When would you use Sorted Sets?
Anywhere you need ordering by a numeric score: leaderboards, priority queues, time-indexed events, sliding-window rate limiters, geospatial indexes.
Q: Explain Redis Cluster vs Sentinel.
Sentinel = HA only: monitors a master and replicas, fails over automatically. Cluster = HA + horizontal sharding via 16384 hash slots distributed across master nodes (each with its own replicas).
Q: What happens when Redis runs out of memory?
Depends on maxmemory-policy. Default noeviction — writes start failing. allkeys-lru — evicts least-recently-used keys. Eight policies total.
Q: How do you safely scan all keys?
Never use KEYS * in production — it blocks. Use SCAN cursor MATCH pattern COUNT n to iterate non-blocking in chunks.
Q: What is a hash slot?
A bucket in Redis Cluster. Keys hash to one of 16384 slots via CRC16. Each slot belongs to one master. Distributes keys across nodes.
Q: How do you do an atomic counter increment?
INCR or INCRBY. Single command, atomic by design.
Q: Difference between DEL and UNLINK?
DEL deletes synchronously — for big keys this blocks. UNLINK removes the key from the keyspace immediately and frees memory in a background thread.
Q: How does Redis pub/sub differ from streams?
Pub/Sub is fire-and-forget — no persistence, no acks, late subscribers miss everything. Streams are durable append-only logs with consumer groups, acknowledgements, and pending lists.
Q: Can Redis transactions roll back on error?
No. Inside MULTI/EXEC, if a command errors at execution, others still run. Redis only aborts the whole transaction if a command fails to queue (syntax error). For consistency use Lua scripts (atomic) or WATCH-based optimistic locking.
Q: How is replication consistency? Strong or eventual?
Eventual. Master writes async to replicas. After a master crash, a few in-flight writes may be lost when a replica is promoted.
Q: What's a hot key and how do you handle it?
A single key getting disproportionate traffic; in cluster mode it overloads one node. Shard logically (e.g., counter:0..N), use local in-process caching with short TTL, or cache the result client-side.
Q: How do you make Redis durable enough for important data?
Hybrid persistence (AOF + RDB preamble) with appendfsync everysec for ~1s data loss bound, plus replication, plus a backup of the AOF/RDB to S3 or similar. For stricter, appendfsync always but expect a throughput hit.

Memory Sizing & Capacity

How much can Redis store?

Redis can address up to (2^63)−1 bytes of memory — effectively unlimited from a software perspective. The real limit is your machine's RAM (or RAM × number of nodes in Cluster mode). The largest production single Redis instances in the wild run with hundreds of GB of RAM. Beyond that, shard with Cluster.

Per-key memory math

ItemApprox bytesNotes
Empty key entry overhead~50–90Dictionary entry + key string + expire slot
Short string value (≤44 bytes)value size + ~16embstr encoding
Long string valuevalue size + ~56raw encoding
Hash with 5 small fields~150–250listpack — extremely compact
Sorted set member~80–100skiplist + dict
List element~50–80quicklist
Set member (string)~70–100hashtable

Worked estimates for EasyAudit

redis-central — sessions, OTP, JWT blocklist
  • Active sessions: assume 10,000 concurrent users × ~500 bytes (hash with user_id, csrf, role, etc.) = 5 MB
  • JWT blocklist: 50,000 revoked tokens × ~120 bytes = 6 MB
  • OTP keys: 1,000 in-flight × ~150 bytes = 0.15 MB
  • Refresh-token allowlist: 20,000 × 200 bytes = 4 MB
  • Total: ~15 MB working set — 256 MB allocation is plenty, leaving room for spikes.

Recommendation: maxmemory 256mb, volatile-ttl eviction, AOF on.

redis-accounting — report & aggregate cache
  • Cached report responses: 5,000 × ~50 KB JSON = 250 MB
  • Computed aggregates (balance sheet snapshots): 2,000 × ~10 KB = 20 MB
  • Lookup caches (chart of accounts, currencies): ~10 MB
  • Total: ~280 MB peak

Recommendation: maxmemory 512mb-1gb (give headroom; reports vary), allkeys-lru, no persistence.

redis-task — locks, queues, task state
  • Active distributed locks: 1,000 × ~200 bytes = 0.2 MB
  • Pending task queue (List or Stream): 10,000 × ~2 KB = 20 MB
  • In-progress task state (hashes): 500 × ~5 KB = 2.5 MB
  • Cron job locks & markers: trivial
  • Total: ~25 MB working set

Recommendation: maxmemory 256mb, volatile-ttl, AOF on.

redis-hub — caching
  • Pure cache, depends on usage. Start with maxmemory 256mb, allkeys-lru, no persistence. Watch evicted_keys in INFO; bump if eviction rate is high.
redis-notification — rate limits, idempotency
  • Per-user/IP rate counters: 100,000 buckets × ~150 bytes = 15 MB
  • Idempotency key registry (Kafka message dedup): 7-day window × ~1 M msg × 100 bytes = ~100 MB
  • Template render cache: ~10 MB
  • Total: ~125 MB

Recommendation: maxmemory 256mb, volatile-lru, AOF on.

redis-logging — counters & recent buffer
  • Per-service / per-level counters: trivial (~1 MB).
  • Recent log ring buffer (List, capped via LTRIM): 50 services × 1,000 lines × 500 bytes = ~25 MB
  • Top-N error sketches: ~5 MB
  • Total: ~30 MB

Recommendation: maxmemory 256mb, allkeys-lru, no persistence.

InstanceSuggested maxmemoryHeadroom for fragmentation/RSS

Plan for 1.4× headroom: Redis RSS (resident set size) is typically 1.2–1.5× the configured maxmemory due to fragmentation, fork-on-save, replication buffers, client buffers. Always size the host generously above the sum of maxmemory values.

How to know when to grow

Watch these per instance:

  • used_memory approaching maxmemory → bump maxmemory.
  • evicted_keys rising fast → cache is too small.
  • mem_fragmentation_ratio > 1.5 sustained → enable activedefrag or restart.
  • keyspace_misses / keyspace_hits ratio rising → cache hit rate falling.

When to move from separate-instances to Cluster

If any single instance grows past ~30–50 GB or exceeds one core's CPU capacity (~100k ops/sec sustained), shard that instance via Redis Cluster. For EasyAudit at typical SMB scale, a single instance per backend on a beefy VM is the sweet spot.

Concrete usage examples

central-backend: OTP storage

public class OtpStore
{
    private readonly IDatabase _db;
    public OtpStore(IConnectionMultiplexer mux) => _db = mux.GetDatabase();

    public Task SaveOtpAsync(string userId, string otpHash) =>
        _db.StringSetAsync($"otp:login:{userId}", otpHash, TimeSpan.FromMinutes(5));

    public async Task<string?> PopOtpAsync(string userId)
    {
        var key = $"otp:login:{userId}";
        var v = await _db.StringGetAsync(key);
        if (v.HasValue) await _db.KeyDeleteAsync(key);
        return v;
    }
}

central-backend: JWT blocklist on logout

public Task RevokeAsync(string jti, DateTime expUtc) =>
    _db.StringSetAsync($"jwt:revoked:{jti}", "1", expUtc - DateTime.UtcNow);

public Task<bool> IsRevokedAsync(string jti) =>
    _db.KeyExistsAsync($"jwt:revoked:{jti}");

task-backend: distributed lock via SET NX EX

public async Task<bool> TryAcquireLockAsync(string resource, string ownerId, TimeSpan ttl)
{
    return await _db.StringSetAsync(
        $"lock:{resource}", ownerId, ttl, When.NotExists);
}

public async Task ReleaseLockAsync(string resource, string ownerId)
{
    const string lua = @"
        if redis.call('GET',KEYS[1])==ARGV[1] then
            return redis.call('DEL',KEYS[1])
        else return 0 end";
    await _db.ScriptEvaluateAsync(lua,
        new RedisKey[] { $"lock:{resource}" },
        new RedisValue[] { ownerId });
}

accounting-backend: cache-aside for reports

public async Task<ReportDto> GetReportAsync(int reportId)
{
    var key = $"report:{reportId}";
    var cached = await _db.StringGetAsync(key);
    if (cached.HasValue)
        return JsonSerializer.Deserialize<ReportDto>(cached!)!;

    var fresh = await _reportService.ComputeReportAsync(reportId);
    await _db.StringSetAsync(key, JsonSerializer.Serialize(fresh),
        TimeSpan.FromMinutes(15));
    return fresh;
}

notification-backend: rate limiter (sliding window)

public async Task<bool> AllowAsync(string user, int maxPerMinute)
{
    var key = $"rate:notif:{user}";
    var now = DateTimeOffset.UtcNow.ToUnixTimeMilliseconds();
    var windowStart = now - 60_000;

    var tx = _db.CreateTransaction();
    _ = tx.SortedSetRemoveRangeByScoreAsync(key, 0, windowStart);
    var countTask = tx.SortedSetLengthAsync(key);
    _ = tx.SortedSetAddAsync(key, now.ToString(), now);
    _ = tx.KeyExpireAsync(key, TimeSpan.FromMinutes(2));
    await tx.ExecuteAsync();

    return await countTask < maxPerMinute;
}

notification-backend: idempotency check for Kafka

public async Task<bool> TryClaimIdempotencyAsync(string messageId, TimeSpan ttl)
{
    // Returns true if this is the first time we've seen this messageId.
    return await _db.StringSetAsync(
        $"idem:{messageId}", "1", ttl, When.NotExists);
}

Module 44 — Project
Operations Plan

Backups

  • For instances with persistence (central, task, notification): nightly BGSAVE, copy dump.rdb + appendonly.aof to S3-compatible storage.
  • Pure caches (accounting, hub, logging): no backup needed; data is regenerable.

Monitoring per instance

Run a redis_exporter per Redis instance, scrape from Prometheus, dashboard in Grafana. Track:

  • used_memory vs maxmemory (alert at 80%)
  • evicted_keys rate
  • keyspace_hits / (keyspace_hits + keyspace_misses) — hit rate
  • connected_clients
  • instantaneous_ops_per_sec
  • Slow log entries

Connection limits

Default maxclients is 10000. With 6 instances and several backends each opening pools, you're fine. Watch connected_clients in INFO; bump if needed.

Failure isolation in action

The win of separate instances: if redis-accounting crashes mid-day:

  • Reports become slow (cache miss → DB), but auth/login, tasks, notifications all keep working.
  • Restart redis-accounting; cache warms up over a few minutes.
  • If it had been one shared Redis, all backends would have stalled.

Going to HA later

When the project demands ≤30s of failover for critical instances:

  1. Add a replica per critical instance (central, task, notification).
  2. Add 3 Sentinels watching them.
  3. Switch .NET clients to use the Sentinel-aware connection string format.

Going to managed Redis later

If/when you move to Azure or AWS, swap each docker instance for an equivalent managed cache:

  • Azure Cache for Redis — Basic/Standard/Premium tiers.
  • AWS ElastiCache (Redis) — Cluster mode disabled is the default, fine for these workloads.

Connection strings change; everything else stays the same.

Security checklist

  • Different passwords per instance (already in compose).
  • Bind to private network only — never expose 6379–6384 publicly.
  • Enable TLS for cross-host communication.
  • Use ACL users in Redis 6+ — give each backend a least-privilege user.
  • Rotate passwords periodically; secrets in environment variables, not config files.
  • Disable dangerous commands in shared envs: rename-command FLUSHALL "".

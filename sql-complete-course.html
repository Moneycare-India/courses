Module 1
What is SQL & Why It Still Wins

What is SQL?

SQL (Structured Query Language) is the standard language for talking to relational databases. You declare what data you want; the database engine figures out how to get it.

SQL has been around since the 1970s, was standardized as ANSI SQL in 1986, and is the most widely-used data language on the planet — every big system, from your bank to your phone, has SQL inside somewhere.

What's a relational database?

Data organized into tables (rows + columns), with relationships between tables expressed via shared keys. Think Excel spreadsheets that know about each other.

  └────┴───────┴───────────┘    └────┴─────────┴────────┴────────┘

Why SQL is still the default after 50 years

  • Declarative. You say what, not how. The query optimizer picks the best execution path.
  • ACID transactions. Atomic multi-row updates. Critical for money, audits, anything correctness-sensitive.
  • Relational model. Joins make connecting data trivial.
  • Mature tooling. 50 years of optimizers, monitoring, replication, backups.
  • Standard. Skills transfer between databases (with quirks).
  • Constraints at the DB level. Foreign keys, NOT NULL, CHECK enforce data quality regardless of which app writes.
  • Universally understood. Every BI tool, every analyst, every backend speaks SQL.

The five things you'll do over and over

  1. Query data — SELECT.
  2. Add data — INSERT.
  3. Modify data — UPDATE.
  4. Remove data — DELETE.
  5. Define schema — CREATE / ALTER / DROP.

Plus the architectural skills: indexing, transactions, stored procs, security. This course covers all of it.

This course's focus

Examples are in T-SQL (SQL Server flavor) since that's what your EasyAudit stack uses. Where syntax differs meaningfully in Postgres / MySQL, you'll see a PG / MySQL note. The concepts transfer; the syntax is 95% the same.

Database Design Basics

The three layers

LayerWhat it is
Conceptual modelBusiness entities and how they relate (drawn on a whiteboard)
Logical modelTables, columns, keys, relationships (no DB-specific stuff yet)
Physical modelActual schema in a specific DB — data types, indexes, partitions

Anatomy of a table

CREATE TABLE users (
    id          INT IDENTITY(1,1) PRIMARY KEY,
    email       NVARCHAR(255) NOT NULL UNIQUE,
    name        NVARCHAR(100) NOT NULL,
    age         INT NULL,
    is_active   BIT NOT NULL DEFAULT 1,
    created_at  DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME()
);

Each component:

  • id INT IDENTITY(1,1) — auto-incrementing integer.
  • PRIMARY KEY — unique row identifier; cannot be NULL.
  • NVARCHAR(255) — Unicode string up to 255 chars.
  • NOT NULL — column must have a value.
  • UNIQUE — values must be unique across rows.
  • DEFAULT — value used when not specified on INSERT.

Relationships — the relational part

TypeExampleImplementation
One-to-oneUser ↔ UserSettingsFK with UNIQUE constraint
One-to-manyUser → OrdersFK in the "many" side (orders.user_id)
Many-to-manyUsers ↔ RolesJunction table with two FKs (user_roles)

Foreign keys

CREATE TABLE orders (
    id        INT IDENTITY(1,1) PRIMARY KEY,
    user_id   INT NOT NULL,
    amount    DECIMAL(10, 2) NOT NULL,
    status    NVARCHAR(20) NOT NULL,
    CONSTRAINT FK_orders_user FOREIGN KEY (user_id) REFERENCES users(id)
);

The FK guarantees at the DB level that user_id always points to a real user. Application bugs can't corrupt this — the DB rejects bad inserts.

Naming conventions

Pick one and stick with it:

  • snake_case for tables and columns: users, created_at, user_orders. Most common.
  • PascalCase: Users, CreatedAt. Common in SQL Server / .NET shops.
  • Pluralize tables (users) or singular (user). Pick one. Plural is more common.
  • FK columns: <referenced_table_singular>_id → user_id, order_id.
  • Index names: IX_table_columns → IX_users_email.
  • Constraint names: PK_table, FK_table_referenced, CK_table_column.

The audit columns every table should have

created_at  DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME()
created_by  NVARCHAR(100) NULL
updated_at  DATETIME2 NULL
updated_by  NVARCHAR(100) NULL
is_deleted  BIT NOT NULL DEFAULT 0    -- soft delete
row_version ROWVERSION                -- optimistic concurrency

You won't always need them, but most enterprise apps do.

  • Use the smallest type that fits the data — saves storage AND speeds queries (more rows per page).

  • Don't use NVARCHAR(255) "just in case" if you know names fit in 100 chars. Right-size.
  • Always use NVARCHAR (not VARCHAR) for Unicode safety; the storage difference is small with modern compression.

Module 4
NULL Handling

What NULL is (and isn't)

NULL means "unknown" or "not applicable". It is NOT zero, empty string, or false. It's the absence of a value.

The three-valued logic

Most predicates evaluate to TRUE, FALSE, or UNKNOWN. NULL = NULL is UNKNOWN, not TRUE.

ExpressionResult
NULL = NULLUNKNOWN (not TRUE!)
NULL = 5UNKNOWN
NULL <> 5UNKNOWN
NULL + 5NULL
NULL IS NULLTRUE
NULL IS NOT NULLFALSE

The trap that bites everyone

SELECT * FROM users WHERE age <> 30;

This excludes users with NULL age! Because NULL <> 30 is UNKNOWN, not TRUE.

Fix:

SELECT * FROM users WHERE age <> 30 OR age IS NULL;

NULL handling functions

FunctionWhat it does
ISNULL(col, 0)Returns 0 if col is NULL (SQL Server)
COALESCE(a, b, c, 0)Returns first non-NULL — standard SQL, prefer this
NULLIF(a, b)Returns NULL if a = b, else a — useful for "treat 0 as NULL"
IS [NOT] NULLTest for NULL — never use = NULL

Aggregations and NULLs

  • COUNT(*) counts rows including NULL.
  • COUNT(column) counts non-NULL values only.
  • SUM, AVG, MAX, MIN ignore NULL.
  • AVG(col) = sum / count of non-NULL — beware if NULL ≠ "unknown" semantically.

Should I allow NULL?

Default to NOT NULL. Only allow NULL when "no value" has a meaningful business interpretation. Examples:

  • NULL OK: middle_name, deleted_at (means "not deleted"), parent_id (root nodes), completed_at (means "in progress").
  • NULL bad: email, created_at, order_total, anything required for the row to make sense.

Empty string vs NULL

Different things. '' is "empty value provided"; NULL is "no value provided". Pick one and be consistent. Many teams pick: never store empty strings, use NULL.

Standard SQL vs vendor extensions

The ANSI SQL standard defines a common subset. Anything beyond is vendor-specific. Examples:

  • CTEs (WITH ...) — standard, works everywhere.
  • Window functions — standard.
  • JSON path queries — vendor-specific syntax.
  • Stored procedures — completely different per vendor.
  • Recursive CTEs — standard but slight syntax variations.

Practical rule

Stick to ANSI SQL when you can; reach for vendor features when needed. Keep a list of vendor-specific things you use, in case you ever migrate.

Module 7
SELECT, FROM, WHERE

The shape of every query

SELECT  <columns>
FROM    <tables>
WHERE   <row filter>
GROUP BY <columns>
HAVING  <group filter>
ORDER BY <columns>;

Logical execution order (different from written order!):

  1. FROM — pick the tables.
  2. WHERE — filter rows.
  3. GROUP BY — group rows.
  4. HAVING — filter groups.
  5. SELECT — pick columns / compute expressions.
  6. ORDER BY — sort.
  7. LIMIT / OFFSET / TOP — restrict results.

Knowing this order explains things like "why can't I use my SELECT alias in WHERE?" — because WHERE runs before SELECT.

Basic SELECT

-- Everything (don't do this in production)
SELECT * FROM users;

-- Specific columns
SELECT id, name, email FROM users;

-- Computed column with alias
SELECT
    name,
    UPPER(email) AS upper_email,
    DATEDIFF(YEAR, dob, GETDATE()) AS age_years
FROM users;

-- Distinct values
SELECT DISTINCT country FROM users;

-- Distinct combinations
SELECT DISTINCT country, city FROM users;

WHERE — filtering

SELECT * FROM users WHERE country = 'IN';
SELECT * FROM users WHERE age >= 18;
SELECT * FROM users WHERE created_at >= '2026-01-01';
SELECT * FROM users WHERE name LIKE 'A%';
SELECT * FROM users WHERE country IN ('IN', 'US', 'UK');
SELECT * FROM users WHERE age BETWEEN 18 AND 65;
SELECT * FROM users WHERE deleted_at IS NULL;
SELECT * FROM orders WHERE amount > 1000 AND status = 'paid';

SELECT * is an antipattern

In production code, never. Reasons:

  • Fetches columns you don't need — wastes bandwidth and memory.
  • Schema changes break consumers (new column appears in unexpected position).
  • Prevents index-only scans (covering indexes don't cover *).
  • Causes implicit joins to load entire wide rows.

Always list the columns you actually use.

Aliases

-- Column alias
SELECT name AS user_name FROM users;
SELECT name user_name FROM users;     -- AS is optional
SELECT name [User Name] FROM users;   -- bracketed when alias has spaces (T-SQL)

-- Table alias
SELECT u.name, u.email
FROM users AS u
WHERE u.country = 'IN';

Always alias your tables in queries with joins or subqueries — much more readable.

Comments

-- single-line comment

/* multi-line
   comment */

Module 8
ORDER BY, TOP/LIMIT, OFFSET

Sorting

SELECT * FROM users
ORDER BY created_at DESC;        -- newest first

SELECT * FROM users
ORDER BY country ASC, name DESC; -- by country, then name desc

SELECT * FROM users
ORDER BY 2;                       -- by 2nd column in SELECT — works but fragile

NULL ordering

By default, SQL Server treats NULL as the smallest value (NULLs first ASC, last DESC). Postgres opposite.

-- Force NULLs to the end
ORDER BY age DESC                       -- SQL Server: NULLs last automatically
ORDER BY age NULLS LAST                 -- Postgres
ORDER BY CASE WHEN age IS NULL THEN 1 ELSE 0 END, age DESC;  -- Portable

TOP and LIMIT

-- T-SQL
SELECT TOP 10 * FROM users ORDER BY created_at DESC;
SELECT TOP 10 PERCENT * FROM users;

-- Standard / Postgres / MySQL
SELECT * FROM users ORDER BY created_at DESC LIMIT 10;

OFFSET — pagination basics

-- T-SQL (must have ORDER BY)
SELECT * FROM users
ORDER BY id
OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY;

-- Standard / Postgres / MySQL
SELECT * FROM users
ORDER BY id
LIMIT 10 OFFSET 20;
OFFSET is slow for large pages. The DB must scan and discard OFFSET rows. Page 1000 with 100 per page = scan 100,000 rows just to throw them away. See Module 45 for keyset pagination.

The "ORDER BY is required for OFFSET" rule

SQL doesn't guarantee row order without ORDER BY — even on the same query, results could come back differently. Always specify ORDER BY for paginated/limited results.

Ordering by multiple columns with directions

SELECT * FROM products
ORDER BY category ASC, price DESC, name ASC;

Ordering by an expression

-- Sort by month name in correct order using a CASE
SELECT month_name FROM months
ORDER BY CASE month_name
  WHEN 'Jan' THEN 1 WHEN 'Feb' THEN 2 WHEN 'Mar' THEN 3
  -- ... etc
END;

-- Or sort by length
SELECT name FROM users ORDER BY LEN(name) DESC;

Logical operators

SELECT * FROM users
WHERE country = 'IN'
  AND (age >= 18 OR is_verified = 1)
  AND NOT is_banned = 1;

Operator precedence: NOT > AND > OR. Use parentheses when in doubt.

The IN/NOT IN NULL gotcha

-- Bad: NOT IN with a list containing NULL never returns rows
SELECT * FROM users WHERE id NOT IN (SELECT user_id FROM orders);
-- If any user_id is NULL, this returns NOTHING.

-- Good: use NOT EXISTS
SELECT * FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);

BETWEEN gotcha

BETWEEN '2026-01-01' AND '2026-01-31' includes Jan 31 at midnight. Anything during Jan 31 day is excluded.

-- Wrong (misses everything Jan 31)
WHERE created_at BETWEEN '2026-01-01' AND '2026-01-31'

-- Right
WHERE created_at >= '2026-01-01' AND created_at < '2026-02-01'

Predicate vs expression

A predicate evaluates to true/false/unknown. An expression evaluates to a value. age >= 18 is a predicate; age + 5 is an expression.

Module 10
LIKE & Pattern Matching

Wildcards in LIKE

WildcardMatches
%Any sequence of characters (including none)
_Exactly one character
[abc]Any single character in set (T-SQL)
[^abc]Any single character NOT in set (T-SQL)
 
SELECT * FROM users WHERE name LIKE 'A%';        -- starts with A
SELECT * FROM users WHERE name LIKE '%son';      -- ends with 'son'
SELECT * FROM users WHERE name LIKE '%john%';    -- contains 'john'
SELECT * FROM users WHERE name LIKE 'J_n';       -- 3 chars: J, anything, n
SELECT * FROM users WHERE name LIKE 'J[ao]n';    -- 'Jan' or 'Jon'

Performance — the leading wildcard problem

Slow — leading wildcard

WHERE name LIKE '%alice%'
-- Cannot use index on name; full table scan

Fast — anchored at start

WHERE name LIKE 'alice%'
-- Index seek on name works

If you need full-text search (matching anywhere), use a real full-text index (Module 66) or Elasticsearch.

Case sensitivity

SQL Server's default collation is case-insensitive — 'Alice' = 'ALICE'. Postgres is case-sensitive by default. Use ILIKE in Postgres for case-insensitive, or LOWER() on both sides:

WHERE LOWER(name) = LOWER('alice')

But — wrapping a column in a function defeats indexes. For case-insensitive lookups, store a normalized lowercase column or use a case-insensitive collation.

Escape special characters

-- Search for literal '%'
WHERE description LIKE '%50\%%' ESCAPE '\'

Regular expressions

  • SQL Server — no native regex; use LIKE patterns or CLR functions.
  • Postgres — ~ (match), ~* (case-insensitive), !~ (not match).
  • MySQL — REGEXP / RLIKE.

Module 11
CASE Expressions

CASE is SQL's if-then-else. Two forms — both useful.

Searched CASE

SELECT
    name,
    CASE
        WHEN age < 18 THEN 'Minor'
        WHEN age < 65 THEN 'Adult'
        ELSE 'Senior'
    END AS age_group
FROM users;

Simple CASE

SELECT
    name,
    CASE country
        WHEN 'IN' THEN 'India'
        WHEN 'US' THEN 'United States'
        WHEN 'UK' THEN 'United Kingdom'
        ELSE country
    END AS country_name
FROM users;

CASE in aggregations — counting conditionally

SELECT
    country,
    COUNT(*) AS total,
    COUNT(CASE WHEN age >= 18 THEN 1 END) AS adults,
    SUM(CASE WHEN is_active = 1 THEN 1 ELSE 0 END) AS active_count,
    AVG(CASE WHEN age >= 18 THEN age END) AS avg_adult_age
FROM users
GROUP BY country;

Trick: COUNT(CASE WHEN ... THEN 1 END) counts only rows matching the condition (because COUNT ignores NULL).

CASE in ORDER BY

-- Custom sort: pending first, then paid, then anything else
SELECT * FROM orders
ORDER BY
    CASE status
        WHEN 'pending' THEN 1
        WHEN 'paid' THEN 2
        ELSE 3
    END,
    created_at DESC;

CASE in UPDATE

UPDATE users
SET status = CASE
    WHEN last_login < DATEADD(YEAR, -1, GETDATE()) THEN 'inactive'
    WHEN last_login < DATEADD(MONTH, -1, GETDATE()) THEN 'dormant'
    ELSE 'active'
END;

IIF (T-SQL only) — shorthand

SELECT IIF(age >= 18, 'Adult', 'Minor') FROM users;
-- Equivalent to: CASE WHEN age >= 18 THEN 'Adult' ELSE 'Minor' END

COALESCE — pick first non-NULL

SELECT COALESCE(nickname, name, email, 'Anonymous') AS display_name FROM users;
-- Returns nickname if not NULL; else name; else email; else 'Anonymous'.

Module 12
Date Functions

Getting current date/time

SELECT GETDATE();          -- T-SQL: server local time
SELECT SYSUTCDATETIME();   -- T-SQL: UTC, recommended
SELECT CURRENT_TIMESTAMP;  -- ANSI standard
-- Postgres: NOW(), CURRENT_TIMESTAMP
-- MySQL: NOW(), UTC_TIMESTAMP()

Date parts

SELECT YEAR(created_at), MONTH(created_at), DAY(created_at) FROM orders;
SELECT DATEPART(WEEKDAY, created_at) FROM orders;        -- 1=Sunday by default
SELECT DATEPART(QUARTER, created_at) FROM orders;
SELECT DATEPART(WEEK, created_at) FROM orders;
SELECT DATENAME(MONTH, created_at) FROM orders;          -- 'October'

Adding / subtracting

SELECT DATEADD(DAY, 7, GETDATE());          -- 7 days from now
SELECT DATEADD(MONTH, -1, GETDATE());        -- 1 month ago
SELECT DATEADD(HOUR, 2, GETDATE());
SELECT DATEADD(YEAR, 1, '2026-02-29');       -- valid: gives 2027-02-28

Difference between dates

SELECT DATEDIFF(DAY, '2026-01-01', '2026-04-15');     -- 104 days
SELECT DATEDIFF(YEAR, dob, GETDATE()) AS age FROM users;   -- crude age

Note: DATEDIFF(YEAR, ...) gives the number of year boundaries crossed, NOT exact age. For exact age, more math needed.

Truncating to a day / month / year

-- T-SQL
SELECT CAST(GETDATE() AS DATE);            -- strip time
SELECT DATEFROMPARTS(YEAR(GETDATE()), MONTH(GETDATE()), 1);   -- first of month
SELECT DATETRUNC(MONTH, GETDATE());        -- SQL Server 2022+

-- Postgres
SELECT DATE_TRUNC('month', NOW());

Formatting dates

SELECT FORMAT(GETDATE(), 'yyyy-MM-dd');       -- '2026-05-07'
SELECT FORMAT(GETDATE(), 'yyyy-MM-dd HH:mm:ss');
SELECT CONVERT(VARCHAR, GETDATE(), 23);       -- '2026-05-07' (style 23)
SELECT CONVERT(VARCHAR, GETDATE(), 120);      -- '2026-05-07 14:30:00'

Rule: format dates at the presentation layer, not in SQL. Send raw datetime to the app; let it format per user locale.

Common queries

-- Last 7 days
WHERE created_at >= DATEADD(DAY, -7, SYSUTCDATETIME())

-- This month
WHERE created_at >= DATEFROMPARTS(YEAR(GETDATE()), MONTH(GETDATE()), 1)
  AND created_at < DATEADD(MONTH, 1, DATEFROMPARTS(YEAR(GETDATE()), MONTH(GETDATE()), 1))

-- Year-to-date
WHERE YEAR(created_at) = YEAR(GETDATE())   -- but this prevents index use!

-- Better — keep column raw
WHERE created_at >= DATEFROMPARTS(YEAR(GETDATE()), 1, 1)
  AND created_at < DATEFROMPARTS(YEAR(GETDATE()) + 1, 1, 1)
SARGable rule (Module 43): never wrap an indexed column in a function in WHERE. WHERE YEAR(date) = 2026 ignores the index. WHERE date >= '2026-01-01' AND date < '2027-01-01' uses it.

String & Numeric Functions

String basics

SELECT LEN(name) FROM users;                      -- length (T-SQL); LENGTH() in Postgres/MySQL
SELECT UPPER(email), LOWER(email) FROM users;
SELECT TRIM(name) FROM users;                     -- removes leading + trailing whitespace
SELECT LTRIM(name), RTRIM(name) FROM users;
SELECT REVERSE(name) FROM users;
SELECT REPLACE(phone, '-', '') FROM users;        -- remove dashes

Substring and search

SELECT SUBSTRING(name, 1, 5) FROM users;         -- first 5 chars
SELECT LEFT(name, 5) FROM users;                  -- T-SQL/MySQL
SELECT RIGHT(name, 3) FROM users;
SELECT CHARINDEX('@', email) FROM users;          -- T-SQL; POSITION() in Postgres
-- Get domain part of email:
SELECT SUBSTRING(email, CHARINDEX('@', email) + 1, 100) FROM users;

Concatenation

SELECT first_name + ' ' + last_name AS full_name FROM users;     -- T-SQL
-- BUT: if any part is NULL, the whole thing is NULL.

-- CONCAT handles NULLs as empty string
SELECT CONCAT(first_name, ' ', last_name) FROM users;             -- standard

-- Skip NULLs explicitly with separator
SELECT CONCAT_WS(' ', first_name, middle_name, last_name) FROM users;

Padding and formatting

SELECT REPLICATE('0', 5) + CAST(id AS VARCHAR);        -- T-SQL
SELECT FORMAT(amount, 'N2');                            -- '1,234.50'
SELECT FORMAT(amount, 'C', 'en-IN');                    -- '₹1,234.50'

Useful numeric functions

SELECT ABS(-5);                          -- 5
SELECT ROUND(3.14159, 2);                -- 3.14
SELECT CEILING(4.3);                     -- 5
SELECT FLOOR(4.9);                       -- 4
SELECT POWER(2, 10);                     -- 1024
SELECT SQRT(16);                         -- 4
SELECT MOD(10, 3);                       -- 1 (Postgres); use 10 % 3 in T-SQL
SELECT 10 % 3;                            -- 1 (T-SQL)

Type conversion

SELECT CAST('123' AS INT);                    -- standard
SELECT CONVERT(INT, '123');                    -- T-SQL
SELECT TRY_CAST('abc' AS INT);                 -- T-SQL: returns NULL on failure
SELECT TRY_CONVERT(INT, 'abc');                -- T-SQL: same

Use TRY_CAST when input may be malformed — saves errors.

Generating strings

SELECT NEWID();                           -- T-SQL: random GUID
SELECT NEWSEQUENTIALID();                  -- T-SQL: sequential GUID (better for indexes)
SELECT CHAR(65);                           -- 'A'
SELECT ASCII('A');                         -- 65

SELECT JSON_QUERY(json_col, '$.address');                       -- nested object

Module 14
INNER JOIN

The most common join

Returns rows where the join condition matches in both tables.

SELECT u.name, o.amount, o.created_at
FROM users u
INNER JOIN orders o ON o.user_id = u.id
WHERE o.status = 'paid';

What happens visually

  users                orders             Result
  ┌─────────┐        ┌──────────┐        ┌────────────────────┐
  │1 Alice  │───┐    │1 1 99.50 │        │Alice  99.50  ...   │
  │2 Bob    │   ├───►│2 1 145.00│  →    │Alice  145.00 ...   │
  │3 Carol  │   │    │3 2 29.99 │        │Bob    29.99  ...   │
  └─────────┘        └──────────┘        └────────────────────┘
                  Carol has no orders → excluded from INNER JOIN

Multiple join conditions

SELECT *
FROM tax_rates t
INNER JOIN orders o ON o.country = t.country
                    AND o.tax_year = t.year;

JOIN ... USING

-- Postgres / MySQL — when both columns have the same name
SELECT * FROM users INNER JOIN orders USING (user_id);
-- Equivalent to: ON users.user_id = orders.user_id

Implicit JOIN syntax (avoid)

-- Old, harder to read, easy to forget
SELECT *
FROM users u, orders o
WHERE o.user_id = u.id;

Always use explicit JOIN ... ON. Reads better, separates filtering from joining.

JOIN order doesn't matter (for INNER)

For INNER joins, the optimizer can reorder. A INNER JOIN B = B INNER JOIN A. For OUTER joins, order matters.

Module 15
OUTER JOINs (LEFT / RIGHT / FULL)

LEFT JOIN — keep all left-side rows

SELECT u.name, o.amount
FROM users u
LEFT JOIN orders o ON o.user_id = u.id;
  users                orders             Result (LEFT JOIN)
  ┌─────────┐        ┌──────────┐        ┌──────────────────┐
  │1 Alice  │───────►│1 1 99.50 │        │Alice  99.50      │
  │2 Bob    │───────►│2 1 145.00│        │Alice  145.00     │
  │3 Carol  │        │3 2 29.99 │        │Bob    29.99      │
  └─────────┘        └──────────┘        │Carol  NULL  ←────┤ unmatched left
                                          └──────────────────┘

RIGHT JOIN — keep all right-side rows

Mirror image of LEFT. Rarely seen in practice — most people just write LEFT and swap the table order.

FULL OUTER JOIN — keep both sides

SELECT u.name, o.amount
FROM users u
FULL OUTER JOIN orders o ON o.user_id = u.id;

Includes:

  • Matched rows.
  • Users without orders (right side NULL).
  • Orders with no user (left side NULL — orphan orders, shouldn't happen with FK!).

MySQL doesn't support FULL OUTER JOIN — emulate with LEFT JOIN UNION RIGHT JOIN.

The classic LEFT JOIN bug

Bad — filter in WHERE breaks LEFT JOIN

-- "Show all users with their paid orders"
SELECT u.name, o.amount
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.status = 'paid';
-- BUG: filters out users with no orders too,
-- because their o.status is NULL (NOT 'paid').

Good — filter in JOIN condition

SELECT u.name, o.amount
FROM users u
LEFT JOIN orders o
   ON o.user_id = u.id
  AND o.status = 'paid';
-- Users with no paid orders show up with NULL.

"Find rows in A that have no match in B"

The classic anti-join pattern:

-- Users who never placed an order
SELECT u.*
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.user_id IS NULL;

-- Or with NOT EXISTS (often faster, clearer intent)
SELECT u.*
FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);

Module 16
CROSS JOIN & SELF JOIN

CROSS JOIN — Cartesian product

-- Every user × every product (use with care!)
SELECT u.name, p.name AS product
FROM users u
CROSS JOIN products p;

If users has 1000 rows and products has 500, you get 500,000 rows. Almost always a bug. Real uses:

  • Generating a date range × every region.
  • Producing all combinations for a calendar.
  • Test data generation.

SELF JOIN — table joined to itself

When the relationship is within one table.

-- Find each employee and their manager (manager_id → employees.id)
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON m.id = e.manager_id;

Two aliases (e and m) for the same table — that's the trick.

Hierarchical examples

-- Categories with their parent category names
SELECT c.name, COALESCE(p.name, '(root)') AS parent
FROM categories c
LEFT JOIN categories p ON p.id = c.parent_id;

For arbitrary-depth hierarchies, use recursive CTEs (Module 63).

SELF JOIN to find duplicates

-- Find users with the same email but different IDs
SELECT u1.id, u1.email, u2.id
FROM users u1
INNER JOIN users u2
    ON u1.email = u2.email
   AND u1.id < u2.id;

The u1.id < u2.id ensures each duplicate pair appears once, not twice.

Module 17
Multi-Table Joins

Three+ tables

SELECT
    o.id,
    u.name AS customer,
    p.name AS product,
    oi.quantity,
    oi.unit_price
FROM orders o
INNER JOIN users u ON u.id = o.user_id
INNER JOIN order_items oi ON oi.order_id = o.id
INNER JOIN products p ON p.id = oi.product_id
WHERE o.status = 'paid'
  AND o.created_at >= DATEADD(MONTH, -1, GETDATE());

Joins are evaluated left to right (logically), but the optimizer picks the best physical order.

Mix of INNER and LEFT

-- All orders with their items, including items without products (data quality issue)
SELECT o.id, oi.quantity, p.name
FROM orders o
INNER JOIN order_items oi ON oi.order_id = o.id      -- must have items
LEFT JOIN products p ON p.id = oi.product_id;        -- product may be missing

Join performance — what to watch

  • Always have indexes on the join columns (FKs especially).
  • Filter as early as possible — push predicates close to the table.
  • Watch for "row explosion" — joining one row to N children, then to M grandchildren = N×M rows.
  • EXPLAIN your plan; check the row count estimates.

Star schema joins (analytics)

-- Fact table at center, dimension tables around it
SELECT
    d_date.year,
    d_date.month,
    d_product.category,
    SUM(f_sales.amount)
FROM fact_sales f_sales
INNER JOIN dim_date d_date ON d_date.date_key = f_sales.date_key
INNER JOIN dim_product d_product ON d_product.product_key = f_sales.product_key
INNER JOIN dim_customer d_cust ON d_cust.customer_key = f_sales.customer_key
WHERE d_date.year = 2026
  AND d_cust.country = 'IN'
GROUP BY d_date.year, d_date.month, d_product.category;

This pattern is the foundation of data warehousing. Each dimension table answers a "by what" question.

Module 18
UNION, INTERSECT, EXCEPT

Set operations combine result sets vertically

OperatorReturns
UNIONDistinct rows from both queries
UNION ALLAll rows from both queries — duplicates kept
INTERSECTRows that appear in both
EXCEPT (T-SQL/PG) / MINUS (Oracle)Rows in first but not in second

UNION example

SELECT id, name, 'employee' AS type FROM employees
UNION
SELECT id, name, 'contractor' AS type FROM contractors
ORDER BY name;

Rules:

  • Same number of columns in both queries.
  • Compatible types in the same position.
  • Final ORDER BY applies to combined result.
  • Column names taken from the first query.

UNION vs UNION ALL — performance

UNION sorts and removes duplicates — extra work. UNION ALL just concatenates. Use UNION ALL unless you need duplicate removal; the difference can be 10× on big results.

INTERSECT

-- Users who are both employees AND contractors
SELECT email FROM employees
INTERSECT
SELECT email FROM contractors;

EXCEPT

-- Customers who were active last year but not this year
SELECT user_id FROM orders WHERE YEAR(created_at) = 2025
EXCEPT
SELECT user_id FROM orders WHERE YEAR(created_at) = 2026;

vs JOIN-based equivalents

Most set operations can be rewritten as joins / EXISTS. The optimizer often produces similar plans. Use whichever expresses your intent more clearly.

Module 19
Subqueries & EXISTS

Subqueries as values

-- A scalar subquery returns one value
SELECT name, age,
       (SELECT AVG(age) FROM users) AS avg_age,
       age - (SELECT AVG(age) FROM users) AS diff_from_avg
FROM users;

Subqueries in WHERE

-- Customers who placed at least one order over $100
SELECT * FROM users
WHERE id IN (SELECT user_id FROM orders WHERE amount > 100);

EXISTS — usually better than IN

SELECT * FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id AND o.amount > 100);

Why EXISTS:

  • Doesn't materialize the inner result — short-circuits on first match.
  • Doesn't have the NULL trap of NOT IN.
  • Often clearer for "is there any X?" intent.

NOT EXISTS

-- Users who haven't ordered
SELECT * FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);

Correlated vs non-correlated

-- NON-correlated: inner query is independent
SELECT * FROM users WHERE id IN (SELECT user_id FROM orders);

-- CORRELATED: inner query references outer row, runs per outer row
SELECT u.*,
       (SELECT COUNT(*) FROM orders o WHERE o.user_id = u.id) AS order_count
FROM users u;

Correlated subqueries can be slow if the outer set is large — the inner query runs N times.

Subqueries in FROM (derived tables)

SELECT t.country, t.cnt
FROM (
    SELECT country, COUNT(*) AS cnt
    FROM users
    GROUP BY country
) AS t
WHERE t.cnt > 100;

For complex queries, CTEs (Module 63) usually read better than nested subqueries.

ANY and ALL

-- Get products more expensive than every product in category 5
SELECT * FROM products
WHERE price > ALL (SELECT price FROM products WHERE category_id = 5);

-- Equivalent
SELECT * FROM products WHERE price > (SELECT MAX(price) FROM products WHERE category_id = 5);

Most ANY/ALL queries are clearer with MAX/MIN/EXISTS.

Module 20
GROUP BY

The aggregation functions

FunctionWhat
COUNT(*)Number of rows (incl. NULL)
COUNT(col)Number of non-NULL values
COUNT(DISTINCT col)Number of distinct non-NULL values
SUM(col)Sum (NULLs ignored)
AVG(col)Average
MIN(col) / MAX(col)Smallest / largest

Basic GROUP BY

SELECT
    country,
    COUNT(*) AS user_count,
    AVG(age) AS avg_age,
    MAX(created_at) AS most_recent
FROM users
GROUP BY country;

The unyielding rule

Every column in SELECT must be either:

  1. Listed in GROUP BY, OR
  2. Inside an aggregate function.

Otherwise the DB doesn't know which value to pick from the group.

Bad — name not aggregated or grouped

SELECT country, name, COUNT(*)
FROM users
GROUP BY country;
-- Error: name must appear in GROUP BY or be aggregated

Good — explicit choice

SELECT country, COUNT(*), MAX(name) AS sample_name
FROM users
GROUP BY country;

Multi-column groups

SELECT country, city, COUNT(*) AS users
FROM users
GROUP BY country, city
ORDER BY country, users DESC;

Conditional aggregation

-- Per country: total users, adults, kids
SELECT
    country,
    COUNT(*) AS total,
    SUM(CASE WHEN age >= 18 THEN 1 ELSE 0 END) AS adults,
    SUM(CASE WHEN age <  18 THEN 1 ELSE 0 END) AS kids
FROM users
GROUP BY country;

GROUPING SETS, ROLLUP, CUBE

-- ROLLUP: subtotals + grand total
SELECT country, city, COUNT(*) FROM users
GROUP BY ROLLUP(country, city);
-- Output rows: each (country,city), subtotal per country, grand total

-- CUBE: all combinations of grouping
SELECT country, city, COUNT(*) FROM users
GROUP BY CUBE(country, city);

-- GROUPING SETS: explicit list
SELECT country, city, COUNT(*) FROM users
GROUP BY GROUPING SETS ( (country, city), (country), () );

STRING_AGG — flatten group to comma list

SELECT
    country,
    STRING_AGG(name, ', ') WITHIN GROUP (ORDER BY name) AS users_in_country
FROM users
GROUP BY country;

Module 21
HAVING vs WHERE

The distinction

  • WHERE filters individual rows BEFORE grouping.
  • HAVING filters groups AFTER grouping.
-- Both used together
SELECT country, COUNT(*) AS users
FROM users
WHERE is_active = 1                    -- filter rows BEFORE grouping
GROUP BY country
HAVING COUNT(*) > 100                  -- filter GROUPS after aggregating
ORDER BY users DESC;

Why not just put it all in WHERE?

You can't reference an aggregate in WHERE — aggregates don't exist yet (rows haven't been grouped). HAVING runs after GROUP BY when aggregates are computed.

Common mistake

Bad — using HAVING for row filtering

SELECT country, COUNT(*)
FROM users
GROUP BY country
HAVING is_active = 1;
-- Error or wrong result: is_active is per-row,
-- but HAVING runs AFTER GROUP BY where individual rows are gone

Good — row filter in WHERE

SELECT country, COUNT(*)
FROM users
WHERE is_active = 1
GROUP BY country;

Performance

Filter as early as possible. WHERE before GROUP BY means fewer rows to aggregate. Don't put filtering in HAVING that could be in WHERE.

Module 22
Window Functions Intro

The big idea

Aggregates collapse rows into one. Window functions compute aggregates while keeping the original rows.

-- Without window: collapsed
SELECT country, AVG(age) FROM users GROUP BY country;

-- With window: each row plus its country's average
SELECT
    name,
    age,
    country,
    AVG(age) OVER (PARTITION BY country) AS country_avg_age
FROM users;

The OVER clause

function() OVER (
    [PARTITION BY ...]    -- "groups" within the result
    [ORDER BY ...]        -- ordering within each partition
    [ROWS / RANGE ...]    -- frame: which rows to include
)

Row numbers and ranks

SELECT
    name,
    department,
    salary,
    ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS rn,
    RANK()       OVER (PARTITION BY department ORDER BY salary DESC) AS rk,
    DENSE_RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS drk,
    NTILE(4)     OVER (ORDER BY salary) AS quartile
FROM employees;
FunctionBehavior on ties
ROW_NUMBER()Sequential 1, 2, 3, 4… (no ties)
RANK()1, 2, 2, 4 (gaps after ties)
DENSE_RANK()1, 2, 2, 3 (no gaps)
NTILE(n)Divides rows into n buckets

Top-N per group

-- Top 3 highest-paid per department
WITH ranked AS (
    SELECT *,
           ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS rn
    FROM employees
)
SELECT name, department, salary
FROM ranked
WHERE rn <= 3;

This is one of the most common patterns. Memorize it.

LAG and LEAD

SELECT
    user_id,
    order_date,
    amount,
    LAG(amount, 1) OVER (PARTITION BY user_id ORDER BY order_date) AS prev_amount,
    LEAD(amount, 1) OVER (PARTITION BY user_id ORDER BY order_date) AS next_amount,
    amount - LAG(amount, 1) OVER (PARTITION BY user_id ORDER BY order_date) AS diff_from_prev
FROM orders;

Used for: "did the value go up or down?", "find consecutive events", "gaps in time series".

Module 23
Window Functions Advanced

Running totals (cumulative sum)

SELECT
    order_date,
    amount,
    SUM(amount) OVER (ORDER BY order_date
                      ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total
FROM orders;

Moving averages

-- 7-day moving average
SELECT
    order_date,
    daily_total,
    AVG(daily_total) OVER (
        ORDER BY order_date
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
    ) AS ma_7d
FROM daily_totals;

Frame specifications

ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW    -- from start to current
ROWS BETWEEN 6 PRECEDING AND CURRENT ROW            -- last 7 rows including current
ROWS BETWEEN 3 PRECEDING AND 3 FOLLOWING            -- 7-row centered window
ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING    -- current to end
RANGE BETWEEN INTERVAL '7' DAY PRECEDING AND CURRENT ROW   -- by value, not row count (PG)

FIRST_VALUE / LAST_VALUE

SELECT
    user_id,
    order_date,
    amount,
    FIRST_VALUE(amount) OVER (PARTITION BY user_id ORDER BY order_date) AS first_order,
    LAST_VALUE(amount) OVER (
        PARTITION BY user_id ORDER BY order_date
        ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
    ) AS last_order
FROM orders;

Note: LAST_VALUE needs an explicit unbounded frame — the default frame ends at CURRENT ROW.

PERCENT_RANK and CUME_DIST

SELECT
    name,
    salary,
    PERCENT_RANK() OVER (ORDER BY salary) AS pct_rank,
    CUME_DIST()    OVER (ORDER BY salary) AS cumulative_dist
FROM employees;

Common patterns

Detect gaps in series

SELECT id, prev_id, id - prev_id AS gap
FROM (
    SELECT id, LAG(id) OVER (ORDER BY id) AS prev_id
    FROM logs
) t
WHERE id - prev_id > 1;

Sessionize events (gaps + islands)

-- Mark the start of a new session when gap > 30 min
SELECT *,
       SUM(is_new_session) OVER (PARTITION BY user_id ORDER BY ts) AS session_id
FROM (
    SELECT *,
           CASE WHEN DATEDIFF(MINUTE, LAG(ts) OVER (PARTITION BY user_id ORDER BY ts), ts) > 30
                THEN 1 ELSE 0 END AS is_new_session
    FROM events
) t;

Why window functions are the most under-used SQL feature

Once you internalize them, you stop writing self-joins and correlated subqueries. Most "hard" SQL problems collapse to one window function.

Module 24
INSERT

Single row

INSERT INTO users (email, name, country)
VALUES ('a@x.com', 'Alice', 'IN');

Multiple rows

INSERT INTO users (email, name, country)
VALUES
    ('a@x.com', 'Alice', 'IN'),
    ('b@x.com', 'Bob',   'US'),
    ('c@x.com', 'Carol', 'UK');

INSERT ... SELECT

INSERT INTO archived_orders (id, user_id, amount, created_at)
SELECT id, user_id, amount, created_at
FROM orders
WHERE created_at < '2024-01-01';

Capture inserted IDs (T-SQL OUTPUT)

INSERT INTO users (email, name)
OUTPUT INSERTED.id, INSERTED.email
VALUES ('d@x.com', 'Dave');

Returns a result set with the inserted ID(s). Equivalent to Postgres RETURNING:

INSERT INTO users (email, name)
VALUES ('d@x.com', 'Dave')
RETURNING id, email;

INSERT with default columns

-- Use DEFAULT VALUES if all columns have defaults
INSERT INTO logs DEFAULT VALUES;

-- Skip auto-increment ID; let DB assign
INSERT INTO users (email, name) VALUES ('e@x.com', 'Eve');

Bulk insert at scale

  • SQL Server: BULK INSERT from file, or SqlBulkCopy from .NET. Orders of magnitude faster than per-row INSERT.
  • Postgres: COPY command.
  • MySQL: LOAD DATA INFILE, INSERT ... VALUES (...), (...), ... in big batches.

Common INSERT mistakes

  • Forgetting NOT NULL columns → error.
  • Inserting one row at a time in a loop from app code → 1000× slower than batch.
  • Inserting without a transaction → partial inserts on error.
  • Not using parameterized queries → SQL injection (Module 72).

Module 25
UPDATE

Basic UPDATE

UPDATE users
SET name = 'Alice Smith',
    updated_at = SYSUTCDATETIME()
WHERE id = 42;
The cardinal rule: always have a WHERE clause. UPDATE users SET name = 'X' updates EVERY row. Many DBAs require a SELECT first to see what rows would be affected, then convert to UPDATE.

UPDATE from another table (T-SQL)

UPDATE u
SET u.country = c.country_name
FROM users u
INNER JOIN countries c ON c.code = u.country_code;

Postgres uses UPDATE users SET country = c.name FROM countries c WHERE u.country_code = c.code;

UPDATE with subquery

UPDATE users
SET order_count = (SELECT COUNT(*) FROM orders WHERE user_id = users.id);

Conditional update with CASE

UPDATE products
SET price = CASE
    WHEN category = 'premium' THEN price * 1.10
    WHEN category = 'budget'  THEN price * 1.05
    ELSE price
END;

Capture old/new values (OUTPUT)

UPDATE users
SET status = 'inactive'
OUTPUT
    DELETED.id,
    DELETED.status AS old_status,
    INSERTED.status AS new_status
WHERE last_login < DATEADD(YEAR, -1, GETDATE());

UPDATE with TOP / LIMIT

-- Update only the next 1000 (useful for batched updates on huge tables)
UPDATE TOP (1000) users SET status = 'archived' WHERE last_login < '...';

-- Postgres
UPDATE users SET status = 'archived' WHERE id IN (
    SELECT id FROM users WHERE last_login < '...' LIMIT 1000
);

Common pitfalls

  • Updating without checking — trial in transaction with rollback.
  • Updating in a loop from app code → batch when possible.
  • Updating indexed columns — slower; rebuilds index entries.
  • Long-running update locks the rows — chunked updates avoid blocking.

Always-pattern: trial run

-- Step 1: see what would change
SELECT * FROM users WHERE last_login < DATEADD(YEAR, -1, GETDATE());

-- Step 2: do it
UPDATE users SET status = 'inactive'
WHERE last_login < DATEADD(YEAR, -1, GETDATE());

-- Step 3 (optional): wrap in transaction first
BEGIN TRAN;
UPDATE users SET ...;
-- Check row count, sample results
ROLLBACK TRAN;   -- or COMMIT TRAN if happy

Module 26
DELETE

Basic DELETE

DELETE FROM users WHERE id = 42;
DELETE FROM users WHERE created_at < '2020-01-01';

DELETE with JOIN (T-SQL)

DELETE u
FROM users u
INNER JOIN inactive_log il ON il.user_id = u.id
WHERE il.archived = 1;

Soft delete (preferred for audited systems)

-- Don't actually delete; mark as deleted
UPDATE users SET deleted_at = SYSUTCDATETIME() WHERE id = 42;

-- All queries filter on deleted_at IS NULL
SELECT * FROM users WHERE deleted_at IS NULL;

Pros: undo, audit trail, FK references survive. Cons: every query needs the filter; soft-deleted rows still take space.

TRUNCATE — when you want it all gone

TRUNCATE TABLE staging_data;
  • Faster than DELETE FROM table — doesn't log per row.
  • Resets identity counter.
  • Cannot have WHERE.
  • Cannot truncate a table referenced by an FK.

Cascading deletes

CREATE TABLE orders (
    id INT PRIMARY KEY,
    user_id INT,
    CONSTRAINT FK_orders_user
        FOREIGN KEY (user_id) REFERENCES users(id)
        ON DELETE CASCADE                    -- delete orders when user deleted
);

Other options: ON DELETE SET NULL, ON DELETE NO ACTION (default), ON DELETE RESTRICT.

Cascade carefully: deleting a user that cascades to 1M orders takes minutes and locks both tables. Soft delete or batched delete is often safer.

Batched delete for large purges

-- Delete in chunks to avoid one giant transaction
DECLARE @BatchSize INT = 10000;
DECLARE @Deleted INT = 1;

WHILE @Deleted > 0
BEGIN
    DELETE TOP (@BatchSize) FROM logs WHERE created_at < '2024-01-01';
    SET @Deleted = @@ROWCOUNT;
    -- Optional: WAITFOR DELAY '00:00:01' to give other queries a chance
END

Module 27
MERGE / Upsert / Bulk

The "insert if new, update if exists" problem

Every system has it. Three solutions:

Option 1: T-SQL MERGE (controversial)

MERGE users AS target
USING (VALUES ('a@x.com', 'Alice')) AS source (email, name)
   ON target.email = source.email
WHEN MATCHED THEN
    UPDATE SET name = source.name, updated_at = SYSUTCDATETIME()
WHEN NOT MATCHED THEN
    INSERT (email, name) VALUES (source.email, source.name);
Heads up: SQL Server's MERGE has had multiple correctness bugs over the years and concurrency issues with concurrent merges. Many experienced DBAs recommend avoiding it. See option 3.

Option 2: Postgres / MySQL upsert

-- Postgres
INSERT INTO users (email, name)
VALUES ('a@x.com', 'Alice')
ON CONFLICT (email) DO UPDATE SET name = EXCLUDED.name;

-- MySQL
INSERT INTO users (email, name) VALUES ('a@x.com', 'Alice')
ON DUPLICATE KEY UPDATE name = VALUES(name);

Option 3: Conditional INSERT/UPDATE (T-SQL safe pattern)

BEGIN TRAN;

UPDATE users
SET name = @name
WHERE email = @email;

IF @@ROWCOUNT = 0
BEGIN
    INSERT INTO users (email, name) VALUES (@email, @name);
END

The forms in plain English

Why normalize

  • No data duplication — change Alice's name once, not in every order.
  • No update anomalies — partial updates can't put data out of sync.
  • Smaller storage.
  • Cleaner constraints (FKs enforce integrity).

Why NOT to normalize fully

  • Joins cost. A 5-way join is slower than reading one wide row.
  • Analytical workloads often benefit from denormalized "fact" tables.
  • Read-heavy reporting wants fewer joins.

The pragmatic answer: 3NF, then denormalize where measured

Default to 3NF. When you measure a query that's slow because of joins, denormalize that specific case. Don't denormalize "just in case" — every duplicate column is a bug waiting to happen.

Module 29
Denormalization Trade-offs

When denormalization is right

  • Read-heavy reporting — pre-joined facts in a star schema.
  • Computed values used everywhere — total order amount stored on the order row, refreshed when items change.
  • Hot lookups — copy the most-used columns from a parent table to a child to avoid joins.
  • Search — flatten data into a search index.
  • Frozen historical data — order rows store the price-at-time-of-order, not the current product price.

The "frozen at time of event" pattern

Most underused denormalization. Orders store the customer name AND email at order time, so:

  • If the customer changes their name later, old orders still reflect what was true at order time.
  • Reports don't break if the customer is deleted.
  • Audit trails are accurate.

The cost

Every denormalization is a place where data can drift. To stay consistent:

  • Update both copies in the same transaction.
  • Or use triggers to keep them in sync (Module 55).
  • Or pre-aggregate on a schedule (materialized view, Module 47).
  • Or accept the inconsistency — sometimes "frozen" is the feature.

Keys (PK, FK, Composite)

Primary key

  • Uniquely identifies each row.
  • Cannot be NULL.
  • Implies UNIQUE + NOT NULL.
  • Backs the clustered index by default in SQL Server.
CREATE TABLE users (
    id INT IDENTITY PRIMARY KEY,
    email NVARCHAR(255) NOT NULL UNIQUE
);

Composite primary key

CREATE TABLE order_items (
    order_id   INT NOT NULL,
    product_id INT NOT NULL,
    quantity   INT NOT NULL,
    PRIMARY KEY (order_id, product_id)
);

Useful for junction tables. The pair (order_id, product_id) is unique.

Foreign key

CREATE TABLE orders (
    id INT IDENTITY PRIMARY KEY,
    user_id INT NOT NULL,
    CONSTRAINT FK_orders_user
        FOREIGN KEY (user_id) REFERENCES users(id)
        ON DELETE NO ACTION
        ON UPDATE NO ACTION
);

FK options:

  • NO ACTION (default) — block delete/update if children exist.
  • CASCADE — delete/update children too.
  • SET NULL — set FK column to NULL.
  • SET DEFAULT — set FK to its default.

SQL Server doesn't auto-index FKs. Without an index, the FK check on parent delete becomes a full table scan of the child. Add an index on every FK column in your schema migrations.

Surrogate vs natural keys (covered fully in Module 32)

  • Surrogate — meaningless ID like id INT IDENTITY. Most rows.
  • Natural — meaningful key like email, isbn. Use carefully.

Zero-downtime migrations — the expand/contract pattern

Renaming a column without breaking the running app:

  1. Expand: add new column. Both old and new exist.
  2. Deploy code that writes to BOTH columns.
  3. Backfill old → new for existing rows.
  4. Deploy code that reads from new only.
  5. Deploy code that writes only to new.
  6. Contract: drop the old column.

Each step is reversible. Never a single "big bang" migration on a live DB.

Things you can ALMOST always do safely

  • Add a nullable column.
  • Add an index (use CREATE INDEX ... WITH (ONLINE = ON) in SQL Server Enterprise).
  • Add a new table.
  • Add a new stored procedure or view.

Things that need expand/contract

  • Renaming a column.
  • Changing a column type.
  • Making a nullable column NOT NULL.
  • Splitting one column into two.
  • Dropping a column the app still uses.

Migration discipline

  • Migrations are append-only — never edit a deployed migration. Add a new one.
  • Each migration is reviewed in PR.
  • Migrations run in CI before merge.
  • Never apply manual changes to prod — always through migrations.

Module 35
How Indexes Work (B-tree)

The problem indexes solve

Without an index, finding "the row with email='alice@x.com'" requires scanning every row. With a million rows, that's a million reads.

An index is a separate sorted structure. Looking up Alice's row becomes O(log n) — about 20 reads for a million rows. With B-trees, even a billion rows takes ~30 reads.

The B-tree structure

                    [50, 100]
                   /    |    \
              [25, 40] [60,80,90] [120,150]
              /  |  \   /|\ |\    /  |  \
           [10][30][45]...[110][130][170]
            ↓   ↓   ↓     ↓    ↓    ↓
           rows rows rows rows rows rows

Each node holds many keys (typically dozens to hundreds — fits a page). Tree depth grows logarithmically. Index seek = walk root → leaf = depth I/O operations.

Two flavors

FlavorWhat's at the leaves
Clustered index The actual table rows, in physical order. One per table. Without one, the table is a "heap".
Non-clustered index Pointer (RID for heap, clustered key for clustered table) to the actual row. Many per table.

The cost of indexes

  • Storage — typically 10–30% of the indexed table per index.
  • Write cost — INSERT/UPDATE/DELETE must update every relevant index.
  • Memory — hot indexes live in buffer pool.

The architect's mindset: indexes are not free. Every index is a bet that the read benefit exceeds the write cost.

What gets indexed automatically

  • PRIMARY KEY — gets a unique index (clustered by default in SQL Server).
  • UNIQUE constraint — gets a unique index.
  • Foreign key — does NOT auto-index in SQL Server. You must add it.

Module 36
Clustered vs Non-Clustered

Clustered index

  • The table's physical row order.
  • One per table.
  • Should be: narrow, unique, ever-increasing, never-changing.
  • By default in SQL Server: the PRIMARY KEY.

Why "ever-increasing" matters

Inserts at the END of the clustered index are cheap — append a row. Inserts in the MIDDLE require splitting pages, which fragments the index. That's why INT IDENTITY beats random GUID for clustered keys.

Range queries are fastest on clustered indexes

-- This is amazing on a clustered index on created_at
SELECT * FROM orders WHERE created_at BETWEEN '2026-01-01' AND '2026-01-31';

Why? The rows are physically adjacent. The DB does a sequential read.

Non-clustered index — point lookups

Stored separately from the table, sorted by the index key. Each leaf entry points to the row.

  Non-clustered index on email:
  [alice@x.com → row 42]
  [bob@x.com   → row 17]
  [carol@x.com → row 8]

Lookup: walk the B-tree on email → get the row pointer → fetch the row from the heap or clustered index.

The "key lookup" cost

Non-clustered index seek is fast, but if your SELECT needs columns NOT in the index, the DB does an extra "key lookup" per row to fetch from the table. Many key lookups = slow. Solution: covering indexes (Module 38).

Choosing what to index

  • Columns in WHERE for selective queries (low matching row %).
  • Columns in JOIN ON.
  • Columns in ORDER BY (avoids sort).
  • Columns in GROUP BY (avoids hash aggregate).
  • Foreign key columns (ALWAYS).

What NOT to index

  • Columns that change frequently.
  • Columns rarely queried.
  • Very wide columns (NVARCHAR(MAX), VARBINARY(MAX)) — index gets huge.
  • Low-cardinality columns alone (is_active) — index won't help much.

Module 37
Composite Indexes

Index on multiple columns

CREATE INDEX IX_orders_user_date
ON orders (user_id, created_at);

This index sorts by user_id first, then by created_at. The order of columns matters HUGELY.

The leftmost-prefix rule

An index on (A, B, C) can serve queries that filter on:

  • WHERE A = ? ✓
  • WHERE A = ? AND B = ? ✓
  • WHERE A = ? AND B = ? AND C = ? ✓
  • WHERE A = ? AND C = ? ✓ (uses A, then filters; not as efficient)
  • WHERE B = ? ✗ Cannot use this index efficiently.
  • WHERE C = ? ✗ Same.

Practical implication

The most-selective / most-frequently-filtered column should come first. (user_id, created_at) if you usually search by user. (created_at, user_id) if you usually search by date.

Range column should be last

If your query has equality on A and range on B, index (A, B) works perfectly. If your query has range on A and equality on B, the equality on B doesn't benefit from the index.

-- Index: (user_id, created_at)

WHERE user_id = 42 AND created_at >= '2026-01-01'
-- ✓ Perfect: equality first, range second

WHERE created_at >= '2026-01-01' AND user_id = 42
-- Same query plan — order in WHERE doesn't matter.

WHERE created_at >= '2026-01-01'
-- ✗ Cannot use index efficiently — user_id not specified.

Real-world ordering heuristic

Equality columns first (most-selective first). Range column last. Unused / sometimes-used columns at the end.

Don't go wild

An index on (a, b, c, d, e) is rarely better than (a, b). Each extra column makes the index bigger, slower to maintain, and rarely used. Pick 2–3 columns.

Module 38
Covering Indexes & INCLUDE

The key lookup problem revisited

-- Index: IX_users_email on (email)
-- Query:
SELECT id, name, email, age FROM users WHERE email = 'alice@x.com';

-- Plan: index seek on email → key lookup on clustered index for id, name, age

One key lookup per matching row. For a single-row query, fine. For thousands of rows, expensive.

Covering index — INCLUDE the rest

CREATE INDEX IX_users_email_inc
ON users (email)
INCLUDE (id, name, age);

The INCLUDE columns are stored at the leaf level of the index but NOT used for searching. Now the query is answered entirely from the index — no table read needed.

When covering helps

  • Queries that hit many rows but need just a few columns.
  • Reports / dashboards.
  • Hot-path queries (login, profile fetch).

When NOT to cover

  • Includes that double the index size for marginal benefit.
  • Tables with frequent UPDATEs to included columns — every update touches the index too.

Inspect — is your query covered?

Look at the execution plan. If you see "Key Lookup" or "RID Lookup", the index isn't covering. Adding the missing columns to INCLUDE eliminates it.

Filtered indexes — index a subset (T-SQL)

-- Only index active users
CREATE INDEX IX_users_active_email
ON users (email)
WHERE deleted_at IS NULL AND is_active = 1;

Smaller, faster, only used by queries that have the same WHERE filter. Great for soft-delete scenarios.

Postgres "partial indexes" — same idea

CREATE INDEX idx_users_active_email
ON users (email)
WHERE deleted_at IS NULL;

Module 39
Index Maintenance

Fragmentation

Over time, INSERTs and UPDATEs cause page splits — index pages become only 50% full and physically scattered. Range scans get slower because more pages to read.

Detection

-- SQL Server: check fragmentation per index
SELECT
    OBJECT_NAME(ips.object_id) AS table_name,
    i.name AS index_name,
    ips.avg_fragmentation_in_percent,
    ips.page_count
FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'LIMITED') ips
JOIN sys.indexes i ON i.object_id = ips.object_id AND i.index_id = ips.index_id
WHERE ips.avg_fragmentation_in_percent > 10
  AND ips.page_count > 1000
ORDER BY ips.avg_fragmentation_in_percent DESC;

Fixing

FragmentationAction
< 10%Do nothing
10–30%ALTER INDEX ... REORGANIZE (online, lighter)
> 30%ALTER INDEX ... REBUILD (heavier, full rebuild)
 
ALTER INDEX IX_users_email ON users REORGANIZE;
ALTER INDEX ALL ON orders REBUILD WITH (ONLINE = ON);   -- Enterprise edition

Statistics

The optimizer uses statistics about column value distributions to estimate row counts. Stale statistics → bad plans.

UPDATE STATISTICS users WITH FULLSCAN;
-- Or for one index:
UPDATE STATISTICS users IX_users_email;

Auto-update is on by default and triggers when ~20% of rows change. For huge tables, that threshold rarely fires — manual updates help.

Unused indexes — delete them

SELECT OBJECT_NAME(s.object_id), i.name,
       s.user_seeks, s.user_scans, s.user_lookups, s.user_updates
FROM sys.dm_db_index_usage_stats s
JOIN sys.indexes i ON i.object_id = s.object_id AND i.index_id = s.index_id
WHERE i.name IS NOT NULL
  AND s.user_seeks + s.user_scans + s.user_lookups = 0
  AND s.user_updates > 0;
-- Indexes with zero reads but updates — pure write tax

Missing indexes — what would help?

SELECT TOP 20
    mid.statement AS table_name,
    migs.avg_user_impact AS impact,
    migs.user_seeks,
    mid.equality_columns,
    mid.inequality_columns,
    mid.included_columns
FROM sys.dm_db_missing_index_group_stats migs
JOIN sys.dm_db_missing_index_groups mig ON mig.index_group_handle = migs.group_handle
JOIN sys.dm_db_missing_index_details mid ON mig.index_handle = mid.index_handle
ORDER BY migs.avg_user_impact * migs.user_seeks DESC;

SQL Server tracks missed-index opportunities. Don't blindly create them all — verify each one makes sense.

Module 40
Statistics & Cardinality

What statistics are

The optimizer doesn't see your data — it sees a histogram of value distribution. "How many rows match WHERE country = 'IN'?" → from the histogram.

Why estimates matter

The optimizer picks plans based on estimates:

  • Few matches expected → use index seek.
  • Many matches expected → full scan or hash join.

Bad estimates (10× off) → bad plans, sometimes catastrophically slow.

Cardinality estimation pitfalls

  • Uneven distribution — 90% of users in country='IN' breaks naive estimates.
  • Correlation — country and city aren't independent; product of probabilities is wrong.
  • Out-of-range values — querying for last-week's data when stats were updated last month.
  • Parameter sniffing — first execution's parameters shape the cached plan, hurting later executions with different parameters.

Inspect statistics

DBCC SHOW_STATISTICS('users', 'IX_users_country');
-- Shows: histogram of country values, range_rows, equal_rows, avg_range_rows

Help the optimizer

  • Keep statistics fresh — periodic UPDATE STATISTICS.
  • Use parameterized queries (cache benefits).
  • For known skew: filtered statistics on hot ranges.
  • Use OPTION (RECOMPILE) on queries with wildly varying parameters.
  • Use OPTION (OPTIMIZE FOR ...) to hint typical parameter values.

Real-world story: parameter sniffing

A stored procedure runs for the first time with @country = 'IN' (90% of users). Plan picks scan. Cached plan is reused for @country = 'JP' (0.1% of users). Now JP users get a scan that should be a seek — pages of slow queries, hard to debug. Solution: WITH RECOMPILE, OPTION (OPTIMIZE FOR UNKNOWN), or split into two procedures.

  4. Hash joins on big inputs — sometimes fine, sometimes a sign of missing indexed merge join.

Module 42
Common Bottlenecks

The usual suspects, in priority order

1. Missing index on a WHERE / JOIN column

Symptom: table scan in plan. Fix: add the index. Most common DB performance bug.

2. SELECT *

Forces every column to be read; defeats covering indexes.

3. Function on indexed column in WHERE

WHERE YEAR(created_at) = 2026                  -- bad
WHERE created_at >= '2026-01-01'
  AND created_at <  '2027-01-01'                -- good

4. Implicit type conversion

WHERE phone = 9876543210               -- if phone is VARCHAR, converts implicitly, kills index
WHERE phone = '9876543210'              -- match types

5. NOT IN / NOT EXISTS / negation

Negation is hard for the optimizer. Often forces scans. Try EXCEPT, LEFT JOIN ... IS NULL, or restructured logic.

6. OR conditions across columns

WHERE country = 'IN' OR city = 'Mumbai'         -- often two index seeks UNIONed
-- Sometimes faster as:
SELECT * FROM users WHERE country = 'IN'
UNION
SELECT * FROM users WHERE city = 'Mumbai';

7. Large IN lists

WHERE id IN (1, 2, ..., 10000) can choke. Use a temp table or table-valued parameter:

-- T-SQL TVP
DECLARE @ids dbo.IntList;
INSERT INTO @ids VALUES (1), (2), ..., (10000);

8. N+1 queries from app code

Loop loading children one row at a time. See Module 44.

9. Locking / blocking

Slow query is actually waiting for another transaction. Modules 60–62.

10. Bloated, fragmented tables

Tables grown to 100 GB with deleted-but-not-reclaimed pages. Rebuild indexes; consider partitioning (Module 67).

  1. Get the query and parameter values.
  2. EXPLAIN ANALYZE / actual plan.
  3. Look for scans on big tables, key lookups, sort operators.
  4. Check estimated vs actual rows.
  5. Check stats — when last updated?
  6. Check for blocking locks.
  7. If all else equal, profile in dev.

Module 43
SARGable Predicates

What SARGable means

"Search ARGument-able". A predicate that the DB can use an index for. The opposite — non-SARGable — disables the index.

The rule

Don't wrap an indexed column in a function or expression. The DB can't use the index because it has to compute the function for every row first.

Examples

Non-SARGable (slow)SARGable (fast)
WHERE YEAR(created_at) = 2026 WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'
WHERE UPPER(name) = 'ALICE' WHERE name = 'Alice' (with case-insensitive collation)
WHERE LEFT(email, 5) = 'alice' WHERE email LIKE 'alice%'
WHERE id + 1 = 100 WHERE id = 99
WHERE CAST(price AS INT) = 100 WHERE price >= 100 AND price < 101
WHERE phone = 9876543210 (when phone is VARCHAR) WHERE phone = '9876543210'
WHERE name LIKE '%alice%' Hard — leading wildcard. Use full-text search.

Computed columns can save you

If you really need YEAR(created_at) queries:

ALTER TABLE orders ADD created_year AS YEAR(created_at) PERSISTED;
CREATE INDEX IX_orders_year ON orders(created_year);

-- Now this is fast:
WHERE created_year = 2026

Implicit conversion warnings

Watch for the yellow triangle in execution plans — implicit conversion. Fix the type mismatch.

OR is a SARGability killer

-- Often non-SARGable as one operation
WHERE country = 'IN' OR (country IS NULL AND city = 'Mumbai')

-- Often faster as UNION
SELECT ... WHERE country = 'IN'
UNION
SELECT ... WHERE country IS NULL AND city = 'Mumbai'

Module 44
Avoiding N+1 Queries

The classic ORM mistake

// EF Core
var users = await _db.Users.ToListAsync();   // 1 query
foreach (var u in users)
{
    Console.WriteLine(u.Orders.Count);        // 1 query PER user
}
// Total: 1 + N queries

For 1000 users, that's 1001 queries. Each is a network round-trip. Even at 1ms each = 1 second. With more latency = minutes.

Fix 1: eager load

var users = await _db.Users
    .Include(u => u.Orders)
    .ToListAsync();
// 1 query (with JOIN) or 2 queries (split query)

Fix 2: project to DTOs

var summaries = await _db.Users
    .Select(u => new UserSummary
    {
        Id = u.Id,
        Name = u.Name,
        OrderCount = u.Orders.Count()
    })
    .ToListAsync();
// 1 query, only the needed columns

Fix 3: batch load

var users = await _db.Users.ToListAsync();
var userIds = users.Select(u => u.Id).ToList();
var orderCounts = await _db.Orders
    .Where(o => userIds.Contains(o.UserId))
    .GroupBy(o => o.UserId)
    .Select(g => new { UserId = g.Key, Count = g.Count() })
    .ToDictionaryAsync(x => x.UserId, x => x.Count);
// 2 queries total

Detecting N+1 in development

  • EF Core: .LogTo(Console.WriteLine) in dev — count the queries.
  • MiniProfiler — visualizes per-request queries.
  • Application Insights / DataDog — instruments every query.

Pure SQL N+1 — same idea

-- Bad:
for each user in result_of_query_1:
    run "SELECT * FROM orders WHERE user_id = @id"

-- Good:
SELECT * FROM orders WHERE user_id IN (id1, id2, ..., idN);
-- Or join:
SELECT u.*, o.* FROM users u LEFT JOIN orders o ON o.user_id = u.id;

The "row at a time" anti-pattern in stored procs

Cursors processing one row at a time × thousands of rows = slow. Almost always there's a set-based equivalent (one UPDATE/DELETE/INSERT) that's 100× faster.

Module 45
Pagination Strategies

OFFSET pagination — simple but slow at scale

SELECT * FROM users
ORDER BY id
OFFSET 100000 ROWS FETCH NEXT 20 ROWS ONLY;

The DB still must read and discard 100,000 rows to skip them. Page 5000 of a 100-row pagination ≈ same cost as scanning 500,000 rows.

Keyset pagination — the modern fix

Instead of OFFSET, remember the last row's key from the previous page and fetch rows AFTER it.

-- Page 1
SELECT TOP 20 * FROM users ORDER BY id;
-- Last id returned: 20

-- Page 2 — start AFTER id 20
SELECT TOP 20 * FROM users WHERE id > 20 ORDER BY id;
-- Last id: 40

-- Page 3
SELECT TOP 20 * FROM users WHERE id > 40 ORDER BY id;

Each query is O(log n) — uses the index seek directly. Page 5000 is just as fast as page 1.

Multi-column keyset

-- Sort by (created_at DESC, id DESC) for stable order
-- Last row had: (created_at = '2026-05-01 10:00', id = 142)

SELECT TOP 20 * FROM orders
WHERE (created_at, id) < ('2026-05-01 10:00', 142)
ORDER BY created_at DESC, id DESC;

API design with keyset

GET /users?cursor=eyJpZCI6MTQyfQ&limit=20

The cursor is opaque (often base64-encoded JSON of the keyset). Clients pass it back; server decodes.

When OFFSET is fine

  • Small total results (< 1000).
  • Admin pages users only browse the first few.
  • You need page numbers ("page 5 of 100").

When keyset is required

  • Mobile/web feeds with infinite scroll.
  • Anything where users go deep into results.
  • Very large tables.

Module 47
Materialized / Indexed Views

The problem

Some queries are expensive every time they run — a 5-table join with aggregations on millions of rows. The result rarely changes minute-to-minute.

Materialized view (Postgres) / Indexed view (SQL Server)

Pre-compute the result; store it like a table; refresh on a schedule or on update. Reads from it are as fast as a table scan.

SQL Server indexed view

CREATE VIEW dbo.OrderTotalsByUser
WITH SCHEMABINDING
AS
SELECT
    user_id,
    COUNT_BIG(*) AS order_count,
    SUM(amount) AS total_amount
FROM dbo.orders
GROUP BY user_id;
GO

CREATE UNIQUE CLUSTERED INDEX IX_OrderTotalsByUser_user
ON dbo.OrderTotalsByUser (user_id);

Now SELECT * FROM OrderTotalsByUser reads from the materialized data, not the underlying tables.

Constraints (T-SQL)

  • WITH SCHEMABINDING — view's tables can't be altered without dropping view.
  • Cannot use OUTER JOIN, subqueries, *, COUNT(col), MIN/MAX in indexed views (some restrictions relaxed in newer versions).
  • Updates to base tables also update the indexed view → slower writes.

Postgres materialized view

CREATE MATERIALIZED VIEW order_totals_by_user AS
SELECT user_id, COUNT(*) AS order_count, SUM(amount) AS total
FROM orders
GROUP BY user_id;

-- Refresh manually or on schedule
REFRESH MATERIALIZED VIEW order_totals_by_user;
REFRESH MATERIALIZED VIEW CONCURRENTLY order_totals_by_user;   -- non-blocking

Postgres MV doesn't auto-refresh — you trigger it (cron, trigger, etc.). SQL Server's indexed view auto-maintains on every base-table change.

When to use

  • Reports with expensive aggregates run frequently.
  • Reads vastly outweigh writes.
  • Slight staleness (minutes) is acceptable in Postgres MV case.

When not to

  • Real-time accuracy needed → indexed view (auto-maintained) or live query.
  • Underlying data changes constantly → MV refresh becomes the bottleneck.
  • Many slightly-different aggregates → consider a separate analytics DB.

Module 48
Query Hints & Plan Forcing

Hints — last resort

Hints tell the optimizer to use (or avoid) specific strategies. Use them only when you've exhausted other options and have measured a clear win.

Common T-SQL hints

-- Force index usage
SELECT * FROM orders WITH (INDEX(IX_orders_user))
WHERE user_id = 42;

-- Disable parallelism
SELECT * FROM big_table OPTION (MAXDOP 1);

-- Recompile this query — don't cache plan
SELECT * FROM users WHERE country = @country
OPTION (RECOMPILE);

-- Optimize for typical value
SELECT * FROM users WHERE country = @country
OPTION (OPTIMIZE FOR (@country = 'IN'));

-- Optimize for unknown — average estimates
OPTION (OPTIMIZE FOR UNKNOWN)

-- Force a specific join type (rarely needed)
SELECT * FROM a INNER MERGE JOIN b ON a.id = b.a_id;
SELECT * FROM a INNER LOOP JOIN b ON a.id = b.a_id;
SELECT * FROM a INNER HASH JOIN b ON a.id = b.a_id;

-- Read uncommitted (dirty reads — careful!)
SELECT * FROM orders WITH (NOLOCK);    -- often a smell, see Module 59

Plan Guides & Query Store

For when you need to force a known-good plan without changing query text:

  • Plan Guides (T-SQL) — attach hints to a query pattern.
  • Query Store (SQL Server 2016+) — captures all queries and their plans; you can pin a "good" plan permanently. Excellent for plan-regression scenarios.

NOLOCK is a smell

WITH (NOLOCK) reads dirty data. You may see rows mid-update, miss rows, or read the same row twice. Modern alternative: enable RCSI (Read Committed Snapshot Isolation, Module 62) at the database level — gives non-blocking reads without dirty data.

The pyramid of solutions

  1. Better query (rewrite logic) — try first.
  2. Better index — usually wins.
  3. Updated statistics.
  4. Schema change (denormalization, materialized view).
  5. Query hints / plan forcing — last resort.

Module 49
Stored Procedure Basics

What a stored procedure is

A named, parameterized block of T-SQL stored in the database. Compiled once (plan cached), executed on demand.

CREATE PROCEDURE GetActiveUsersByCountry
    @Country NVARCHAR(2)
AS
BEGIN
    SET NOCOUNT ON;

    SELECT id, name, email
    FROM users
    WHERE country = @Country
      AND is_active = 1
    ORDER BY name;
END
GO

-- Execute
EXEC GetActiveUsersByCountry @Country = 'IN';

Why use SPs

  • Encapsulation — complex logic lives near the data.
  • Performance — plan cached on first execution.
  • Security — grant EXECUTE on SP without granting access to underlying tables.
  • Network savings — one call instead of many.
  • Refactoring — change logic without touching app code.

Why NOT to overuse SPs

  • Versioning — schema migrations harder to track.
  • Testing — pure SQL is harder to unit-test.
  • Debugging — stack traces in T-SQL are limited.
  • Tooling — your favorite IDE / refactoring tools work better in app code.
  • Portability — different DB? Rewrite all SPs.

Modern verdict

For most CRUD apps in 2026: write SQL via ORM or parameterized queries. Use SPs for: complex business logic close to data, batch operations, performance-critical paths, security boundaries. Don't make every CRUD a stored procedure "for performance" — modern parameterized queries cache plans too.

Anatomy

CREATE PROCEDURE [schema].[ProcName]
    @Param1 INT,
    @Param2 NVARCHAR(50) = 'default value',     -- with default
    @OutParam INT OUTPUT                          -- returns to caller
AS
BEGIN
    SET NOCOUNT ON;        -- skip "(N rows affected)" messages
    -- body
    RETURN 0;              -- optional return value
END

SET NOCOUNT ON — always include it

Without it, every statement sends a row-count message back to the client. For loops with thousands of statements, that's thousands of network packets.

CREATE PROCEDURE TransferFunds
    @FromAcct INT, @ToAcct INT, @Amount DECIMAL(10,2)

Module 51
Functions: Scalar & Table-Valued

Scalar function

Returns one value. Can be used in SELECT / WHERE expressions.

CREATE FUNCTION dbo.GetAge(@Dob DATE)
RETURNS INT
AS
BEGIN
    RETURN DATEDIFF(YEAR, @Dob, GETDATE())
        - CASE WHEN MONTH(@Dob) > MONTH(GETDATE())
                 OR (MONTH(@Dob) = MONTH(GETDATE()) AND DAY(@Dob) > DAY(GETDATE()))
               THEN 1 ELSE 0 END;
END

-- Use
SELECT name, dbo.GetAge(dob) AS age FROM users;
Scalar UDF performance trap: in older SQL Server, scalar UDFs run row-by-row, defeating parallelism and inflating cost. SQL Server 2019+ has "scalar UDF inlining" that rewrites them when possible. For perf-critical paths, prefer inline TVFs or computed columns.

Inline table-valued function (ITVF) — fast

CREATE FUNCTION dbo.OrdersByUser(@UserId INT)
RETURNS TABLE
AS
RETURN (
    SELECT id, amount, status, created_at
    FROM orders
    WHERE user_id = @UserId
);

-- Use as a virtual table
SELECT * FROM dbo.OrdersByUser(42);
SELECT u.name, o.amount
FROM users u
CROSS APPLY dbo.OrdersByUser(u.id) o;

The optimizer "inlines" the function body into the calling query — same plan as if you'd written the SQL directly. Use ITVFs liberally.

Multi-statement table-valued function (MSTVF) — slow

CREATE FUNCTION dbo.ProcessOrders(@UserId INT)
RETURNS @Result TABLE (id INT, processed_amount DECIMAL(10,2))
AS
BEGIN
    INSERT INTO @Result
    SELECT id, amount * 1.05 FROM orders WHERE user_id = @UserId;
    -- more logic, more INSERTs...
    RETURN;
END

The optimizer treats this as a black box and estimates 1 row (older versions) or 100 rows (newer). Bad estimates = bad plans. Avoid for perf-critical paths.

The TRY/CATCH block

        @ErrorState INT = ERROR_STATE();

Module 54
SP vs Ad-hoc — When to Use Which

The modern reality

Parameterized queries (via ORM or SqlCommand) cache plans just like SPs. Most "performance" arguments for SPs apply less than they used to.

Use SPs when

  • Complex business logic close to data — multi-statement transactions, conditional logic, cursor-style work.
  • Security boundary — grant EXECUTE on SP without table-level access.
  • Hot read paths — slight plan-cache advantage at extreme scale.
  • Refactoring without app deploy — change SP, no recompile of app.
  • DBA-owned logic — when the DBA team owns the data layer.

Use parameterized queries / ORM when

  • CRUD operations.
  • Logic naturally lives in the app layer.
  • Dynamic queries (filter by 1–N optional parameters).
  • Tests benefit from app-side mocking.
  • Schema changes are tracked via EF migrations.

Anti-pattern: SP-per-CRUD

"GetUserById", "GetUserByEmail", "UpdateUserName", "UpdateUserEmail" — fifty SPs that each do one CRUD. This becomes a maintenance burden and the app layer ends up duplicating filtering logic anyway. EF Core / Dapper handle these cleanly.

The pragmatic split

  • SPs for: nightly batch jobs, complex reports, multi-step transactional workflows, security-sensitive operations.
  • App / ORM for: per-request CRUD, dynamic filtering, simple queries.

Versioning & testing SPs

  • SPs in version control (under db/procedures/).
  • Automated deployment via migrations (RoundhousE, FluentMigrator, EF migrations script-only).
  • Tests with tSQLt (T-SQL test framework) or integration tests via app layer.

Module 55
Trigger Basics

What a trigger is

A stored procedure that fires automatically when a specific event happens on a table — INSERT, UPDATE, DELETE.

CREATE TRIGGER TR_users_audit
ON users
AFTER INSERT, UPDATE, DELETE
AS
BEGIN
    SET NOCOUNT ON;

    -- 'inserted' and 'deleted' are virtual tables
    -- INSERT: rows in 'inserted'
    -- DELETE: rows in 'deleted'
    -- UPDATE: old rows in 'deleted', new rows in 'inserted'

    INSERT INTO users_audit (user_id, action, action_at)
    SELECT i.id, 'INSERT', SYSUTCDATETIME() FROM inserted i
    WHERE NOT EXISTS (SELECT 1 FROM deleted d WHERE d.id = i.id)

    UNION ALL

    SELECT d.id, 'DELETE', SYSUTCDATETIME() FROM deleted d
    WHERE NOT EXISTS (SELECT 1 FROM inserted i WHERE i.id = d.id)

    UNION ALL

    SELECT i.id, 'UPDATE', SYSUTCDATETIME()
    FROM inserted i INNER JOIN deleted d ON d.id = i.id;
END

The two virtual tables

Operationinserted containsdeleted contains
INSERTNew rows(empty)
UPDATENew row valuesOld row values
DELETE(empty)Removed rows

Triggers fire ONCE per statement, not per row

If a single UPDATE affects 1000 rows, the trigger runs once with 1000 rows in inserted and deleted. Write triggers as set operations, never row-by-row.

Common uses

  • Auditing — record changes to an audit table.
  • Maintaining computed values — e.g., orders.total = SUM(items.price).
  • Cross-table consistency — when a row is inserted in A, also insert/update in B.
  • Enforcing complex rules — that CHECK constraints can't express.
  • Soft delete — instead-of-delete trigger that marks rows as deleted.

Performance impact

Triggers run synchronously inside the transaction. Slow trigger = slow INSERT/UPDATE for everyone. Always:

  • Keep triggers small.
  • Use set-based logic.
  • Don't do external calls (HTTP, etc.) — the transaction holds locks.

Module 56
AFTER vs INSTEAD OF

AFTER trigger

  • Fires after the statement completes.
  • Constraints already validated.
  • Most common type.
  • Cannot prevent the original operation, only react to it (or roll back via ROLLBACK).

INSTEAD OF trigger

  • Replaces the original operation.
  • You decide what (if anything) actually happens.
  • Common on views — make a view "writable".
  • Useful for soft delete: replace DELETE with UPDATE deleted_at.
-- Soft delete via INSTEAD OF
CREATE TRIGGER TR_users_softdelete
ON users
INSTEAD OF DELETE
AS
BEGIN
    UPDATE u SET deleted_at = SYSUTCDATETIME()
    FROM users u INNER JOIN deleted d ON d.id = u.id;
END

Module 57
When NOT to Use Triggers

The hidden-magic problem

Triggers are invisible to developers reading the code. A junior writes a simple UPDATE users SET name='X' WHERE id=42 and unknowingly triggers 5 other tables to update, an HTTP call, a queue insert. Debugging chains of triggered actions is painful.

When triggers usually go wrong

  • Heavy computation — slows every write.
  • External calls (HTTP, file I/O) — extends transaction; deadlocks if external system is slow.
  • Cascading triggers — trigger A modifies B, B's trigger fires, modifies C, etc. Hard to reason about.
  • Recursive triggers — A's trigger updates A again. Disabled by default; turn on at your peril.
  • Replacing application logic — business rules in triggers are hard to test, version, port.

  • You don't control the application code (legacy / third-party).
  • You need a guarantee that runs even if someone uses raw SQL.
  • Audit logging where compliance demands DB-level enforcement.
  • Truly small, fast, set-based logic with no external dependencies.

Trigger checklist (if you must write one)

  • Set-based, not row-by-row.
  • No external calls.
  • No CASE on @@ROWCOUNT or single-row assumptions.
  • Test with multi-row INSERTs / UPDATEs / DELETEs.
  • Document why the trigger exists and what it does.
  • Add a comment in the table definition pointing to the trigger.

Module 58
Transactions & ACID

What a transaction is

A unit of work that either fully completes (commits) or has no effect (rolls back). The classic example: transferring money — if the debit succeeds but the credit fails, neither should happen.

BEGIN TRANSACTION;

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

COMMIT TRANSACTION;
-- Or:
-- ROLLBACK TRANSACTION;

ACID — the four guarantees

LetterMeaning
AtomicityAll steps succeed or none do.
ConsistencyConstraints hold before and after the transaction.
IsolationConcurrent transactions don't see each other's intermediate state.
DurabilityOnce committed, data survives crashes.

Implicit vs explicit transactions

  • Auto-commit (default in SQL Server) — every statement is its own transaction.
  • Explicit — BEGIN TRAN ... COMMIT/ROLLBACK.
  • Implicit — SET IMPLICIT_TRANSACTIONS ON; every statement starts one, you must commit. Rare.

Nested transactions in SQL Server (a trap)

BEGIN TRAN;             -- @@TRANCOUNT = 1
    BEGIN TRAN;         -- @@TRANCOUNT = 2 (but it's still really one)
        ROLLBACK;       -- ROLLBACK rolls back EVERYTHING; @@TRANCOUNT = 0
    -- COMMIT here would fail
COMMIT;                  -- error: no active transaction

SQL Server doesn't support true nested transactions. Use savepoints if you need partial rollback:

BEGIN TRAN;
    SAVE TRAN sp1;
    -- some work
    ROLLBACK TRAN sp1;   -- rolls back to savepoint, transaction continues
    -- more work
COMMIT;

Best practices

  • Keep transactions short. Long ones hold locks → blocking, deadlocks.
  • Don't do external calls (HTTP, queue) inside a transaction.
  • Set a query timeout / lock timeout.
  • Use SET XACT_ABORT ON to auto-rollback on errors.
  • Always handle errors with TRY/CATCH (Module 53).

Locks & Blocking

Lock modes

Lock granularity

  • Row-level — most fine-grained.
  • Page-level — 8 KB.
  • Extent-level — 8 pages.
  • Table-level.

The DB chooses based on operation size. Updating one row → row lock. Updating millions → table lock (lock escalation).

Detecting blocking

-- SQL Server: who's blocking whom
SELECT
    blocking_session_id,
    session_id AS blocked_session_id,
    wait_type,
    wait_time_ms,
    wait_resource,
    DB_NAME(database_id) AS db
FROM sys.dm_exec_requests
WHERE blocking_session_id <> 0;

-- Get the running query of a session
DBCC INPUTBUFFER(123);   -- session id from above

Common blocking causes

  • Long-running update / delete on a hot table.
  • Open transaction (someone forgot to COMMIT in SSMS).
  • Lock escalation to table level.
  • Wide reads (table scans) holding shared locks too long.
  • External call inside transaction extending lock duration.

Mitigations

  • Keep transactions short.
  • Add appropriate indexes (smaller scans, fewer locks).
  • Enable RCSI (Module 62).
  • Batch updates instead of one giant statement.
  • Use NOLOCK only when stale-OK and you understand the risks.

Lock hints

SELECT * FROM users WITH (READPAST);          -- skip locked rows
SELECT * FROM users WITH (HOLDLOCK);          -- equiv to SERIALIZABLE
SELECT * FROM users WITH (UPDLOCK);           -- take update lock for read
SELECT * FROM users WITH (NOLOCK);            -- read uncommitted (avoid)

UPDLOCK is useful for "select for update" — avoids deadlocks during read-then-write.

Module 61
Deadlocks

What a deadlock is

Two transactions wait for each other's locks. Neither can proceed. The DB picks a "victim" and rolls it back.

  T1: locks Row A, wants Row B
  T2: locks Row B, wants Row A
  → deadlock; one is killed

SQL Server's deadlock detection

A background process (lock monitor) checks every 5 seconds for cycles in the wait-for graph. On detection, picks the one with the lowest "deadlock priority" (or cheapest rollback) and aborts it. Victim's session gets error 1205.

How to make deadlocks rare

  1. Access tables in the same order across all transactions. T1 does A then B; T2 also does A then B. Cycle impossible.
  2. Keep transactions short.
  3. Use the right index — fewer rows locked.
  4. Lower isolation level when correctness allows.
  5. Enable RCSI — readers don't take locks.
  6. Use UPDLOCK on the initial read in read-then-write patterns.

Capturing deadlock details

-- Enable extended events to capture deadlock graphs
CREATE EVENT SESSION DeadlockCapture ON SERVER
ADD EVENT sqlserver.xml_deadlock_report
ADD TARGET package0.event_file (SET filename='C:\xel\deadlocks.xel');

ALTER EVENT SESSION DeadlockCapture ON SERVER STATE = START;

Or check the system_health session — it captures deadlocks by default.

Handling deadlocks in app code

// EF Core — retry on deadlock (error 1205)
for (int attempt = 1; attempt <= 3; attempt++)
{
    try
    {
        await _db.SaveChangesAsync();
        break;
    }
    catch (SqlException ex) when (ex.Number == 1205)
    {
        if (attempt == 3) throw;
        await Task.Delay(TimeSpan.FromMilliseconds(100 * attempt));
    }
}

Polly with retry-on-1205 does this neatly for you.

Lock escalation deadlocks

A common pattern: SQL Server escalates row locks to table locks at ~5000 locks. If two transactions both escalate concurrently, deadlock. Mitigations:

  • Smaller batches.
  • ALTER TABLE ... SET (LOCK_ESCALATION = DISABLE) for hot tables.

Module 62
Snapshot Isolation & RCSI

The problem with traditional locking

Readers block writers. Writers block readers. Reports running on the OLTP system grind everything to a halt. NOLOCK "fixes" it but allows dirty data.

The MVCC solution

Multi-Version Concurrency Control: each row stores its history in tempdb. Readers see a snapshot of committed data as of the start of their transaction (or statement). No shared locks needed. Writers don't block readers; readers don't block writers.

Two flavors in SQL Server

RCSI — Read Committed Snapshot Isolation

ALTER DATABASE EasyAudit SET READ_COMMITTED_SNAPSHOT ON;
-- Now READ COMMITTED uses snapshot reads — non-blocking

Database-wide flag. Each statement reads from a snapshot taken at statement start. Writers don't block readers.

SNAPSHOT isolation

ALTER DATABASE EasyAudit SET ALLOW_SNAPSHOT_ISOLATION ON;

-- In a session
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRAN;
-- ... reads see the data as of transaction start
COMMIT;

Transaction-scoped snapshot. Reads are consistent across the entire transaction.

Why turn it on

  • Eliminates most reader-writer blocking.
  • No dirty reads (unlike NOLOCK).
  • Reports run alongside OLTP without slowing it down.
  • Standard in Postgres, Oracle, MySQL InnoDB.

The cost

  • tempdb pressure — version store grows; size and tempdb on fast disk.
  • Long-running transactions hold versions longer → bloat.
  • Update conflicts (in SNAPSHOT, not RCSI) — if two transactions update the same row concurrently, second one fails. Retry.
  • 14 bytes added per row (version pointer).

Recommendation

Enable RCSI on most modern OLTP databases. It's been Postgres' default behavior forever. SQL Server's default is locking-based for legacy reasons, but RCSI is widely considered the right choice for new systems.

Optimistic concurrency with rowversion

CREATE TABLE products (
    id INT PRIMARY KEY,
    name NVARCHAR(100),
    price DECIMAL(10,2),
    row_version ROWVERSION   -- auto-increments on every update
);

-- Read
SELECT id, name, price, row_version FROM products WHERE id = 42;
-- Returns row_version = 0x00000000000007D1, say.

-- Update with optimistic check
UPDATE products
SET price = 99.99
WHERE id = 42 AND row_version = 0x00000000000007D1;

IF @@ROWCOUNT = 0
    THROW 50001, 'Concurrency conflict — someone else updated this row', 1;

Application reads a value with row_version, makes changes, sends the update with the original row_version. If someone else updated in between, row_version doesn't match → 0 rows updated → conflict.

Module 63
CTEs & Recursive Queries

What a CTE is

Common Table Expression — a named, temporary result set you reference within a single statement. WITH cte AS (...).

WITH active_users AS (
    SELECT id, name, country FROM users WHERE is_active = 1
),
order_counts AS (
    SELECT user_id, COUNT(*) AS cnt FROM orders GROUP BY user_id
)
SELECT u.name, u.country, COALESCE(o.cnt, 0) AS orders
FROM active_users u
LEFT JOIN order_counts o ON o.user_id = u.id;

Why CTEs

  • Readability — break complex queries into named steps.
  • Reuse — reference the CTE multiple times in the same statement.
  • Avoid temp tables for one-shot intermediate results.
  • Required for recursive queries.

CTE vs subquery

Functionally similar; CTEs read better. Performance is similar in modern optimizers — CTEs aren't materialized in SQL Server (except Postgres pre-12, which did materialize them).

Recursive CTEs

-- Get all descendants of category 5 in a hierarchy
WITH category_tree AS (
    -- Anchor: starting row
    SELECT id, name, parent_id, 0 AS level
    FROM categories
    WHERE id = 5

    UNION ALL

    -- Recursive part: children of previous level
    SELECT c.id, c.name, c.parent_id, ct.level + 1
    FROM categories c
    INNER JOIN category_tree ct ON c.parent_id = ct.id
)
SELECT * FROM category_tree
ORDER BY level, name
OPTION (MAXRECURSION 100);   -- safety cap

Recursive CTE structure

  1. Anchor query — base case (no self-reference).
  2. UNION ALL.
  3. Recursive query — references the CTE itself.

Default max recursion is 100. Use OPTION (MAXRECURSION n) to change. 0 = unlimited (be careful!).

Other recursive use cases

  • Generate a date range: anchor = start date, recursive = +1 day until end.
  • Climb up to root: anchor = leaf, recursive = parent.
  • Numbered list 1..N: anchor = 1, recursive = +1.
  • Bill-of-materials explosion in manufacturing.

Generate a date range

WITH dates AS (
    SELECT CAST('2026-01-01' AS DATE) AS d
    UNION ALL
    SELECT DATEADD(DAY, 1, d) FROM dates
    WHERE d < '2026-12-31'
)
SELECT d FROM dates
OPTION (MAXRECURSION 366);

Module 64
Pivoting & Unpivoting

The problem

Convert rows to columns (pivot) or columns to rows (unpivot). Common in reporting.

Source data

  sales
  ┌─────────┬───────┬────────┐
  │ region  │ month │ amount │
  ├─────────┼───────┼────────┤
  │ North   │ Jan   │  100   │
  │ North   │ Feb   │  150   │
  │ South   │ Jan   │   80   │
  │ South   │ Feb   │  120   │
  └─────────┴───────┴────────┘

PIVOT — to columns

SELECT region,
       [Jan], [Feb], [Mar]
FROM (
    SELECT region, month, amount FROM sales
) src
PIVOT (
    SUM(amount) FOR month IN ([Jan], [Feb], [Mar])
) AS pvt;
Result:
  ┌─────────┬─────┬─────┬─────┐
  │ region  │ Jan │ Feb │ Mar │
  ├─────────┼─────┼─────┼─────┤
  │ North   │ 100 │ 150 │ NULL│
  │ South   │  80 │ 120 │ NULL│
  └─────────┴─────┴─────┴─────┘

PIVOT alternative — CASE WHEN aggregation

SELECT region,
       SUM(CASE WHEN month = 'Jan' THEN amount END) AS Jan,
       SUM(CASE WHEN month = 'Feb' THEN amount END) AS Feb,
       SUM(CASE WHEN month = 'Mar' THEN amount END) AS Mar
FROM sales
GROUP BY region;

Often clearer than PIVOT, more flexible (can use any aggregate, multiple aggregates).

UNPIVOT — to rows

-- Suppose we have wide table:
-- monthly_sales(region, jan_sales, feb_sales, mar_sales)

SELECT region, month, sales
FROM monthly_sales
UNPIVOT (
    sales FOR month IN (jan_sales, feb_sales, mar_sales)
) AS unp;

Dynamic PIVOT

When the columns to pivot aren't known at write time:

DECLARE @cols NVARCHAR(MAX), @sql NVARCHAR(MAX);

SELECT @cols = STRING_AGG(QUOTENAME(month), ',')
FROM (SELECT DISTINCT month FROM sales) m;

SET @sql = N'
    SELECT region, ' + @cols + N'
    FROM (SELECT region, month, amount FROM sales) src
    PIVOT (SUM(amount) FOR month IN (' + @cols + N')) p';

EXEC sp_executesql @sql;

Module 65
JSON Support

Storing JSON

SQL Server has no native JSON type. Store as NVARCHAR(MAX); use functions to query. Postgres has JSON and JSONB types (use JSONB).

CREATE TABLE events (
    id INT IDENTITY PRIMARY KEY,
    payload NVARCHAR(MAX) NOT NULL CHECK (ISJSON(payload) = 1),
    created_at DATETIME2 DEFAULT SYSUTCDATETIME()
);

INSERT INTO events (payload) VALUES
    ('{"type":"login","user":"alice","ip":"1.2.3.4"}'),
    ('{"type":"click","user":"bob","element":"button-x"}');

JSON functions in T-SQL

-- Extract a scalar value
SELECT JSON_VALUE(payload, '$.user')         -- 'alice'
FROM events;

-- Extract a sub-object or array
SELECT JSON_QUERY(payload, '$.tags')          -- the array as text

-- Modify
SELECT JSON_MODIFY(payload, '$.user', 'carol') FROM events;

-- Test if path exists
SELECT JSON_PATH_EXISTS(payload, '$.user')   -- 1 or 0

-- Convert JSON array to rows
SELECT *
FROM OPENJSON('[{"name":"Alice"},{"name":"Bob"}]')
WITH (name NVARCHAR(100) '$.name');

Filtering by JSON content

SELECT * FROM events
WHERE JSON_VALUE(payload, '$.user') = 'alice';

-- Indexable: extract via computed column
ALTER TABLE events ADD user_name AS JSON_VALUE(payload, '$.user') PERSISTED;
CREATE INDEX IX_events_user ON events(user_name);

Postgres — better JSON support

-- JSONB column
CREATE TABLE events (
    id SERIAL PRIMARY KEY,
    payload JSONB NOT NULL
);

-- Operators
SELECT payload->>'user' FROM events;            -- text extract
SELECT payload->'tags'->>0 FROM events;          -- nested array
SELECT * FROM events WHERE payload @> '{"type":"login"}';   -- containment

-- GIN index for fast containment queries
CREATE INDEX idx_events_payload ON events USING GIN (payload);

When to use JSON in SQL

  • Schema-flexible attributes (event payloads, settings, audit data).
  • Sparse data — many possible attributes, few used per row.
  • Versioned data — different shape per version.

When NOT to use JSON columns

  • Data you query/filter on heavily — real columns are faster.
  • Anything with relationships (FKs).
  • Highly structured data — use a normalized schema.
  • Don't use JSON to "avoid migrations" — it just defers schema problems.

Full-Text Search

Why LIKE '%word%' isn't enough

  • Cannot use indexes (leading wildcard).
  • No relevance ranking.
  • No stemming (run/runs/running treated as different).
  • No tolerance for typos.

SQL Server Full-Text Search

-- Create full-text catalog
CREATE FULLTEXT CATALOG ft_catalog AS DEFAULT;

-- Index a column
CREATE FULLTEXT INDEX ON articles (title, body)
KEY INDEX PK_articles
WITH STOPLIST = SYSTEM;

-- Query
SELECT * FROM articles
WHERE CONTAINS(body, 'database OR SQL');

-- Phrase search
WHERE CONTAINS(body, '"sliding window"')

-- Proximity
WHERE CONTAINS(body, 'NEAR((cat, dog), 5)')

-- With ranking
SELECT a.id, a.title, kt.rank
FROM articles a
INNER JOIN CONTAINSTABLE(articles, body, 'database') kt ON a.id = kt.[KEY]
ORDER BY kt.rank DESC;

Postgres tsvector

-- Add tsvector column
ALTER TABLE articles ADD COLUMN search_vec tsvector;

-- Populate
UPDATE articles SET search_vec = to_tsvector('english', title || ' ' || body);

-- Index it
CREATE INDEX idx_articles_search ON articles USING GIN(search_vec);

-- Query
SELECT * FROM articles
WHERE search_vec @@ to_tsquery('english', 'database & sql');

When to use a separate search engine

SQL full-text is fine for moderate corpora and simple queries. For:

  • Faceted search (filters + counts per facet).
  • Autocomplete with millions of entries.
  • Cross-language relevance, fuzzy matching.
  • Vector / semantic search.
  • Heavy search load.

...use Elasticsearch / OpenSearch / Algolia. Sync your data via CDC or outbox.

Module 67
Partitioning

The problem

A 1-billion-row table is hard to manage. Adding columns, rebuilding indexes, archiving old data — all expensive. Backups grow. Queries scan more.

Partitioning splits one logical table into many physical chunks

Rows are distributed by a partition key (usually a date). Each partition is its own physical structure. Queries that filter on the partition key only touch relevant partitions ("partition elimination").

  orders (logical, partitioned by created_at)
    ├── partition_2024  (rows where 2024-01-01 ≤ created_at < 2025-01-01)
    ├── partition_2025  (...)
    └── partition_2026  (...)

SQL Server partitioning

-- 1. Partition function (the boundaries)
CREATE PARTITION FUNCTION pfYears (DATE)
AS RANGE RIGHT FOR VALUES ('2024-01-01', '2025-01-01', '2026-01-01');

-- 2. Partition scheme (where each partition lives)
CREATE PARTITION SCHEME psYears
AS PARTITION pfYears ALL TO ([PRIMARY]);

-- 3. Create the partitioned table
CREATE TABLE orders (
    id INT,
    created_at DATE,
    user_id INT,
    amount DECIMAL(10,2)
) ON psYears(created_at);

Partition operations

  • SWITCH — instantly move a partition's data to/from another table (e.g., archive last year's orders to a separate table).
  • SPLIT / MERGE — add or combine boundaries.
  • TRUNCATE PARTITION — clear one partition.

What partitioning helps with

  • Sliding window archival — drop oldest partition, add a new one.
  • Faster queries when filtered on the partition key.
  • Per-partition maintenance (rebuild indexes one partition at a time).
  • Per-partition backups.

What partitioning DOES NOT help with

  • Queries that don't filter by partition key — still scan all partitions.
  • Single-row lookups by primary key.
  • "Performance" in general — without alignment to access pattern, partitioning can hurt.

When to partition

  • Tables with hundreds of millions of rows + clear time-based access pattern.
  • Need for fast bulk archive / delete.
  • Long-running maintenance (index rebuilds) need to be partition-by-partition.

Don't reach for partitioning to "speed up everything" — it's an operational tool more than a performance one.

Module 68
Temporal Tables

Built-in time travel

SQL Server 2016+ has system-versioned temporal tables — automatic history tracking without triggers.

CREATE TABLE users (
    id INT IDENTITY PRIMARY KEY,
    email NVARCHAR(255),
    name NVARCHAR(100),
    valid_from DATETIME2 GENERATED ALWAYS AS ROW START,
    valid_to   DATETIME2 GENERATED ALWAYS AS ROW END,
    PERIOD FOR SYSTEM_TIME (valid_from, valid_to)
)
WITH (SYSTEM_VERSIONING = ON (HISTORY_TABLE = dbo.users_history));

Now every UPDATE / DELETE writes the previous version into users_history automatically.

Querying history

-- All current rows (the regular table)
SELECT * FROM users;

-- All historical rows (the history table)
SELECT * FROM users_history;

-- State as of a specific time
SELECT * FROM users
FOR SYSTEM_TIME AS OF '2026-04-01 10:00:00'
WHERE id = 42;

-- Changes during a time range
SELECT * FROM users
FOR SYSTEM_TIME BETWEEN '2026-04-01' AND '2026-04-30'
WHERE id = 42;

-- All versions of one row
SELECT * FROM users
FOR SYSTEM_TIME ALL
WHERE id = 42
ORDER BY valid_from;

Why temporal tables are amazing

  • Audit trail without triggers.
  • "What did this row look like on date X?" — built-in.
  • Undo / restore.
  • Compliance reporting.
  • No application code changes needed.

Costs

  • Storage roughly doubles.
  • Updates write twice.
  • Schema changes need to propagate to the history table.

Cleanup

-- Add a retention policy (SQL Server 2017+)
ALTER TABLE users
    SET (SYSTEM_VERSIONING = ON (HISTORY_TABLE = dbo.users_history,
                                   HISTORY_RETENTION_PERIOD = 7 YEARS));

Postgres equivalent

No native equivalent. Use the temporal_tables extension, or implement via triggers, or use CDC.

Backups & Recovery

SQL Server recovery models

ModelBehavior
SIMPLELog truncated automatically. Only full + differential backups. RPO = last full/diff.
FULL (default for prod)Log retained until backed up. Allows point-in-time recovery.
BULK_LOGGEDLike FULL but bulk operations are minimally logged. Niche.

The three backup types

-- Full backup — entire DB
BACKUP DATABASE EasyAudit
TO DISK = 'D:\Backups\EasyAudit_Full.bak'
WITH COMPRESSION, CHECKSUM;

-- Differential — changes since last full
BACKUP DATABASE EasyAudit
TO DISK = 'D:\Backups\EasyAudit_Diff.bak'
WITH DIFFERENTIAL, COMPRESSION;

-- Transaction log — all log entries since last log backup
BACKUP LOG EasyAudit
TO DISK = 'D:\Backups\EasyAudit_Log.trn'
WITH COMPRESSION;

Common backup strategy

  • Full nightly.
  • Differential every 6 hours.
  • Log every 15 minutes.

RPO with this scheme: ~15 min. RTO: ~30 min if practiced.

Restore

-- Restore full
RESTORE DATABASE EasyAudit FROM DISK = 'D:\Backups\Full.bak'
WITH NORECOVERY, REPLACE;

-- Apply differential
RESTORE DATABASE EasyAudit FROM DISK = 'D:\Backups\Diff.bak'
WITH NORECOVERY;

-- Apply logs sequentially
RESTORE LOG EasyAudit FROM DISK = 'D:\Backups\Log1.trn' WITH NORECOVERY;
RESTORE LOG EasyAudit FROM DISK = 'D:\Backups\Log2.trn' WITH NORECOVERY;

-- Final: bring online
RESTORE LOG EasyAudit FROM DISK = 'D:\Backups\LogN.trn'
WITH RECOVERY, STOPAT = '2026-05-07 14:23:00';

Backup checklist

  • Backups offsite (different region / different account).
  • Backups encrypted.
  • Backups TESTED — restore quarterly to a clean instance.
  • Retention covers worst-case discovery time (often 30 days minimum).
  • Backups monitored — failed backup = alert.
  • Compression enabled (saves a lot).
  • CHECKSUM verifies on read.

Cloud-managed shortcuts

Azure SQL DB, AWS RDS, Cloud SQL: managed automated backups, point-in-time restore, geo-redundant backups. Just configure retention and trust the cloud provider.

Don't store backups in the same place as the data

The classic disaster: server room fire takes out both DB and backups. Always offsite.

Replication Overview

Why replicate

  • HA — failover when primary dies.
  • Read scaling — many replicas serve reads.
  • Geo-distribution — replica close to users.
  • Backups — take from replica without impacting primary.
  • DR — secondary in a different region.

SQL Server options

TechWhat it is
Always On Availability GroupsModern HA + DR. Sync or async replicas. Automatic failover. Up to 8 replicas.
Log ShippingOlder, simpler. Periodic log backup → restore on secondary. Manual failover.
Database MirroringDeprecated. Was replaced by AGs.
Replication (transactional, snapshot, merge)Logical replication of objects. More complex, more flexible.

Always On AG basics

  • Group of databases that fail over together.
  • 1 primary + up to 8 secondaries (1 sync auto-failover, others sync or async).
  • Listener provides single endpoint that routes to current primary.
  • Read-intent connections can route to secondaries (read replicas).

Sync vs async replication trade-off

SyncAsync
No data loss on failoverPossibly lose recent commits
Higher write latency (waits for replica ack)Low write latency
Local replicas only (low-latency network)Cross-region OK

Postgres replication

  • Streaming replication (physical) — primary streams WAL to replicas.
  • Logical replication — per-table, can replicate to different schemas.
  • Tools: Patroni for HA orchestration; pg_auto_failover.

MySQL replication

  • Statement-based, row-based, mixed.
  • Group Replication (multi-primary).
  • Galera Cluster (synchronous multi-master).

Architectural rule

Always have at least one replica in production. Never run a single-node DB for anything important. Cloud-managed services do this for you (AWS RDS Multi-AZ, Azure SQL geo-replication, GCP Cloud SQL HA).

Schemas as security boundaries

Group related objects into schemas; grant per-schema:

CREATE SCHEMA reporting;

-- Now every table created in reporting.* is accessible
CREATE TABLE reporting.daily_summary (...);

Principle of least privilege

  • App connection user gets ONLY what the app needs.
  • Read-only reports → read-only user.
  • DBA tasks → separate elevated login.
  • Never use sa from applications.

Row-level security (T-SQL)

-- Filter predicate: each user only sees their own rows
CREATE FUNCTION dbo.fn_user_filter(@UserId INT)
RETURNS TABLE
WITH SCHEMABINDING
AS RETURN
    SELECT 1 AS allowed
    WHERE @UserId = CAST(SESSION_CONTEXT(N'user_id') AS INT) OR IS_ROLEMEMBER('db_owner') = 1;

CREATE SECURITY POLICY dbo.user_filter
ADD FILTER PREDICATE dbo.fn_user_filter(user_id) ON dbo.documents
WITH (STATE = ON);

The policy applies to every query — users automatically only see their rows. Multi-tenant systems benefit hugely.

Always-Encrypted, Dynamic Data Masking, TDE

  • TDE (Transparent Data Encryption) — encrypts data files at rest. On by default in Azure SQL.
  • Always Encrypted — encryption keys held by client; DB never sees plaintext for sensitive columns.
  • Dynamic Data Masking — non-privileged users see masked values (e.g., ****-****-****-1234).

SQL Injection Prevention

The vulnerability

User input concatenated into SQL → attacker can break out and execute arbitrary SQL.

Vulnerable

// C# (NEVER do this)
string sql = $"SELECT * FROM users WHERE email = '{email}'";
// User submits: '; DROP TABLE users; --
// Becomes: SELECT * FROM users WHERE email = ''; DROP TABLE users; --'

Safe — parameterized

// C#
using var cmd = new SqlCommand(
    "SELECT * FROM users WHERE email = @email", conn);
cmd.Parameters.AddWithValue("@email", email);
// Driver handles escaping; user input is never SQL.

Always parameterize

  • EF Core / Dapper — parameterize automatically.
  • SqlCommand + Parameters in raw ADO.NET.
  • Stored procedures with parameters — by definition parameterized.

The myth: stored procs prevent injection

SPs alone don't. If the SP uses dynamic SQL with concatenated input, you're vulnerable inside the SP:

Vulnerable SP

CREATE PROCEDURE Search @Term NVARCHAR(100)
AS BEGIN
    DECLARE @sql NVARCHAR(MAX);
    SET @sql = 'SELECT * FROM users WHERE name = ''' + @Term + '''';
    EXEC(@sql);   -- INJECTABLE
END

Safe — sp_executesql with parameters

CREATE PROCEDURE Search @Term NVARCHAR(100)
AS BEGIN
    DECLARE @sql NVARCHAR(MAX);
    SET @sql = 'SELECT * FROM users WHERE name = @t';
    EXEC sp_executesql @sql,
         N'@t NVARCHAR(100)',
         @t = @Term;
END

Other defensive measures

  • Least privilege DB user — even if injected, attacker can't drop tables if user only has SELECT.
  • Input validation — for things that should be numeric, parse to int first.
  • QUOTENAME — for legitimate dynamic identifiers (table/column names) when you can't parameterize.
  • WAF — caught at the edge for obvious payloads.
  • ORM — using EF Core / Dapper correctly forces parameterization.

QUOTENAME for safe dynamic objects

DECLARE @TableName NVARCHAR(100) = N'users';
DECLARE @sql NVARCHAR(MAX) =
    N'SELECT * FROM ' + QUOTENAME(@TableName);
EXEC sp_executesql @sql;
-- QUOTENAME wraps in [], escapes any embedded ]

Test for it

  • OWASP ZAP, sqlmap — automated injection scanners.
  • Code review every EXEC() and string concatenation in SQL.
  • Static analysis tools (Roslyn analyzers) flag risky patterns.

1. Audit every FK has an index

-- Find FKs without supporting indexes
SELECT
    OBJECT_NAME(fk.parent_object_id) AS table_name,
    fk.name AS fk_name,
    cols.column_name
FROM sys.foreign_keys fk
JOIN sys.foreign_key_columns fkc ON fkc.constraint_object_id = fk.object_id
JOIN sys.columns c ON c.object_id = fkc.parent_object_id AND c.column_id = fkc.parent_column_id
CROSS APPLY (SELECT c.name AS column_name) cols
WHERE NOT EXISTS (
    SELECT 1
    FROM sys.index_columns ic
    JOIN sys.indexes i ON i.object_id = ic.object_id AND i.index_id = ic.index_id
    WHERE ic.object_id = fkc.parent_object_id
      AND ic.column_id = fkc.parent_column_id
      AND ic.key_ordinal = 1
);

For each result: CREATE INDEX IX_table_fkcol ON table(fkcol);

2. Enable RCSI (Module 62)

ALTER DATABASE EasyAudit SET READ_COMMITTED_SNAPSHOT ON;

Eliminates reader/writer blocking — huge win for OLTP + reporting on the same DB. Almost always a win for modern apps. Test in dev first.

3. Add filtered indexes for soft-delete pattern

-- For every "hot read" table with soft delete:
CREATE INDEX IX_users_email_active
ON users(email)
WHERE deleted_at IS NULL;

CREATE INDEX IX_orders_user_active
ON orders(user_id, created_at DESC)
INCLUDE (amount, status)
WHERE deleted_at IS NULL;

4. Index audit on slow query suspects

-- Top 20 most expensive cached queries
SELECT TOP 20
    qs.execution_count,
    qs.total_elapsed_time / 1000 / qs.execution_count AS avg_ms,
    qs.total_logical_reads / qs.execution_count AS avg_reads,
    SUBSTRING(st.text, qs.statement_start_offset/2,
              CASE WHEN qs.statement_end_offset = -1
                   THEN LEN(st.text)
                   ELSE qs.statement_end_offset/2 END) AS sql
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) st
ORDER BY qs.total_elapsed_time DESC;

Top 10 results = your hot list for optimization. Check actual plans, identify missing indexes, fix.

5. Capture missing index suggestions

SELECT TOP 20
    DB_NAME(mid.database_id) AS db,
    OBJECT_NAME(mid.object_id, mid.database_id) AS table_name,
    migs.user_seeks,
    CAST(migs.avg_user_impact AS INT) AS impact_pct,
    'CREATE INDEX IX_' +
    OBJECT_NAME(mid.object_id, mid.database_id) + '_'
    + REPLACE(REPLACE(REPLACE(ISNULL(mid.equality_columns,'') + '_' + ISNULL(mid.inequality_columns,''), ', ', '_'), '[', ''), ']', '')
    + ' ON ' + mid.statement
    + ' (' + ISNULL(mid.equality_columns + ',', '') + ISNULL(mid.inequality_columns, '') + ')'
    + ISNULL(' INCLUDE (' + mid.included_columns + ')', '') AS suggested_index
FROM sys.dm_db_missing_index_details mid
JOIN sys.dm_db_missing_index_groups mig ON mig.index_handle = mid.index_handle
JOIN sys.dm_db_missing_index_group_stats migs ON mig.index_group_handle = migs.group_handle
ORDER BY migs.user_seeks * migs.avg_user_impact DESC;

Don't blindly create them all — review each. Some duplicate existing ones; some have impact too low to matter.

6. Index maintenance job

Schedule weekly:

-- Reorganize 10–30%; rebuild > 30%
DECLARE @sql NVARCHAR(MAX) = '';

SELECT @sql = @sql +
    'ALTER INDEX ' + QUOTENAME(i.name) + ' ON ' + QUOTENAME(s.name) + '.' + QUOTENAME(o.name) +
    CASE WHEN ips.avg_fragmentation_in_percent > 30 THEN ' REBUILD' ELSE ' REORGANIZE' END + ';' + CHAR(10)
FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'LIMITED') ips
JOIN sys.indexes i ON i.object_id = ips.object_id AND i.index_id = ips.index_id
JOIN sys.objects o ON o.object_id = i.object_id
JOIN sys.schemas s ON s.schema_id = o.schema_id
WHERE ips.avg_fragmentation_in_percent > 10
  AND ips.page_count > 1000
  AND i.name IS NOT NULL;

EXEC sp_executesql @sql;

EasyAudit Optimization Checklist

Per-query checklist

Before merging any SQL change to production:

  • ☐ No SELECT * — explicit columns.
  • ☐ All FKs / WHERE / JOIN columns indexed.
  • ☐ No function on an indexed column in WHERE (SARGable).
  • ☐ Correct join type (INNER/LEFT) for the data shape.
  • ☐ Pagination uses keyset, not OFFSET, for > 1000 rows.
  • ☐ Aggregations don't run on the entire table when not needed.
  • ☐ NOLOCK only when explicitly justified (and consider RCSI alternative).
  • ☐ Estimated plan reviewed for table scans on > 10k rows.
  • ☐ Parameterized — no string concatenation.
  • ☐ No N+1 from app code.

Per-stored-procedure checklist

  • ☐ SET NOCOUNT ON; at the top.
  • ☐ SET XACT_ABORT ON; if it does writes.
  • ☐ TRY/CATCH around any transaction.
  • ☐ Always check @@TRANCOUNT > 0 before ROLLBACK.
  • ☐ No external HTTP / network calls inside transactions.
  • ☐ Parameter sniffing addressed if needed (RECOMPILE, OPTIMIZE FOR).
  • ☐ TVPs for list inputs, not giant IN clauses.
  • ☐ Documented at the top: purpose, params, behaviors.

Per-table checklist

  • ☐ Has a clustered PK (no heaps).
  • ☐ Created / updated audit columns.
  • ☐ Soft delete column (if applicable).
  • ☐ row_version for optimistic concurrency on hot rows.
  • ☐ Foreign keys with appropriate ON DELETE behavior.
  • ☐ All FK columns indexed.
  • ☐ Indexes match WHERE / ORDER BY / GROUP BY patterns.
  • ☐ No NVARCHAR(MAX) for things that fit in NVARCHAR(N).
  • ☐ Correct numeric type (DECIMAL for money, never FLOAT).
  • ☐ DATETIME2 (not old DATETIME), UTC stored.
  • ☐ Tenant ID column (multi-tenant).

Daily / weekly ops

  • ☐ Slow query log reviewed.
  • ☐ Deadlock graph reviewed.
  • ☐ Disk usage trending OK.
  • ☐ Backup ran & succeeded.
  • ☐ Index fragmentation report scanned.

Monthly

  • ☐ Backup restore drill in dev.
  • ☐ Index usage stats — drop unused indexes.
  • ☐ Stored procedure plan cache reviewed for ones cached for ages with bad plans.
  • ☐ Capacity trend — when do we run out of disk / RAM?

Quarterly

  • ☐ Full security audit (logins, roles, permissions).
  • ☐ Failover drill if you have replicas / AGs.
  • ☐ Schema review — any tech debt growing?
  • ☐ Patch level current.

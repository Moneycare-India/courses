Module 1
What & Why of Docker

What is Docker?

Docker is a platform for packaging applications as containers — lightweight, portable, isolated processes that run anywhere a Docker (or any OCI-compliant) runtime exists.

A container bundles your code, runtime, libraries, and OS userland into one immutable image. The kernel comes from the host. Containers start in milliseconds, share OS resources, and run identically on any machine.

Docker, Inc. introduced the technology in 2013, but the underlying primitives (Linux namespaces, cgroups, union filesystems) existed earlier. Docker made them easy. The OCI (Open Container Initiative) now standardizes the image and runtime format — Docker is one implementation; others include containerd, CRI-O, podman.

Why containers won

  • "It works on my machine" dies — the same image runs everywhere.
  • Fast startup — milliseconds vs minutes for VMs.
  • Dense packing — 100s of containers per host vs dozens of VMs.
  • Immutable artifacts — image hash = exact deployment.
  • DevOps friendly — same artifact through dev, CI, prod.
  • Microservices enabler — each service in its own image.

What problem does Docker solve?

Before containers, deploying meant: provision servers, install OS, install language runtimes, install dependencies, copy code, configure, hope. Drift between dev/staging/prod was constant. Docker eliminates that — the image carries everything.

Module 3
Mental Model

A container is just a process (or a few processes) on the host kernel, but with these views isolated from the rest of the system:

  • PID namespace — sees only its own processes; PID 1 inside is your app.
  • Mount namespace — its own root filesystem (the image).
  • Network namespace — own interfaces, IP, ports.
  • UTS namespace — own hostname.
  • IPC namespace — own message queues, shared memory.
  • User namespace — optional UID/GID remapping.
  • Cgroups — CPU, memory, I/O resource limits.

The image provides the filesystem; the kernel runs the process; namespaces and cgroups isolate it. That's the entire trick.

Module 4
Core Vocabulary

Image
An immutable, read-only template — a tarball of filesystem layers + metadata. Identified by a hash and optionally tagged (nginx:1.25).
Container
A running (or stopped) instance of an image. Adds a thin writable layer on top.
Layer
One filesystem diff. Layers are cached and shared between images.
Dockerfile
Text recipe describing how to build an image, line by line.
Registry
A server hosting images. Docker Hub, GHCR, ECR, GCR, ACR, Harbor.
Repository
Named collection of images in a registry — e.g., nginx, mycorp/app.
Tag
A human-friendly label on an image — :1.25, :latest. Mutable.
Digest
The image's content hash (sha256:...). Immutable. Pin in production.
Volume
Persistent storage, managed by Docker, lives outside the container layer.
Bind mount
Mount a host path directly into a container.
Network
Virtual network connecting containers; default is bridge.
Compose
Tool to define and run multi-container apps from a YAML file.
Daemon (dockerd)
Background service that builds and runs containers.
OCI
Open Container Initiative — standard for image and runtime formats.

Layers, top to bottom:

  1. docker CLI — talks REST to the daemon.
  2. dockerd — orchestrates images, containers, networks, volumes.
  3. containerd — manages container lifecycles, pulls images.
  4. runc — actually creates the namespaces/cgroups and execs your process.

Kubernetes uses containerd or CRI-O directly, skipping the Docker CLI/daemon — the actual containers and images are the same.

Module 6
Images Deep Dive

Layers

An image is a stack of read-only layers. Each Dockerfile instruction that changes the filesystem creates a new layer. Layers are content-addressed (sha256). Multiple images sharing a base layer use the same bytes on disk.

Image: myapp:1.0
┌──────────────────────────────────────────┐
│  L4: COPY app.dll /app/                  │  ← thin top layer
├──────────────────────────────────────────┤
│  L3: RUN apt-get install -y curl         │
├──────────────────────────────────────────┤
│  L2: WORKDIR /app                        │  (metadata only)
├──────────────────────────────────────────┤
│  L1: FROM mcr.microsoft.com/dotnet/aspnet│  ← base layer (shared)
└──────────────────────────────────────────┘

Image manifest

An OCI image is a JSON manifest pointing at:

  • A config blob (entrypoint, env, exposed ports, labels, layer digests).
  • Layer blobs (each is a tarball, usually gzipped).

Inspecting

docker images                          # list local images
docker image inspect nginx:1.25        # full JSON
docker history nginx:1.25              # layer-by-layer
docker manifest inspect nginx:1.25     # multi-arch manifest

Tags vs digests

nginx:1.25 is a moving target — it can be re-pushed. nginx@sha256:abc123... is immutable. In production, pin to digests for reproducibility.

Multi-arch images

One tag can refer to a manifest list with images for amd64, arm64, etc. The right one is selected at pull. Use docker buildx build --platform linux/amd64,linux/arm64.

The thin writable layer

Each container gets a writable layer on top of the image. Changes go there; the image stays immutable. When the container is removed, the writable layer is gone — that's why state belongs in volumes.

PID 1 matters

The process you run as ENTRYPOINT/CMD is PID 1 inside the container. PID 1 has special responsibilities — handle signals (SIGTERM for graceful shutdown), reap zombie children. Many runtimes don't do this well; use tini or --init as a tiny init shim.

Restart policies

docker run --restart=always nginx             # always restart
docker run --restart=unless-stopped nginx     # restart unless I stopped it
docker run --restart=on-failure:3 nginx       # up to 3 times on non-zero exit
docker run --restart=no nginx                 # default: don't restart

Resource limits

docker run --cpus=1.5 --memory=512m --memory-swap=512m nginx
docker run --pids-limit=200 nginx
docker run --read-only nginx                  # immutable filesystem

Module 8
Dockerfile Reference

Each instruction either modifies the filesystem (creates a layer) or sets metadata.

InstructionPurpose
FROMBase image. Required first instruction.
WORKDIRSet working directory; created if missing.
COPYCopy files from build context into image.
ADDLike COPY but also URL fetch & tar auto-extract. Prefer COPY.
RUNRun a command at build time, commit result as a layer.
ENVSet environment variable (persists at runtime).
ARGBuild-time variable (not at runtime).
EXPOSEDocument a port (informational, doesn't publish).
VOLUMEDeclare a path expected to hold persistent data.
USERRun subsequent commands & the container as this user.
HEALTHCHECKHow Docker tests if container is healthy.
ENTRYPOINTThe fixed command for the container.
CMDDefault args (or default command if no ENTRYPOINT).
LABELMetadata key=value pairs.

Minimal example

FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
EXPOSE 3000
USER node
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD wget --quiet --tries=1 --spider http://localhost:3000/health || exit 1
CMD ["node", "server.js"]

ENTRYPOINT vs CMD

  • CMD only: docker run img uses the CMD. docker run img bash overrides it.
  • ENTRYPOINT only: every docker run img X calls ENTRYPOINT with X as args.
  • Both: ENTRYPOINT is fixed, CMD is default args (overridable).

Build context

docker build . — the dot is the context: everything in that directory is sent to the daemon. Use .dockerignore to exclude (huge speedup):

# .dockerignore
.git
node_modules
*.log
bin/
obj/
.env

Layer caching

Docker caches each layer. If a Dockerfile line and its inputs are unchanged, the cached layer is reused. Order instructions from least-changing to most-changing for fast rebuilds:

  • 1. Base image and OS deps (rarely change)
  • 2. Language deps (manifest files)
  • 3. Install deps
  • 4. Copy source code (changes most)

Module 9
Multi-Stage Builds

Build with one image (with compilers, SDKs), copy artifacts to a slim runtime image. Final image stays small.

.NET 8 example

# --- Stage 1: build ---
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src

COPY ["central-backend/AuditSoftware.csproj", "central-backend/"]
RUN dotnet restore "central-backend/AuditSoftware.csproj"

COPY . .
WORKDIR "/src/central-backend"
RUN dotnet publish "AuditSoftware.csproj" -c Release -o /app/publish \
    --no-restore /p:UseAppHost=false

# --- Stage 2: runtime ---
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS runtime
WORKDIR /app
COPY --from=build /app/publish .

EXPOSE 8080
ENV ASPNETCORE_URLS=http://+:8080
USER app
ENTRYPOINT ["dotnet", "AuditSoftware.dll"]

Result: build stage has the full SDK (~700 MB); runtime image has only the ASP.NET runtime (~220 MB). The final image is what ships.

Node example

FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:alpine AS runtime
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80

Distroless / minimal images

For maximum slimness, use gcr.io/distroless/dotnet-runtime, gcr.io/distroless/nodejs, or Chainguard images. They contain only the runtime — no shell, no package manager, no curl. Excellent for security; harder to debug.

Public registries

  • Docker Hub — docker.io. Default. Rate-limited for anonymous pulls.
  • GitHub Container Registry — ghcr.io. Free for public images. Tied to GitHub auth.
  • Microsoft Container Registry — mcr.microsoft.com. Hosts official .NET, SQL Server, etc.
  • Quay.io, Google Artifact Registry, Amazon ECR, Azure ACR.

DriverUse case

Module 13
Env Vars & Secrets

Setting env vars

docker run -e DB_HOST=db -e DB_USER=admin myapp           # individual
docker run --env-file .env myapp                          # from file

What's wrong with env vars for secrets?

  • Visible in docker inspect.
  • Often leak to logs.
  • Show in /proc/PID/environ.

Better: Docker secrets (Swarm) / mounted files

Treat secrets as files mounted into the container, not env vars:

# Read secret in your app from a path:
cat /run/secrets/db_password

In compose with Swarm:

services:
  api:
    image: myapi
    secrets: [ db_password ]
secrets:
  db_password:
    file: ./db_password.txt

For Kubernetes, use Secrets (Module 30) — same idea, mounted as files or env.

Module 14
Docker Compose

Docker Compose declares a multi-container application in a single YAML file. One command brings it up.

Basic compose.yml

version: '3.8'
services:
  web:
    build: ./web                       # build from Dockerfile
    image: myorg/web:1.0
    ports: [ "8080:8080" ]
    environment:
      DB_HOST: db
      DB_USER: app
      DB_PASS_FILE: /run/secrets/db_pass
    secrets: [ db_pass ]
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped

  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_pass
      POSTGRES_USER: app
    volumes: [ pgdata:/var/lib/postgresql/data ]
    secrets: [ db_pass ]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 5s
      retries: 5

volumes:
  pgdata:

secrets:
  db_pass:
    file: ./db_pass.txt

Daily commands

docker compose up -d              # build + run in background
docker compose ps                 # status
docker compose logs -f web        # tail logs
docker compose exec web sh        # shell into web container
docker compose stop               # stop containers
docker compose down               # stop + remove containers, network
docker compose down -v            # ALSO remove volumes (destructive)
docker compose pull               # pull updated images
docker compose build --no-cache   # rebuild from scratch

Profiles

Define optional services (e.g., dev tools) and only start them when asked:

services:
  pgadmin:
    image: dpage/pgadmin4
    profiles: [ dev ]
# Start with: docker compose --profile dev up

Multiple compose files

docker compose -f compose.yml -f compose.prod.yml up -d

The second file overrides/extends the first. Common pattern: compose.yml base, compose.dev.yml for dev overrides, compose.prod.yml for prod.

Health & Dependencies

HEALTHCHECK

HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD curl -f http://localhost:8080/health || exit 1

    condition: service_healthy        # waits for healthcheck

Wait-for patterns

Compose depends_on only waits for container start, not for the app inside being ready, unless you use service_healthy. For complex cases, use a tiny script like wait-for-it.sh or dockerize.

Module 16
Logs & Monitoring

Where do logs go?

By default, anything your app prints to stdout/stderr is captured by Docker's logging driver. Default driver is json-file. Available drivers: json-file, local, journald, syslog, gelf, fluentd, awslogs, etc.

docker logs my-container
docker logs -f --tail 200 my-container
docker logs --since 10m my-container
docker logs --until 2026-05-07T10:00 my-container

Limit log file size

docker run --log-opt max-size=10m --log-opt max-file=3 myapp
# Or globally in /etc/docker/daemon.json:
# {
#   "log-driver": "json-file",
#   "log-opts": { "max-size": "10m", "max-file": "3" }
# }

Production logging

Stream container logs to a centralized system: Loki, Elasticsearch, Splunk, CloudWatch. In Kubernetes, a node-level agent (Fluent Bit, Promtail) tails container logs and forwards.

Stats

docker stats                       # live CPU/mem/IO of all containers
docker top my-container            # processes inside

Security

Run as non-root

# Many official images now ship a non-root 'app' user

Read-only root filesystem

docker run --read-only --tmpfs /tmp myapp

Seccomp / AppArmor

Default seccomp profile blocks ~50 dangerous syscalls. Custom profiles: --security-opt seccomp=profile.json.

Image scanning

  • docker scout cves myimage:1.0
  • Trivy: trivy image myimage:1.0
  • Grype: grype myimage:1.0
  • Snyk, Anchore — commercial.

Don't ever

  • Mount the Docker socket into a container unless you really need it (full host control).
  • Use --privileged casually.
  • Run as root inside containers.
  • Bake secrets into images.
  • Trust :latest tags in production.

Module 18
Image Optimization

Why size matters

  • Faster pulls and deploys.
  • Less attack surface.
  • Less disk on every node.
  • Faster scaling under load.

Techniques

  1. Multi-stage builds — leave SDK behind.
  2. Slim base images — alpine (~5 MB), -slim Debian variants.
  3. Distroless — only runtime, no shell. Tiny + secure.
  4. Combine RUN commands — fewer layers: 
    RUN apt-get update && apt-get install -y curl \
    && rm -rf /var/lib/apt/lists/*
  5. .dockerignore — keep build context small.
  6. Order for cache — copy dep manifests, install, then copy source.
  7. BuildKit cache mounts: --mount=type=cache,target=/root/.cache to persist NPM/NuGet caches between builds.

Inspect what's bloating

docker history myimage:1.0
dive myimage:1.0                  # excellent TUI, https://github.com/wagoodman/dive

Module 21
What & Why of Kubernetes

What is Kubernetes?

Kubernetes (K8s — 8 letters between K and s) is an open-source container orchestrator. You declare what you want (10 replicas of the API, behind a load balancer, with these env vars). Kubernetes makes it true and keeps it true — restarting failed containers, scheduling new ones if a node dies, rolling updates without downtime.

Originally built at Google as a successor to internal systems Borg and Omega. Open-sourced in 2014, donated to the CNCF. Pronounced "koo-ber-net-ees".

What problem does it solve?

Docker runs containers on one host. Real systems span dozens or thousands of hosts. Without orchestration you'd manually ssh, deploy, restart, balance — at scale, impossible. K8s automates:

  • Scheduling — place containers on nodes based on resources/affinity.
  • Self-healing — replace dead containers; reschedule on dead nodes.
  • Scaling — increase/decrease replicas, automatically based on load.
  • Service discovery — DNS for services; internal load balancing.
  • Rolling updates — gradual deploys with rollback.
  • Configuration & secrets — separate from images, mounted into pods.
  • Storage orchestration — provision and attach volumes.

When you need K8s

  • You run many services (≥5) and they evolve independently.
  • You need zero-downtime deploys, autoscaling, multi-region.
  • You have ops capacity (or you use a managed K8s — EKS, AKS, GKE).

When you don't

  • Single backend + DB → just use a VM or a managed PaaS (Azure App Service, Heroku, Render).
  • Tiny team, no ops capacity → managed alternative.
  • Already on Docker Compose and not feeling pain — stay there longer.

Control plane components

  • kube-apiserver — single entry point. All clients (kubectl, controllers, kubelets) talk REST to it.
  • etcd — distributed key-value store holding all cluster state. Single source of truth.
  • kube-scheduler — picks which node a new pod runs on.
  • kube-controller-manager — runs controllers (Deployment, ReplicaSet, Node, etc.) that watch state and reconcile.
  • cloud-controller-manager — cloud-specific glue (load balancers, persistent disks).

Node components

  • kubelet — agent on each node; talks to apiserver, runs pods via the container runtime.
  • kube-proxy — sets up iptables/IPVS rules for Service IPs.
  • Container runtime — containerd or CRI-O (Docker daemon is no longer used).

The reconciliation loop

You declare desired state ("3 replicas of nginx"). Controllers compare desired vs actual and act ("only 2 running, start one more"). This loop runs continuously — that's the soul of K8s.

Module 25
Pods

A Pod is the smallest unit you can deploy. It's a wrapper for one or more containers that:

  • Share a network namespace (same IP, same localhost).
  • Share volumes.
  • Are scheduled together on the same node.

Most pods have one container. Multi-container pods are for tightly coupled helpers ("sidecars") — e.g., main app + log shipper, or main app + service mesh proxy.

Minimal pod manifest

apiVersion: v1
kind: Pod
metadata:
  name: nginx
  labels:
    app: nginx
spec:
  containers:
    - name: nginx
      image: nginx:1.25
      ports:
        - containerPort: 80
      resources:
        requests: { cpu: "100m", memory: "128Mi" }
        limits:   { cpu: "500m", memory: "256Mi" }

Apply it: kubectl apply -f pod.yaml. But you almost never create raw pods in production — you use Deployments (next module), which manage pods for you.

Pod lifecycle phases

Pending → Running → Succeeded / Failed / Unknown.

Init containers

Run-to-completion containers that execute before app containers. Used for one-off setup, schema migrations, waiting for dependencies.

spec:
  initContainers:
    - name: wait-for-db
      image: busybox
      command: ['sh','-c','until nc -z db 5432; do sleep 1; done']
  containers:
    - name: app
      image: myapi:1.0

Module 26
Deployments

A Deployment declares how many copies of a pod you want and how to update them. It creates a ReplicaSet, which keeps the right number of pods alive.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  labels: { app: api }
spec:
  replicas: 3
  selector:
    matchLabels: { app: api }
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1     # at most 1 pod down during update
      maxSurge: 1           # at most 1 extra pod created
  template:
    metadata:
      labels: { app: api }
    spec:
      containers:
        - name: api
          image: myorg/api:1.4.2
          ports: [ { containerPort: 8080 } ]
          env:
            - name: DB_HOST
              value: postgres
          resources:
            requests: { cpu: "200m", memory: "256Mi" }
            limits:   { cpu: "1",    memory: "512Mi" }

Rolling updates

Change image: myorg/api:1.4.3, kubectl apply -f. K8s creates new pods with the new image one at a time and removes old ones — zero-downtime.

Useful commands

kubectl rollout status deploy/api
kubectl rollout history deploy/api
kubectl rollout undo deploy/api
kubectl rollout undo deploy/api --to-revision=3
kubectl scale deploy/api --replicas=5
kubectl set image deploy/api api=myorg/api:1.4.4

Update strategies

  • RollingUpdate (default) — gradual replacement.
  • Recreate — kill all old, then start new. Brief downtime; OK for non-critical workloads.
  • Blue/Green & Canary — not native; achieved with two Deployments + Service routing or tools like Argo Rollouts, Flagger.

Module 27
StatefulSets, Jobs, CronJobs, DaemonSets

StatefulSet

Like Deployment but for stateful apps:

  • Pods get stable names: db-0, db-1, db-2.
  • Each pod gets its own PersistentVolume (via volumeClaimTemplates).
  • Ordered creation (db-0 first), ordered deletion (db-2 first).

For: databases, distributed coordinators (etcd, Zookeeper), Kafka, Redis with persistence. Often you'll use an Operator instead of writing StatefulSet by hand (Postgres Operator, Strimzi for Kafka, Redis Operator, etc.).

Job

Runs pods until N successful completions. For one-off batch tasks: data migration, report generation, backup.

apiVersion: batch/v1
kind: Job
metadata: { name: db-migration }
spec:
  template:
    spec:
      restartPolicy: OnFailure
      containers:
        - name: migrate
          image: myorg/db-migrator:1.0
          command: ["./migrate.sh"]
  backoffLimit: 3

CronJob

Job on a cron schedule. Like Linux cron, runs in the cluster.

apiVersion: batch/v1
kind: CronJob
metadata: { name: nightly-report }
spec:
  schedule: "0 2 * * *"            # 2 AM daily
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: reporter
              image: myorg/reporter:1.0

DaemonSet

Runs exactly one pod on every node (or matching nodes). For node-level agents: log shippers (Fluent Bit), monitoring (node-exporter), networking (CNI plugins).

Module 28
Services

Pods are ephemeral — they get new IPs on restart. A Service gives a stable virtual IP and DNS name in front of a set of pods (selected by labels) and load-balances across them.

Service types

TypeReachable fromUse
ClusterIP (default)Inside cluster onlyInternal microservices
NodePortAny node IP at a high port (30000–32767)Quick external access in dev/on-prem
LoadBalancerExternal cloud LB (auto-provisioned)Public services on cloud K8s
ExternalNameDNS CNAME to external hostAlias for an external service
Headless (clusterIP: None)DNS returns pod IPs directlyStatefulSets, custom LB

ClusterIP example

apiVersion: v1
kind: Service
metadata:
  name: api
spec:
  selector:
    app: api
  ports:
    - port: 80              # service port
      targetPort: 8080      # container port
      protocol: TCP
  type: ClusterIP

From any pod in the cluster, http://api/ (or http://api.namespace.svc.cluster.local) hits the service and gets load-balanced to one of the matching pods.

How it works

kube-proxy on each node programs iptables (or IPVS) rules so traffic to the service IP is DNAT'd to a random matching pod. CoreDNS resolves service names to service IPs.

Module 29
Ingress

An Ingress is HTTP/HTTPS routing into the cluster. It needs an Ingress Controller (nginx, Traefik, HAProxy, AWS ALB controller) running in the cluster — the controller watches Ingress resources and configures the actual proxy.

Why Ingress instead of LoadBalancer per service?

  • One LB serves many services (host- or path-based routing).
  • Centralized TLS termination.
  • Authentication, rate limits, rewrites in the controller.

Ingress example

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: easyaudit
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod
spec:
  ingressClassName: nginx
  tls:
    - hosts: [ api.easyaudit.com ]
      secretName: easyaudit-tls
  rules:
    - host: api.easyaudit.com
      http:
        paths:
          - path: /central
            pathType: Prefix
            backend:
              service: { name: central-backend, port: { number: 80 } }
          - path: /accounting
            pathType: Prefix
            backend:
              service: { name: accounting-backend, port: { number: 80 } }
          - path: /
            pathType: Prefix
            backend:
              service: { name: audit-frontend, port: { number: 80 } }

cert-manager

Auto-issues TLS certificates from Let's Encrypt or your CA. Two CRDs: ClusterIssuer + Certificate. Once installed, just annotate Ingress.

Module 31
Resources: Requests & Limits

Each container declares two numbers per resource (CPU, memory):

  • Requests — guaranteed minimum. The scheduler uses this to place the pod on a node with enough free capacity.
  • Limits — hard cap. CPU is throttled; memory is OOM-killed.
resources:
  requests:
    cpu: "200m"          # 0.2 of a core
    memory: "256Mi"
  limits:
    cpu: "1"             # 1 full core
    memory: "512Mi"

Units

  • CPU: 1 = 1 core. 500m = half a core. 100m = 0.1 core.
  • Memory: Mi = mebibytes (1024-based). Gi = gibibytes. (Avoid M/G which are 1000-based — confusing.)

QoS classes

ClassConditionEviction order
Guaranteedrequests = limits for all containersLast to be evicted
BurstableHas requests, limits > requestsMiddle
BestEffortNo requests/limitsFirst evicted on memory pressure

How to choose

  • Run the app under realistic load; observe CPU/memory.
  • Set requests at p50–p70 of usage.
  • Set limits at p99 with headroom — don't be too tight on memory (OOM kills).
  • Production tip: many shops set memory request = limit (Guaranteed QoS), keep CPU bursty.

Module 32
Probes

K8s checks if your container is alive and ready via three probes:

ProbeQuestionAction on failure
livenessIs the process stuck/deadlocked?Kill & restart container
readinessCan it serve traffic right now?Remove pod from Service endpoints
startupHas it finished booting?Delay liveness probe until startup passes
 
livenessProbe:
  httpGet: { path: /healthz/live, port: 8080 }
  initialDelaySeconds: 10
  periodSeconds: 10
  failureThreshold: 3

readinessProbe:
  httpGet: { path: /healthz/ready, port: 8080 }
  initialDelaySeconds: 5
  periodSeconds: 5

startupProbe:
  httpGet: { path: /healthz/live, port: 8080 }
  failureThreshold: 30
  periodSeconds: 10        # 30 × 10s = 5 min to boot

Probe types

  • httpGet — HTTP 200–399 = healthy.
  • tcpSocket — TCP connect succeeds = healthy.
  • exec — command exit 0 = healthy.
  • grpc — gRPC health check.
Common mistake: using the same endpoint for liveness and readiness, AND making it depend on the database. If DB is briefly unavailable, K8s starts killing perfectly healthy pods. Liveness should only check "is my process responding?" — not external deps.

Module 33
Auto-scaling

HorizontalPodAutoscaler (HPA)

Scales replicas up/down based on metrics.

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: api }
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70

Needs metrics-server installed. Custom metrics (RPS, queue length) need prometheus-adapter or KEDA.

VerticalPodAutoscaler (VPA)

Adjusts requests/limits over time based on observed usage. Use for unknown sizing; less common in production for live traffic (recreates pods).

Cluster Autoscaler

Adds/removes nodes when pods can't be scheduled or nodes are underused. Cloud-provider integration adds VMs as needed. Modern alternative: Karpenter (faster, smarter on AWS).

KEDA

Event-driven autoscaling. Scale on Kafka lag, Redis queue depth, RabbitMQ messages, AWS SQS, Azure Service Bus, etc. Even scale to zero.

Module 34
Persistent Volumes

The objects

  • PersistentVolume (PV) — actual cluster-wide storage resource.
  • PersistentVolumeClaim (PVC) — a request for storage from a pod.
  • StorageClass — template for dynamic PV provisioning.

Static vs dynamic

Dynamic (modern default): pod creates a PVC, K8s + a CSI driver provision the PV automatically (EBS volume, Azure Disk, etc.).

StorageClass example

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: disk.csi.azure.com   # or ebs.csi.aws.com, etc.
parameters:
  skuName: Premium_LRS
reclaimPolicy: Retain

PVC example

apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: db-data }
spec:
  accessModes: [ ReadWriteOnce ]
  storageClassName: fast-ssd
  resources:
    requests: { storage: 50Gi }

Mount in pod

volumes:
  - name: data
    persistentVolumeClaim: { claimName: db-data }
volumeMounts:
  - name: data
    mountPath: /var/lib/postgresql/data

Access modes

  • ReadWriteOnce (RWO) — one node at a time. Most block storage.
  • ReadOnlyMany (ROX) — many readers.
  • ReadWriteMany (RWX) — many readers/writers. Needs network FS (NFS, EFS, Azure Files).
  • ReadWriteOncePod — single pod (not just node). Stricter.

RBAC & Security

RBAC primitives

  • Role — permissions inside a namespace.
  • ClusterRole — permissions cluster-wide.
  • RoleBinding — binds a Role to a user/group/ServiceAccount.
  • ClusterRoleBinding — same, cluster-scope.
  • ServiceAccount — identity for workloads.
apiVersion: v1

metadata: { name: api-sa, namespace: prod }

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { namespace: prod, name: read-config }
rules:

    resources: ["configmaps","secrets"]

apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { namespace: prod, name: api-read-config }
subjects:

    name: api-sa
    namespace: prod
roleRef:
  kind: Role
  name: read-config
  apiGroup: rbac.authorization.k8s.io

NetworkPolicy

Default: every pod can talk to every other pod. NetworkPolicies let you firewall:

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: db-allow-api }
spec:
  podSelector:
    matchLabels: { app: postgres }
  ingress:
    - from:

            matchLabels: { app: api }
      ports:
        - port: 5432

Needs a CNI plugin that supports policies (Calico, Cilium).

Pod Security Standards

Modern replacement for PodSecurityPolicy. Three levels: privileged, baseline, restricted. Apply per namespace via labels:

kubectl label ns prod \

Helm is a package manager. A "chart" is a directory of templated YAML; values are filled in at install time. The chart + its values become a "release" in the cluster.

Chart structure

mychart/
├── Chart.yaml
├── values.yaml
├── templates/
│   ├── deployment.yaml
│   ├── service.yaml
│   └── _helpers.tpl

apiVersion: apps/v1

    spec:
      containers:

replicaCount: 3

Module 39
Production Operations

Observability stack

  • Metrics: Prometheus + Grafana (commonly via kube-prometheus-stack Helm chart).
  • Logs: Loki + Promtail, or ELK, or commercial (Datadog, Splunk).
  • Traces: Tempo, Jaeger, or vendor APM. Wire OTel SDK in apps.
  • Dashboards: Grafana with prebuilt K8s dashboards.

GitOps

Store all manifests in Git; an operator reconciles cluster to match. Tools: Argo CD, Flux. Pull-based, auditable, easy rollback.

CI/CD pattern

  1. Push to main → CI builds image, runs tests, scans for CVEs.
  2. Image is tagged with commit SHA, pushed to registry.
  3. CI updates Helm values / Kustomization with new tag in a Git repo.
  4. Argo CD/Flux detects the change and applies to cluster.
  5. Rolling update happens; Argo monitors health.

Backups

  • Velero — backup & restore cluster resources + PVs.
  • Database-specific backups (pg_dump for Postgres, etc.) into object storage.

Cost control

  • Right-size requests; over-requesting wastes nodes.
  • Use spot/preemptible nodes for non-critical workloads.
  • Cluster Autoscaler / Karpenter to remove idle nodes.
  • Tools: Kubecost, OpenCost.

Upgrading clusters

K8s releases every ~3 months; supported for ~14 months. Keep within 1–2 minor versions of latest. Process: drain a node, upgrade kubelet/runtime, uncordon. On managed K8s, click "upgrade" and the cloud handles it.

Module 43
Interview Questions

Q: What's the difference between a container and a VM?
VMs include a full guest OS and run on a hypervisor — strong isolation, slow boot, GBs. Containers share the host kernel and isolate via namespaces+cgroups — lightweight, fast boot, MBs.
Q: Explain Docker layers and caching.
Each Dockerfile instruction creates a layer. Layers are content-hashed and cached. If a step's inputs are unchanged, Docker reuses the cached layer. Order matters: put rarely-changing instructions (deps) before frequently-changing ones (source).
Q: How do you reduce image size?
Multi-stage builds, slim/distroless base images, combine RUN commands, .dockerignore to shrink build context, BuildKit cache mounts.
Q: Why shouldn't you use :latest?
Mutable tag — different machines may pull different image bytes for the same name, breaking reproducibility. Pin to specific tags or, ideally, image digests (@sha256:...).
Q: What is a Pod?
The smallest deployable unit in K8s — one or more co-located containers that share network namespace, IPC, and volumes. Usually one container per pod; multi-container pods are for tightly-coupled sidecars.
Q: Deployment vs StatefulSet?
Deployment: stateless replicas, interchangeable. StatefulSet: ordered, named pods with stable identity (db-0, db-1) and stable per-pod storage. For databases and clustered systems.
Q: What is a Service?
An abstraction giving a stable virtual IP and DNS name in front of a dynamic set of pods (selected by labels), with built-in load balancing.
Q: Difference between liveness, readiness, startup probes?
Liveness: am I alive? Failure → restart. Readiness: can I serve traffic? Failure → removed from Service endpoints. Startup: have I finished booting? Delays liveness until startup passes.
Q: How does K8s do rolling updates?
The Deployment creates a new ReplicaSet, scales it up while scaling the old down, respecting maxUnavailable and maxSurge. Old pods are terminated only after new ones are ready (readiness probes).
Q: Requests vs limits?
Requests: guaranteed minimum, used for scheduling. Limits: hard cap, CPU throttled / memory OOM-killed. Requests=limits → Guaranteed QoS class.
Q: How do Secrets differ from ConfigMaps?
API-level: Secrets are intended for sensitive data, base64-encoded by default, can be encrypted at rest in etcd, and have stricter audit. ConfigMaps are for non-sensitive config.
Q: What is HPA?
Horizontal Pod Autoscaler. Scales replicas of a Deployment up/down based on CPU, memory, or custom metrics.
Q: How does a pod talk to another pod's database?
Through a Service. The pod uses the Service DNS name (postgres.default.svc.cluster.local or just postgres in the same namespace). kube-proxy load-balances to a backing pod.
Q: What's the difference between Ingress and LoadBalancer Service?
LoadBalancer: one cloud LB per service; expensive at scale. Ingress: a single ingress controller (one LB) routes many hosts/paths to many services, plus TLS, auth, rewrites.
Q: How do you do zero-downtime database migrations?
Two-phase: deploy code that works with old AND new schema → run schema migration as a Job/initContainer → deploy code that uses only new schema. Never break-and-fix in one step.
Q: How does etcd fit in?
It's the key-value store backing the apiserver — all cluster state lives there (raft-replicated). Lose etcd, lose the cluster's brain. Backup it.
Q: What's a CRD?
Custom Resource Definition. Lets you define your own resource types (kind: MyApp) that the apiserver stores and serves like built-in ones. Operators use CRDs.
Q: Why prefer non-root containers?
If a container is compromised, root inside (especially with the right capabilities) can sometimes break out to host root. Non-root + dropped caps + no-new-privileges + read-only root is defense-in-depth.

Key production decisions

ConcernRecommendation
Stateful infra (DB/Redis/Kafka) Use managed services (Azure SQL, Azure Cache for Redis, Confluent Cloud). Don't run statefulsets for these unless you have ops capacity.
Image registry Azure Container Registry (ACR) attached to AKS — uses managed identity, no secrets to rotate.
Secrets Azure Key Vault + External Secrets Operator (or AKS CSI Driver). Never commit secrets to Git.
CI/CD GitHub Actions or Azure DevOps → build & push image with commit-SHA tag → update Helm/Kustomize values in Git → Argo CD applies.
Helm structure One umbrella chart with sub-charts per backend, OR one chart per backend. Values per env (values-dev.yaml, values-prod.yaml).
Ingress ingress-nginx (Helm) + cert-manager (Helm) + Let's Encrypt. Single LB; host/path routing.
Scaling HPA per backend, baseline replicas=2 for HA, max based on load tests. AKS Cluster Autoscaler or Karpenter to grow nodes.
Observability kube-prometheus-stack (Prometheus + Grafana + Alertmanager), Loki for logs, Tempo for traces; or use Azure Monitor + App Insights.
Backup Velero for cluster-resource backup; managed services handle their own DB backups.
Network policy Default-deny in easyaudit-prod; allow only required pod-to-pod (frontend→backend→DB).
RBAC One ServiceAccount per backend. Devs get namespace-scoped roles. Cluster-admin reserved for cluster ops.

Day-2 operations checklist

  • SLOs/SLIs defined per backend (p99 latency, error rate).
  • Alerts on: pod CrashLoopBackOff, HPA at max for > 10 min, error rate > 1%, p99 latency > threshold, < 80% available pods.
  • Runbooks for: failed rollout, DB connection storm, OOM kills, certificate renewal failure.
  • PodDisruptionBudgets per Deployment so node drains don't take service to zero.
  • Quarterly K8s minor upgrade.
  • Quarterly DR drill: restore Velero backup to a fresh cluster.

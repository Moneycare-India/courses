JavaScript Essentials for React Devs

The features you'll use every day

Arrow functions

// Array

// In function params

Spread & rest

const a = [1, 2, 3];
const b = [...a, 4, 5];                     // spread → [1,2,3,4,5]

const original = { a: 1, b: 2 };
const updated = { ...original, b: 99 };     // shallow copy + override

function sum(...numbers) {                   // rest
    return numbers.reduce((s, n) => s + n, 0);
}

Template literals

const multiline = `
    Line 1
    Line 2

Array methods (the ones that matter for React)

users.map(u => <li key={u.id}>{u.name}</li>);          // transform
users.filter(u => u.isActive);                          // keep matching
users.find(u => u.id === 42);                           // first matching
users.some(u => u.isAdmin);                             // any?

users.flatMap(u => u.tags);                             // flatten one level

Promises

Modules

Module 2
TypeScript Intro

What is TypeScript?

TypeScript is JavaScript with a static type system bolted on top. Types are checked at compile time and erased at runtime — the output is plain JavaScript that any browser/Node can run. Created by Microsoft (Anders Hejlsberg again — same designer as C#).

Why TypeScript?

  • Catch bugs at compile time instead of runtime — typos, null derefs, wrong shapes.
  • Self-documenting — types describe contracts.
  • IDE superpowers — autocomplete, rename, find-references actually work.
  • Refactor safely — break it, the compiler tells you everywhere it broke.
  • Industry standard for React projects in 2026.

JavaScript → TypeScript

// JavaScript
function greet(user) {
    return `Hello, ${user.name}`;       // What if user has no name? What if user is undefined?
}

// TypeScript
function greet(user: { name: string }): string {
    return `Hello, ${user.name}`;
}

greet({ name: 'Alice' });               // OK
greet({});                              // ERROR at compile time
greet(undefined);                       // ERROR
greet({ name: 42 });                    // ERROR — name must be string

How it runs

  .ts file
     │
     ▼ tsc (or Vite/esbuild/swc) compiles & type-checks
  .js file (types stripped) ──► browser/node runs it

In a Vite project (like audit-frontend), TS type-checking and compilation happen via esbuild + tsc --noEmit. Errors stop your build.

Type inference

You usually don't need annotations — TS infers from context.

const name = 'Alice';                      // string (inferred)
const age = 30;                              // number
const user = { name: 'Alice', age: 30 };    // { name: string; age: number }

// Add explicit types when:
// 1. The type would otherwise be wrong (any, unknown)
// 2. Function parameters / public APIs
// 3. You want a wider/narrower type than inferred

Object types — interface vs type alias

// interface
interface User {
    id: number;
    name: string;
    email: string;
    age?: number;        // optional
    readonly createdAt: Date;
}

// type alias — same idea, can also represent unions, primitives
type User = {
    id: number;
    name: string;
};

type Status = 'active' | 'pending' | 'banned';   // union literal type
type UserId = number;                              // alias for primitive

When to use which: in modern TS the difference is mostly stylistic. Use interface for object shapes you might extend later (especially across module boundaries — they merge), and type for unions, intersections, primitives, mapped/conditional types.

Generics

function identity<T>(value: T): T {
    return value;
}

const num = identity(42);          // T = number
const str = identity('hello');     // T = string

function getLength<T extends { length: number }>(x: T): number {

Generic types & data structures

    error?: string;
    timestamp: number;
}

const usersResp: ApiResponse<User[]> = await fetchUsers();
const userResp: ApiResponse<User> = await fetchUser(42);

Type narrowing

The compiler "narrows" a union type as you check it.

function format(value: string | number): string {
    if (typeof value === 'string') {
        return value.toUpperCase();    // value is string here
    }
    return value.toFixed(2);            // value is number here
}

// Narrowing with discriminated unions — the React way
type State =
    | { status: 'idle' }
    | { status: 'loading' }
    | { status: 'success'; data: User[] }
    | { status: 'error'; error: string };

function render(state: State) {
    switch (state.status) {
        case 'idle':    return 'Ready';
        case 'loading': return 'Loading…';
        case 'success': return `${state.data.length} users`;  // .data is typed
        case 'error':   return state.error;                    // .error is typed
    }
}

as const

Type assertions vs type guards

// Assertion — "trust me, compiler" (can lie!)

Object shorthand

const name = 'Alice';
const age = 30;

// Long
const user = { name: name, age: age };

// Short
const user = { name, age };

// In React state updates
setUser({ ...user, name });

Computed property names

// In setState
setForm(prev => ({ ...prev, [field]: value }));

Default function params

function Button({ variant = 'primary', size = 'md' }: ButtonProps) { ... }

Object/array spread vs Object.assign

Always prefer spread — clearer and works in TS without quirks.

// Don't
const merged = Object.assign({}, a, b);
// Do
const merged = { ...a, ...b };

Immutable updates (critical for React)

React detects changes by reference equality. Mutating state in place won't trigger re-renders. Always create a new object/array.

Bad — mutates in place

users.push(newUser);            // same reference
setUsers(users);                // React: "no change"

user.name = 'Bob';
setUser(user);

items[0].done = true;
setItems(items);

Good — new references

setUsers([...users, newUser]);

setUser({ ...user, name: 'Bob' });

setItems(items.map((item, i) =>
    i === 0 ? { ...item, done: true } : item
));

// Remove
setUsers(users.filter(u => u.id !== id));

For complex updates: Immer

import { produce } from 'immer';

setItems(produce(items, draft => {
    draft[0].done = true;       // looks mutable, isn't
    draft.push(newItem);
}));

Async Patterns

async/await

async function fetchUser(id: number): Promise<User> {
    const r = await fetch(`/api/users/${id}`);
    if (!r.ok) throw new Error(`HTTP ${r.status}`);
    return r.json();
}

// Use it
try {
    const user = await fetchUser(42);
    console.log(user.name);
} catch (err) {
    console.error(err);
}

Parallel vs sequential

// Sequential — slow (sum of times)
const a = await fetchA();
const b = await fetchB();

// Parallel — fast (max of times)
const [a, b] = await Promise.all([fetchA(), fetchB()]);

// First to finish wins
const winner = await Promise.race([fetchA(), fetchB()]);

// All settle (some may fail)
const results = await Promise.allSettled([fetchA(), fetchB()]);
results.forEach(r => r.status === 'fulfilled' ? ... : ...);

AbortController — cancellation

const ctrl = new AbortController();

fetch('/api/users', { signal: ctrl.signal })
    .then(r => r.json());

// Cancel
ctrl.abort();

Critical for React — when a component unmounts, abort in-flight requests to prevent state updates on unmounted components.

Module 8
Functional Programming Basics

You don't need to master FP to use React, but the FP mindset makes React click.

Pure functions

Same input → same output. No side effects. No mutation.

// Pure
const add = (a: number, b: number) => a + b;

// Impure — depends on outside, has side effect
let count = 0;
const inc = () => ++count;

React components should be (mostly) pure functions of props + state.

Immutability

Don't mutate; return new values. Already covered in Module 6 — it's the FP cornerstone.

Higher-order functions

// Function that returns a function
const greet = (greeting: string) => (name: string) => `${greeting}, ${name}`;
const sayHi = greet('Hi');
sayHi('Alice');         // 'Hi, Alice'

// Function that takes a function
const onClick = (handler: () => void) => () => handler();

Composition over inheritance

FP composes small functions. React composes small components. The mindset is the same.

Map / filter / reduce

Three workhorses. If you can think in these, you can think in React.

// Get total revenue from active users
const total = users
    .filter(u => u.isActive)
    .flatMap(u => u.orders)
    .reduce((sum, o) => sum + o.amount, 0);

Module 9
React Intro & JSX

What is React?

React is a UI library (not a framework) for building component-based interfaces. Created at Facebook (Meta) by Jordan Walke in 2013. The core idea: describe the UI as a function of state; React figures out how to update the DOM efficiently.

Mental model

    state         render             DOM
   ┌────┐  ──►  ┌──────────┐  ──►  ┌────────┐
   │ {} │       │  <App /> │       │ <div>.. │
   └────┘       └──────────┘       └────────┘
       ▲                                │ user event
       └────────── setState ◄───────────┘

You write what the UI should look like for a given state. React diffs the old vs new tree (the "virtual DOM") and patches only what changed.

JSX

JSX is a syntax extension that looks like HTML but compiles to JavaScript function calls.

// JSX
const greeting = <h1 className="title">Hello, {name}</h1>;

// Compiles to (roughly):
const greeting = React.createElement('h1', { className: 'title' }, 'Hello, ', name);

JSX rules

  • One root element — wrap multiples in <>...</> (Fragment).
  • className not class — class is a JS keyword.
  • htmlFor not for.
  • camelCase event handlers: onClick, onSubmit.
  • Self-close tags without children: <img />, <input />.
  • Curly braces for JS expressions: {count + 1}, {user.name.toUpperCase()}.
  • Inline styles take an object: style={{ color: 'red' }}.

First component

// src/components/Greeting.tsx
type GreetingProps = { name: string };

export function Greeting({ name }: GreetingProps) {
    return (
        <div className="greeting">
            <h1>Hello, {name}!</h1>
            <p>Welcome to React.</p>
        </div>
    );
}

// Use it
<Greeting name="Alice" />

Conditional content

// Ternary
{isLoggedIn ? <Dashboard /> : <Login />}

// Logical AND (only render if true)
{hasError && <ErrorBanner message={error} />}

// CAREFUL: short-circuit gotcha

Module 11
State & useState

What's state?

Any data the component owns and that may change over time. When state changes, React re-renders the component.

import { useState } from 'react';

function Counter() {
    const [count, setCount] = useState(0);   // [value, setter] = useState(initial)

    return (
        <button onClick={() => setCount(count + 1)}>
            Clicked {count} times
        </button>
    );
}

Multiple state variables

function LoginForm() {
    const [email, setEmail] = useState('');
    const [password, setPassword] = useState('');
    const [isSubmitting, setIsSubmitting] = useState(false);
    // ...
}

State updates are asynchronous

function handleClick() {
    setCount(count + 1);
    setCount(count + 1);
    setCount(count + 1);
    // count is still old value here, all three set the SAME value
    // → final count = count + 1 (not + 3)
}

// Use updater function for sequential updates
function handleClick() {
    setCount(c => c + 1);
    setCount(c => c + 1);
    setCount(c => c + 1);
    // → final count = +3
}

State as object

const [form, setForm] = useState({ email: '', password: '' });

// To update one field — spread the rest
setForm(prev => ({ ...prev, email: 'new@x.com' }));

Lazy initial state

If the initial value is expensive to compute, pass a function:

// Bad — runs on EVERY render (wasted work)
const [items, setItems] = useState(JSON.parse(localStorage.getItem('items') || '[]'));

// Good — runs only on mount
const [items, setItems] = useState(() => JSON.parse(localStorage.getItem('items') || '[]'));

State should be minimal

Don't store derivable values. Compute them from existing state instead.

Bad — duplicated state

const [items, setItems] = useState<Item[]>([]);
const [count, setCount] = useState(0);          // redundant
const [hasItems, setHasItems] = useState(false); // redundant

// Now you must keep them in sync — error-prone

Good — derive on render

const [items, setItems] = useState<Item[]>([]);
const count = items.length;         // derived
const hasItems = items.length > 0;  // derived

// One source of truth

Module 12
Effects & useEffect

What's an effect?

Anything outside the pure render path: API calls, subscriptions, manual DOM manipulation, timers. useEffect runs after render.

import { useEffect, useState } from 'react';

function UserProfile({ userId }: { userId: number }) {
    const [user, setUser] = useState<User | null>(null);

    useEffect(() => {
        let cancelled = false;
        fetch(`/api/users/${userId}`)
            .then(r => r.json())
            .then(data => { if (!cancelled) setUser(data); });

        return () => { cancelled = true; };   // cleanup
    }, [userId]);   // dependency array

    if (!user) return <p>Loading...</p>;
    return <h1>{user.name}</h1>;
}

Anatomy of useEffect

useEffect(() => {
    // 1. Effect — runs after every render where deps changed
    const id = setInterval(() => console.log('tick'), 1000);

    // 2. Cleanup — runs before next effect AND on unmount
    return () => clearInterval(id);
}, [/* 3. Deps */]);

Dependency array — three behaviors

PatternWhen effect runs
useEffect(fn) — no arrayEvery render — almost always wrong
useEffect(fn, []) — empty arrayOnly after mount; cleanup on unmount
useEffect(fn, [a, b]) — listed depsWhenever a or b changes (by reference)

Common effect uses

Subscriptions

Timers

Effects you should NOT write

  • Calculating from props/state — just compute during render.
  • Updating state based on props — derive at render or use key to reset.
  • Server data fetching in real apps — use React Query (Module 28); it solves caching, dedup, refetch, errors.
  • Event handlers — those go directly in onClick, not in effects.

The exhaustive-deps rule

The ESLint plugin react-hooks/exhaustive-deps checks your dep arrays. Don't suppress it — if it warns, you have a real bug.

Strict Mode & effects running twice

In dev with <StrictMode>, effects run, clean up, then run again — to expose missing cleanups. This is intentional. Make sure your effects are idempotent and clean up properly.

Why keys?

Keys help React identify which items changed/added/removed. Without stable keys, React might rebuild whole subtrees, lose focus, or apply state to the wrong item.

Bad — index as key

{items.map((item, i) => (
    <li key={i}>{item.label}</li>
))}
// If you reorder/insert/delete, indexes
// shift, breaking React's reconciliation.

Good — stable id as key

{items.map(item => (
    <li key={item.id}>{item.label}</li>
))}
// If no id, generate stable ones
// (e.g. uuid at create time, not in render).

Index keys are OK when

  • The list is static (never reorders).
  • Items have no state of their own.
  • List is rendered top-to-bottom only and items aren't filtered.

useState in Depth

Functional updates — when to use them

When the new value depends on the previous, ALWAYS use the function form.

// WRONG inside async/timer/event-batch
function tick() {
    setSeconds(seconds + 1);    // captures old `seconds` from closure
}

// RIGHT
function tick() {
    setSeconds(prev => prev + 1);
}

Batching

React batches state updates that happen in the same event handler / effect into a single re-render. Multiple setState calls = one render.

function handleClick() {
    setA(1);
    setB(2);
    setC(3);
    // Only ONE re-render after this function ends.
}

The "stale state" trap

function ChatRoom() {
    const [messages, setMessages] = useState<string[]>([]);

    useEffect(() => {
        const ws = new WebSocket('/chat');
        ws.onmessage = (e) => {
            // BAD — captures messages once at mount, forever empty
            setMessages([...messages, e.data]);

            // GOOD
            setMessages(prev => [...prev, e.data]);
        };
    }, []);   // empty deps — handler captures `messages` once
}

Dependencies must include everything used inside

Anything from props/state/context referenced inside the effect must be in the dep array. ESLint enforces this.

Bad — missing deps, stale values

    fetch(`/api/${userId}`).then(setUser);
}, []);   // userId not listed!

Good — listed

useEffect(() => {
    fetch(`/api/${userId}`).then(setUser);
}, [userId]);

Dependencies that change every render

If you depend on a function or object, it must be stable, or the effect runs on every render.

function Parent() {
    const config = { delay: 1000 };  // NEW object each render!
    return <Child config={config} />;
}

function Child({ config }) {
    useEffect(() => {
        // Runs every render — bad
    }, [config]);
}

Fixes (in order of preference):

  1. Move the object/function inside the effect (no dep needed).
  2. Pass primitive deps instead: [config.delay].
  3. Memoize with useMemo/useCallback in the parent.

Module 18
useMemo & useCallback

What they do

  • useMemo — caches a computed value across renders if deps haven't changed.
  • useCallback — caches a function reference across renders if deps haven't changed.
// Expensive calculation
const sortedItems = useMemo(() =>
    items.slice().sort((a, b) => a.price - b.price),
    [items]);

// Stable callback for memoized children
const handleSelect = useCallback((id: number) => {
    setSelectedId(id);
}, []);

When to use them

  • Genuinely expensive computation (sort 10k items, regex, parse).
  • Reference equality matters: passing the value/fn into useEffect deps, React.memo children, or another hook.

When NOT to use them

  • To "speed up" cheap computations — useMemo isn't free; the comparison + extra closure costs something.
  • For every callback "just in case".
  • If the children aren't memoized, useCallback doesn't help.
Don't reach for useMemo/useCallback by reflex. Profile first. The React Compiler (in beta in 2026) auto-memoizes, removing this manual layer entirely.

useMemo with a stable object reference

// Without useMemo, contextValue is a new object each render —
// every consumer of the context re-renders.
const contextValue = useMemo(() => ({ user, login, logout }), [user]);
<AuthContext.Provider value={contextValue}>...</AuthContext.Provider>

Module 19
useReducer

An alternative to useState for complex state with multiple actions. Same idea as Redux: state + dispatch + reducer function.

type CartState = { items: Item[]; total: number };
type CartAction =
    | { type: 'add'; item: Item }
    | { type: 'remove'; id: number }
    | { type: 'clear' };

function reducer(state: CartState, action: CartAction): CartState {
    switch (action.type) {
        case 'add':
            return {
                items: [...state.items, action.item],
                total: state.total + action.item.price,
            };
        case 'remove': {
            const item = state.items.find(i => i.id === action.id);
            return {
                items: state.items.filter(i => i.id !== action.id),
                total: state.total - (item?.price ?? 0),
            };
        }
        case 'clear':
            return { items: [], total: 0 };
    }
}

function Cart() {
    const [state, dispatch] = useReducer(reducer, { items: [], total: 0 });

    return (
        <div>
            {state.items.map(i => (
                <div key={i.id}>
                    {i.name}
                    <button onClick={() => dispatch({ type: 'remove', id: i.id })}>X</button>
                </div>
            ))}
            <p>Total: ${state.total}</p>
            <button onClick={() => dispatch({ type: 'clear' })}>Clear</button>
        </div>
    );
}

useContext

    const [user, setUser] = useState<User | null>(null);
    const value = useMemo(() => ({
        user,
        login: setUser,
        logout: () => setUser(null),
    }), [user]);
    return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>;
}

// 3. Consumer hook

    const ctx = useContext(AuthContext);
    if (!ctx) throw new Error('useAuth must be inside AuthProvider');
    return ctx;
}

// 4. Use anywhere

    const { user, logout } = useAuth();
    return user ? (
        <div>Hi {user.name} <button onClick={logout}>Log out</button></div>
    ) : null;
}

Context performance trap

When the context value changes (new reference), every consumer re-renders. Solutions:

  • Memoize the value (the example above does this).
  • Split context into StateContext + DispatchContext if the dispatcher is stable but state churns.
  • Use Zustand (Module 30) instead — it has selectors so consumers re-render only when their slice changes.

Don't use context for everything

Context is for ambient data. For local component coupling, prop drilling 1–2 levels is FINE — clearer than scattering context.

Custom Hooks

A function whose name starts with use and that calls other hooks. Bundles reusable stateful logic.

Example: useLocalStorage

function useLocalStorage<T>(key: string, initial: T) {
    const [value, setValue] = useState<T>(() => {
        try {
            const raw = localStorage.getItem(key);
            return raw ? JSON.parse(raw) : initial;
        } catch {
            return initial;
        }
    });

    useEffect(() => {
        localStorage.setItem(key, JSON.stringify(value));
    }, [key, value]);

    return [value, setValue] as const;
}

// Use it like useState
function ThemeSwitcher() {
    const [theme, setTheme] = useLocalStorage<'light' | 'dark'>('theme', 'light');
    return <button onClick={() => setTheme(t => t === 'light' ? 'dark' : 'light')}>{theme}</button>;
}

Example: useDebounce

function useDebounce<T>(value: T, delay = 300): T {
    const [debounced, setDebounced] = useState(value);
    useEffect(() => {
        const id = setTimeout(() => setDebounced(value), delay);
        return () => clearTimeout(id);
    }, [value, delay]);
    return debounced;
}

// Use it
const [query, setQuery] = useState('');
const debouncedQuery = useDebounce(query, 500);

useEffect(() => {
    if (debouncedQuery) search(debouncedQuery);
}, [debouncedQuery]);

Example: useToggle

function useToggle(initial = false) {
    const [value, setValue] = useState(initial);
    const toggle = useCallback(() => setValue(v => !v), []);
    const setTrue = useCallback(() => setValue(true), []);
    const setFalse = useCallback(() => setValue(false), []);
    return { value, toggle, setTrue, setFalse } as const;
}

Rules of hooks

  1. Only call hooks at the top level. Not inside loops, conditions, or nested functions.
  2. Only call hooks from React functions. Components or other custom hooks — not regular JS functions.

The ESLint plugin react-hooks/rules-of-hooks enforces both. Don't disable.

When to extract a custom hook

  • Two components share the same useState + useEffect pattern.
  • A component's logic is hard to read; extracting clarifies it.
  • You'd write a "service" in another framework — that's a custom hook in React.

Module 27
State Taxonomy — Pick the Right Tool

Most React apps mix four kinds of state. They need different tools.

KindExamplesBest tool
Server state User list from API, current user profile, dashboard data React Query / TanStack Query
URL state Current page, filters, sort, search query, modal open React Router (search params, route params)
Local UI state Modal open/closed, form input, hovered, expanded useState / useReducer in the component
Global client state Theme, current user, selected workspace, cart contents Zustand (or Context for small needs)

Why this matters

Most React performance and complexity issues come from putting state in the wrong place — fetching data with useEffect (server state in local state), or syncing the whole world through Context (everything is global state).

Quick decision rules

  • Comes from an API? → React Query.
  • Should survive refresh / be shareable via URL? → URL state.
  • Used by exactly one component? → useState.
  • Used by 5+ unrelated components? → Zustand.
  • "Ambient" data (theme, user, locale)? → Context (with care).

TanStack Query (formerly React Query) is the standard tool for fetching, caching, and syncing server state. It eliminates 90% of useEffect + useState + setError boilerplate.

import { QueryClient, QueryClientProvider } from '@tanstack/react-query';

const queryClient = new QueryClient({
    defaultOptions: {

            refetchOnWindowFocus: false,
        },

useQuery — fetching data

import { useQuery } from '@tanstack/react-query';

function UserPage({ userId }: { userId: number }) {
    const { data, isLoading, isError, error } = useQuery({
        queryKey: ['user', userId],                     // unique key for cache
        queryFn: () => fetch(`/api/users/${userId}`).then(r => r.json()),
    });

    if (isLoading) return <Spinner />;
    if (isError) return <p>Error: {(error as Error).message}</p>;
    return <h1>{data.name}</h1>;
}

What you get for free

  • Caching — same key = no duplicate requests across components.
  • Background refetching — when window refocuses, network reconnects, or staleTime expires.
  • Loading / error states managed for you.
  • Request deduplication — multiple components with the same key fire one request.
  • Devtools — see every query, its data, and its cache status.

Strongly typed wrapper

// api/users.ts
export const usersApi = {
    list: () => fetch('/api/users').then(r => r.json() as Promise<User[]>),
    byId: (id: number) => fetch(`/api/users/${id}`).then(r => r.json() as Promise<User>),
};

// hooks/useUsers.ts
export const userKeys = {
    all: ['users'] as const,
    lists: () => [...userKeys.all, 'list'] as const,
    detail: (id: number) => [...userKeys.all, 'detail', id] as const,
};

export function useUsers() {
    return useQuery({
        queryKey: userKeys.lists(),
        queryFn: usersApi.list,
    });
}

export function useUser(id: number) {
    return useQuery({
        queryKey: userKeys.detail(id),
        queryFn: () => usersApi.byId(id),
        enabled: id > 0,                    // skip until id valid
    });
}

ConceptWhat
staleTimeHow long data is considered "fresh" — no auto-refetch within this window.

Optimistic updates

Update the UI immediately, roll back if the request fails.

const updateUser = useMutation({
    mutationFn: (user: User) => api.updateUser(user),

    onMutate: async (user) => {
        // Cancel outgoing refetches
        await qc.cancelQueries({ queryKey: userKeys.detail(user.id) });

        // Snapshot for rollback
        const prev = qc.getQueryData<User>(userKeys.detail(user.id));

        // Optimistically update
        qc.setQueryData(userKeys.detail(user.id), user);

        return { prev };
    },

    onError: (err, user, ctx) => {
        // Roll back
        if (ctx?.prev) qc.setQueryData(userKeys.detail(user.id), ctx.prev);
        toast.error('Update failed, reverted');
    },

    onSettled: (_, __, user) => {
        // Always refresh from server
        qc.invalidateQueries({ queryKey: userKeys.detail(user.id) });
    },
});

Zustand for Client State

Zustand ("state" in German) is a tiny, hooks-based state library. No provider, no boilerplate, with selector-based subscriptions to avoid unnecessary re-renders.

Setup

npm i zustand

// stores/cartStore.ts
import { create } from 'zustand';

type Item = { id: number; name: string; price: number };

type CartState = {
    items: Item[];
    add: (item: Item) => void;
    remove: (id: number) => void;
    clear: () => void;
    total: () => number;
};

export const useCart = create<CartState>((set, get) => ({
    items: [],
    add: (item) => set(state => ({ items: [...state.items, item] })),
    remove: (id) => set(state => ({ items: state.items.filter(i => i.id !== id) })),
    clear: () => set({ items: [] }),
    total: () => get().items.reduce((s, i) => s + i.price, 0),
}));

Use it anywhere — no provider needed

function CartIcon() {
    // Subscribe to JUST the count — re-renders only when count changes
    const count = useCart(state => state.items.length);
    return <span>Cart ({count})</span>;
}

function CartList() {
    const items = useCart(state => state.items);
    const remove = useCart(state => state.remove);
    return (
        <ul>
            {items.map(i => (
                <li key={i.id}>{i.name} <button onClick={() => remove(i.id)}>X</button></li>
            ))}
        </ul>
    );
}

Module 31
Redux / Jotai / Context — Comparison

ToolMental ModelBest forPain points
useState Per-component value Local UI state Prop drilling if shared
Context + useReducer Tree-scoped state Auth, theme, small global state Re-renders all consumers; not great for frequent updates
Zustand Single store, hook-based, selectors Global client state, simple API Lacks DevTools features of Redux at full power
Jotai Atomic primitives — small atoms compose Fine-grained reactive state, derived values Different mental model; can fragment
Redux Toolkit Single store, reducers, actions, slices Big apps, complex flows, time travel debug More boilerplate; overkill for many apps
React Query Server cache, not "state" Anything from an API Not for purely client state

Recommended modern stack

  • useState/useReducer for local UI.
  • React Query for server data.
  • React Router for URL state.
  • Zustand for global client state.
  • Context only for genuinely tree-scoped, low-churn data (auth user, theme, locale).

This combination handles 95% of apps with minimum boilerplate.

Manual form state with useState gets painful fast. React Hook Form handles refs, validation, errors, and only re-renders the inputs that changed.

type FormValues = {
    email: string;
    password: string;
};

export function LoginForm() {
    const {
        register,
        handleSubmit,
        formState: { errors, isSubmitting },
    } = useForm<FormValues>({
        defaultValues: { email: '', password: '' },
    });

    const onSubmit = async (values: FormValues) => {
        await login(values);
    };

    return (
        <form onSubmit={handleSubmit(onSubmit)}>
            <input
                type="email"
                {...register('email', {
                    required: 'Email is required',
                    pattern: { value: /^[^@]+@[^@]+$/, message: 'Invalid email' },

            />

            <input
                type="password"
                {...register('password', {
                    required: 'Password is required',
                    minLength: { value: 8, message: 'Min 8 chars' },

            />

            <button type="submit" disabled={isSubmitting}>
                {isSubmitting ? 'Logging in…' : 'Log in'}

}

Module 42
Testing Philosophy

The testing pyramid for frontend

         ┌─────────┐
         │  E2E    │   few — full user flows in real browser (Playwright)
         └─────────┘
       ┌─────────────┐
       │ Integration │  some — multiple components together,
       │   tests     │  with mocked network (RTL + MSW)
       └─────────────┘
     ┌──────────────────┐
     │   Unit tests     │  many — pure functions, hooks, utilities
     └──────────────────┘

Test what users do, not how it's built

Kent C. Dodds' rule: "the more your tests resemble the way your software is used, the more confidence they can give you." Don't test internal state or implementation details. Test what's rendered and what happens when users click.

Bad — testing implementation

const wrapper = mount(<Counter />);
expect(wrapper.state('count')).toBe(0);
wrapper.instance().increment();
expect(wrapper.state('count')).toBe(1);
// Breaks if you refactor to hooks or rename state.

Good — testing behavior

render(<Counter />);
expect(screen.getByText('0')).toBeInTheDocument();
await userEvent.click(screen.getByRole('button', { name: /increment/i }));
expect(screen.getByText('1')).toBeInTheDocument();

What to test (priority order)

  1. Critical user flows (login, checkout).
  2. Business logic (validation rules, calculations).
  3. Custom hooks and utilities.
  4. Components with non-trivial logic.
  5. Integration with APIs (mocked).

What you DON'T need to test

  • Trivial components (a div with text).
  • Third-party library internals.
  • Type-checked-by-TypeScript stuff.
  • Visual styling (use visual regression tools instead).

MSW for API Mocking

MSW (Mock Service Worker) intercepts network requests at the network level. Same mocks work in tests AND in browser dev — your app makes real fetch calls, MSW catches them.

npm i -D msw

// src/test/handlers.ts
import { http, HttpResponse } from 'msw';

export const handlers = [
    http.get('/api/users/:id', ({ params }) => {
        const id = Number(params.id);
        if (id === 42) {
            return HttpResponse.json({ id: 42, name: 'Alice', email: 'a@b.com' });
        }
        return new HttpResponse(null, { status: 404 });
    }),

    http.post('/api/users', async ({ request }) => {
        const body = await request.json();
        return HttpResponse.json({ id: 99, ...body }, { status: 201 });
    }),

    http.get('/api/users', () => HttpResponse.json([
        { id: 1, name: 'Alice' },
        { id: 2, name: 'Bob' },
    ])),
];

// src/test/server.ts
import { setupServer } from 'msw/node';
import { handlers } from './handlers';
export const server = setupServer(...handlers);

// src/test/setup.ts
import { afterAll, afterEach, beforeAll } from 'vitest';
import { server } from './server';

beforeAll(() => server.listen({ onUnhandledRequest: 'error' }));
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

Per-test override

it('handles 500', async () => {
    server.use(
        http.get('/api/users', () => new HttpResponse(null, { status: 500 }))
    );

    render(<UsersList />);
    expect(await screen.findByText(/error/i)).toBeInTheDocument();
});

Why MSW beats fetch mocks

  • You don't mock the function — you mock the network. Real fetch still runs.
  • Same mocks work in dev (browser): tell developers no backend needed.
  • Catches contract drift — if your code changes the URL, MSW reports unhandled.
  • Lets you test loading/error/success paths simply by overriding handlers.

Module 47
React Re-renders — How & When

When does a component re-render?

  1. Its state changes.
  2. Its parent re-renders (and it doesn't bail out).
  3. Its context value changes (and it consumes that context).

Important: re-render ≠ DOM update

Re-rendering means React calls your component function. The actual DOM only changes if the diff finds differences. So most re-renders are cheap. Don't optimize what you can't measure.

The cascade

function App() {
    const [count, setCount] = useState(0);
    return (
        <div>
            <button onClick={() => setCount(c => c + 1)}>{count}</button>
            <ExpensiveTree />     {/* re-runs every click! */}
        </div>
    );
}

Every click on the button re-renders the whole App, including ExpensiveTree. Three fixes:

Fix 1 — Move state down

function App() {
    return (
        <div>
            <Counter />             // state lives here
            <ExpensiveTree />       // unaffected
        </div>
    );
}
function Counter() {
    const [count, setCount] = useState(0);
    return <button onClick={() => setCount(c => c + 1)}>{count}</button>;
}

Fix 2 — Lift content up via children prop

function App() {
    return <Counter><ExpensiveTree /></Counter>;
}
function Counter({ children }: { children: React.ReactNode }) {
    const [count, setCount] = useState(0);
    return (
        <div>
            <button onClick={() => setCount(c => c + 1)}>{count}</button>
            {children}        {/* same element ref each render — won't re-render */}
        </div>
    );
}

Fix 3 — React.memo

const ExpensiveTree = React.memo(function ExpensiveTree() { ... });
// Won't re-render unless its PROPS change (shallow compare).

The Profiler

Open React DevTools → Profiler tab. Record an interaction; it shows each render's duration and why. The fastest way to find expensive re-renders.

Module 48
memo / useMemo / useCallback (the right way)

The trio

APISkips re-render ofCost if misused
React.memo(C)Component C when props are reference-equalAdds shallow-compare overhead
useMemo(fn, deps)—Adds memo overhead; useless if deps churn
useCallback(fn, deps)—Same; only helps if consumer is memoized

The "useless memo" pitfall

Bad — memo broken by inline objects/fns

const Child = React.memo(ChildImpl);

function Parent() {
    return (
        <Child
            data={{ a: 1 }}                {/* new object each render */}
            onClick={() => doStuff()}      {/* new function each render */}
        />
    );
}
// Child re-renders anyway. Memo did nothing.

Good — stable references

const Child = React.memo(ChildImpl);

function Parent() {
    const data = useMemo(() => ({ a: 1 }), []);
    const onClick = useCallback(() => doStuff(), []);
    return <Child data={data} onClick={onClick} />;
}

When to actually use them

  • useMemo: an expensive computation that you'd rather not redo.
  • useCallback: passing a function to a memoized child or as a hook dep.
  • React.memo: a component that's expensive AND its parent re-renders often.

The React Compiler

The React team is shipping an automatic memoizing compiler (in beta in 2026). When stable, it'll remove the need for most useMemo/useCallback/memo by hand. Until then: profile, don't pre-optimize.

Module 53
Error Boundaries & Suspense

Error boundaries

Catch render errors in a subtree and show a fallback. React doesn't yet have a hook for this — class component is required.

import { Component, ReactNode } from 'react';

type Props = { fallback: ReactNode; children: ReactNode };
type State = { hasError: boolean; error?: Error };

export class ErrorBoundary extends Component<Props, State> {
    state: State = { hasError: false };

    static getDerivedStateFromError(error: Error): State {
        return { hasError: true, error };
    }

    componentDidCatch(error: Error, info: React.ErrorInfo) {
        // Log to your error tracker (Sentry, Rollbar, App Insights)
        console.error('Render error', error, info);
    }

    render() {
        return this.state.hasError ? this.props.fallback : this.props.children;
    }
}

// Use
<ErrorBoundary fallback={<p>Something went wrong.</p>}>
    <Routes />
</ErrorBoundary>

Or use react-error-boundary npm package — provides hooks and reset behavior.

Error boundaries DON'T catch: errors in event handlers, async errors, server-rendering errors, or errors thrown in the boundary itself. For those, use try/catch or React Query's onError.

Suspense

Module 61
Interview Questions

Q: What does React do that vanilla JS doesn't?
It maintains a declarative tree of UI as a function of state, then efficiently patches the DOM via reconciliation. You describe what the UI should be; React figures out what to change.
Q: Why must list items have unique keys?
Keys let React identify items across renders. Without stable keys, items might be re-created instead of moved, losing focus, animations, and component state — and rendering becomes O(n²) in the worst case.
Q: Difference between controlled and uncontrolled inputs?
Controlled — React holds the value in state and renders it. Uncontrolled — DOM holds the value; React reads via ref. React Hook Form uses uncontrolled internally for performance.
Q: What are the rules of hooks?
Only call hooks at the top level (no loops/conditions/nested fns) and only from React functions or other hooks. The plugin react-hooks/rules-of-hooks enforces this.
Q: Why is React's component pure?
For a given input (props, state, context) the same JSX should be produced. Side effects belong in useEffect or event handlers. Purity allows React to safely re-render and to move work between renders.
Q: Differences: useState vs useReducer?
useState is per-piece; useReducer is one state object updated through actions. Use reducer when state has many shapes/actions or when transitions need to be testable in isolation.
Q: Why prefer React Query over useEffect for data?
It handles caching, deduplication, refetch on focus/reconnect, loading/error states, optimistic updates, and request cancellation. With useEffect you re-write all of that and it never quite works the same.
Q: What's a stale closure in useEffect?
A closure captures variables from the render in which it was defined. If your effect's deps array misses a value, the effect uses the old value forever — silent stale-state bugs. ESLint's exhaustive-deps catches them.
Q: When does a component re-render?
When its own state changes, when its parent re-renders (and it doesn't bail out via memo), or when context it consumes changes.
Q: When does React.memo help?
When a component is expensive, its parent re-renders often, and its props are reference-equal across renders. Pair with useMemo/useCallback for object/function props or move state down to avoid the cascade.
Q: Difference between useMemo and useCallback?
useMemo caches a value; useCallback caches a function. useCallback(fn, deps) is shorthand for useMemo(() => fn, deps).
Q: Why are mutations bad for React state?
React detects changes by reference equality. Mutating an array/object in place doesn't change its reference, so React skips the re-render. Always create new objects/arrays for state updates.
Q: What is Suspense for?
Pause rendering of a subtree until a resource (lazy import, data) is ready, showing a fallback. Lets React coordinate loading states across many components.
Q: Why do effects sometimes run twice in dev?
StrictMode intentionally mounts → unmounts → remounts in development to expose missing cleanups. Real production behavior runs once. If your effect breaks under StrictMode, you have a cleanup bug.
Q: What's the difference between type and interface?
Both describe object shapes. Interfaces auto-merge across files (declaration merging) and read more naturally for class-like contracts. Types can also represent unions, intersections, primitives, mapped/conditional types. Modern code uses both interchangeably for objects.
Q: What is type narrowing?
The compiler refining a union type as you check it (typeof, in, equality, custom type guards). Lets you write code that's safe with each member of a union.
Q: When would you use a discriminated union?
When a value has different shapes depending on a field. The "discriminant" lets the compiler narrow precisely. Used heavily for state machines, action types, props with mode flags.
Q: What's as const for?
Tells TypeScript to infer the narrowest possible literal types and mark properties readonly. Good for option lists, action types, configs that should be const.
Q: When NOT to use Context?
For server data (use React Query), for state that changes frequently (re-render storms), or for things that just two components share (lift state up instead).
Q: What is hydration?
Attaching React event handlers and state to HTML rendered on the server. Mostly relevant in Next.js / SSR setups; pure-CSR Vite apps don't have it.
Q: How do you style React apps?
Modern stack: Tailwind utility classes for most things, cva for variant components, semantic tokens for theming. CSS-in-JS (styled-components, emotion) is on its way out for new projects.
Q: How do you handle errors in React?
Render errors → ErrorBoundary. Async/event errors → try/catch and report to a tracker. API errors → React Query's onError + a toast. Unhandled rejection & window.onerror → global handlers reporting to Sentry/App Insights.
Q: Why is useState's initial value sometimes a function?
Because the value passed directly is computed on every render even though it's only used the first time. Pass a function (lazy initializer) for expensive computations to run only once.
Q: What's the best default for testing React?
Vitest + React Testing Library + MSW + Playwright for E2E. Test user-visible behavior, not implementation details.

        ApiService.post<BankApi>(URL, toBankApi(data)).then(toBank),
    // ...
};

Cost: real work, must be done per service. Benefit: components and types use idiomatic camelCase; backend can rename fields safely behind the mapper. Decide as a team — half-done is worse than not done.

What NOT to do

  • Don't introduce Redux/Zustand — React Query + Context handles state here. CLAUDE.md is explicit; respect it.
  • Don't switch routing libraries. React Router 7 is current and battle-tested in this app.
  • Don't migrate to Next.js or RSC for this project unless there's a strong product reason. Vite SPA + the existing infrastructure works.
  • Don't add CSS-in-JS. Tailwind is the established convention.
  • Don't break domain boundaries. If you genuinely need to share something across account/task, move it to shared with care.

Test what brings the most value

  1. The auth/token-refresh flow — concurrency-sensitive, security-critical.
  2. Permission helpers — anything that gates UI must be verified.
  3. Validation schemas — catch regressions on rules that protect data quality.
  4. Mutation hooks — verify cache invalidation patterns work.
  5. Critical Playwright flows — login, OTP, organization switch, create invoice end-to-end. You already have Playwright; expand it.

Testing principles

  • Test what users do, not implementation. Use accessible queries (getByRole, getByLabelText).
  • One behavior per test.
  • No real network — MSW intercepts. No real timers — use vi.useFakeTimers() when needed.
  • Keep test files next to the code (e.g. BankForm.test.tsx next to BankForm.tsx) — easier to find and maintain.
  • Snapshot tests are fragile — avoid except for stable static markup.
